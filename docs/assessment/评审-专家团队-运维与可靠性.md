# 评审报告：运维与可靠性专家视角

- 评审对象：Hydra-Multipath-Proxy（v1.0 交付状态，TCP/TLS 转型后）
- 评审角色：专家团队之运维与可靠性
- 评审日期：2026-10
- 证据基线：README.md、`deploy/`（install.sh / hydra-node.service / env.example / 99-hydra-bbr.conf / docker/*）、`docs/guides/部署指南.md`、`docs/assessment/部署运维评估.md`、`hydra-node/src/`（tcp_server.rs / health.rs / main.rs / config.rs）、`hydra-protocol/src/handshake.rs`、仓库目录结构（`.github/` 不存在）

## 一、总评分与结论

**总评分：7.5 / 10（良好，服务器侧运维闭环已成型，客户端分发与监控告警是主要短板）**

结论：上一轮部署运维评估（`docs/assessment/部署运维评估.md`）列出的 P0 项**基本全部落实且有据可查**——systemd unit（含 WorkingDirectory 证书陷阱修复、非 root + CAP_NET_BIND_SERVICE、EnvironmentFile 密钥管理、沙箱加固）、install.sh 一键安装（幂等、密钥不覆盖）、Docker/compose、/health 健康端点、防火墙与三类静默故障排障表、升级流程文档均已交付。资源耗尽防护（Semaphore 连接额度 + 快速失败、TLS 握手 10s 超时、认证阶段 10s 超时、300s idle 看门狗）在源码中真实存在且注释清晰。日志脱敏与排障的平衡处理得当（info 级 SHA-256 短哈希 + debug 明文逃生门）。

主要问题集中在三处：**① Windows 客户端零分发产物、零 CI（仓库无 `.github/`）；② 健康端点只回答"进程活着"，不回答"数据面健康"，且无任何指标/告警接入点；③ 升级流程存在一个真实的操作陷阱（install.sh 重装后旧进程不会自动加载新二进制）**。此外文档存在密钥长度表述不一致的遗留（env.example 写"至少 16 字节"，代码强制恰好 32 字节），会在排障时误导运维。

## 二、亮点（均有代码/文档证据）

1. **systemd unit 质量高于同类自建项目平均水平**（`deploy/hydra-node.service`）：
   - `WorkingDirectory=/etc/hydra` 显式修掉"证书写到 `/` 导致客户端全员失配"的 CWD 陷阱（unit 第 14-19 行，注释直接引用部署评估坑③）；
   - 非 root 运行 + `AmbientCapabilities=CAP_NET_BIND_SERVICE` + `CapabilityBoundingSet` 单能力白名单（34-37 行）；
   - `ProtectSystem=strict` + `ReadWritePaths=/etc/hydra` + `PrivateTmp` + `RestrictAddressFamilies` 全套沙箱加固（41-48 行）——很多正式项目都做不到这个完整度。
2. **install.sh 幂等且密钥安全**（`deploy/install.sh`）：`/etc/hydra/env` 已存在则保留（81-83 行"升级不覆盖密钥与证书"）；密钥自动 `openssl rand -hex 32` 生成、600 权限、属主 hydra；明确拒绝 `--auth-key` 之外的密钥泄漏面。配套地，`hydra-node/src/main.rs:21-28` **移除了 `--auth-key` CLI 参数**并解释原因（进 cmdline 全机可读），代码与文档口径一致。
3. **资源耗尽防护四件套真实落地**（`hydra-node/src/tcp_server.rs`）：
   - TLS 握手 10s 超时（第 37 行，slowloris 防护，注释说明动机）；
   - 认证阶段 10s 超时（第 34 行）；
   - 转发 idle 看门狗默认 300s，env 可调且 `clamp(30, 86400)` 防呆（41-51 行）；
   - `HYDRA_MAX_CONNECTIONS` 用 Semaphore 强制，**额度满 `try_acquire_owned` 立即丢弃**而非在 backlog 排队（105-108 行，主动 shedding，注释说明客户端有故障切换兜底）。
4. **BBR sysctl 部署有降级反馈而非静默失败**（`deploy/install.sh:121-132`）：安装 99-hydra-bbr.conf 后回读 `tcp_congestion_control` 验证，不支持（如 OpenVZ）打警告保持 CUBIC——这是运维脚本应有的姿态。
5. **排障文档直击"静默关流"这一自身设计带来的痛点**（`docs/guides/部署指南.md` §4）：把"防火墙未放行 / 密钥不一致 / 端口错 / 证书指纹不匹配"四种在两端日志中**看起来一样（什么都没有）**的故障做成症状→确认方法（tcpdump / ss / openssl fingerprint）→修复的对照表，并说明可用 `/health` 先区分"进程死"与"链路断"。脱敏与排障的平衡也交代清楚（§6：info 级短哈希，`RUST_LOG=hydra_node=debug` 明文逃生门）。
6. **健康端点小而正确**（`hydra-node/src/health.rs`）：默认只绑 `127.0.0.1:8081`（env.example:30-31 反复警告勿绑 0.0.0.0）；绑定失败**显式退出进程**而非吞掉（main.rs:141-148，注释"静默吞掉会让运维以为拨测已接入"——这个意识很好）；读首行 1KB 上限 + 5s 超时防异常客户端（119-125 行）。
7. **对上一轮评估的改进落实是可验证的**：部署评估缺失清单 8 项中，1（systemd/install.sh）、2（GUI 配置持久化+首启向导，README 39 行）、3（/health + 排障决策表）、6（证书固定 /etc/hydra）、7（journald 说明）已落实；第 8 项"config 死代码"也反转为可用的分层配置（main.rs:73-97，`--config > env > node.toml > 默认值`，显式报错不静默回落）。

## 三、问题清单（按优先级）

### P0（影响交付/排障成败）

| # | 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P0-1 | **Windows 客户端无任何分发产物、仓库无 CI** | 全库无 `.github/` 目录（glob 验证）；`deploy/install.sh:11-13` 自述"没有远程发布产物（无 GitHub release、无预编译包）"；README 环境要求直接要求用户自装 Rust 工具链 | GUI 是主打卖点（README"GUI 客户端（推荐）"），但目标用户（Windows 小白）恰恰最不可能装 Rust；exe 未签名 + 自编译，SmartScreen 与 TUN（wintun.dll）两道门槛叠加，客户端侧实际不可交付 | 加 GitHub Actions：`windows-latest` 构建 `hydra-client-gui`（含 wintun.dll 下载或打包指引）+ `ubuntu-latest` musl 静态构建 `hydra-node`，tag 触发 release。约 1 天工作量，是当前 ROI 最高的一项 |
| P0-2 | **升级后新二进制不生效的陷阱**：install.sh 对已运行服务执行 `systemctl enable --now`，**不会重启已运行的单元**，旧进程继续跑旧二进制 | `deploy/install.sh:114`；`docs/guides/部署指南.md:93` 只含糊写"若 install.sh 未自动重启"——实际上它从不重启 | 运维按文档"git pull → install.sh → 完成"操作后以为已升级，实际版本未变；且无 `--version` 子命令（main.rs --help 输出无版本行），无法快速核实 | install.sh 末尾对 active 状态的服务追加 `systemctl restart hydra-node`（或至少打印醒目提示）；给 hydra-node 加 `--version` / 启动日志打印 `CARGO_PKG_VERSION` |
| P0-3 | **密钥长度文档不一致，排障误导**：`deploy/env.example:7,34` 仍写"解码后**至少 16 字节**"，而代码强制**恰好 32 字节**（`hydra-protocol/src/handshake.rs:128-133`，注释明确说"文档曾允许 ≥16B"是审查修正项），README:163 已改为"恰好 32 字节" | 见左 | 运维照 env.example 生成 16-31 字节密钥 → 握手期静默关流，正是部署指南 §4 说的"无日志"故障族 | 修正 env.example 两处为"恰好 32 字节"；env.example 属部署套件，与 README 的不一致属于文档回归 |

### P1（可靠性/可观测性缺口）

| # | 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P1-1 | **/health 只反映进程存活，不反映数据面健康** | `hydra-node/src/health.rs:52-57`：响应恒 `status:ok`，字段仅 mode/uptime/version；无当前连接数、额度使用率、最近握手成功与否 | 数据面假死（如证书目录被清、句柄异常）时探活仍全绿；负载均衡摘流/告警都拿不到依据 | /health 加入 `active_connections`、`max_connections`（Semaphore 可用 permits 可查）；可选 `?deep=1` 触发一次本地自检（证书文件可读、监听仍在） |
| P1-2 | **无指标端点、无告警文档** | 全库无 Prometheus/metrics 相关代码；部署指南 §6 只有手动 curl 与 journalctl | 连接额度打满、Offline 节点比例、idle 断连频率等全靠人肉翻日志；额度满时的 `debug!("Connection limit reached")`（tcp_server.rs:106）甚至默认不可见 | 最小方案：/health JSON 扩字段即可被 node_exporter 式脚本采集；进阶：`/metrics`（prometheus crate，半天）；部署指南补一节"拨测 + 告警建议"（探 443/tcp 握手 + /health 双探针） |
| P1-3 | **认证失败完全静默，无计数钩子，fail2ban/防扫描无法对接** | 部署评估 §4 已指出；`tcp_server.rs:118-124` 失败仅 `debug!`，无计数器 | 反探测设计与可观测性冲突时，现在一边倒向静默：被扫描/爆破时运维毫无感知 | 保持零回显不变，但节点侧内存计数（每 IP / 全局握手失败率），超阈值打一条不含细节的 warn（"N handshake failures in 60s from X.X.X.X"）；文档给 fail2ban 可选对接思路 |
| P1-4 | **日志无文件输出/轮转，Docker 场景未交代** | `hydra-node` 仅 stdout（main.rs init_tracing）；部署指南 §6 说"systemd 走 journald 即可"，但 Docker 章节（部署指南 §2）未说明日志去向与 `max-size` 限制 | Docker 默认 json-file 无上限，长跑节点可写满磁盘——这是部署套件自己引入的新场景，原评估坑⑦只解决了一半 | compose 加 logging: {driver: json-file, options: max-size/max-file}；或文档注明用 journald log-driver |
| P1-5 | **回滚流程依赖"旧 commit 重构建"**（部署指南 §5:99），无版本化产物/镜像 tag | `hydra-node:latest`（docker-compose.yml:14）、无 release tag 流程 | 线上出问题时"检出旧 commit 现场编译"既慢又不可复现（依赖树已漂移，Cargo.lock 之外的系统工具链不受控） | CI 出产物后自然获得版本化 tag（`ghcr.io/.../hydra-node:v1.x`）；systemd 路线至少文档化"保留上一版二进制为 hydra-node.bak，回滚 = mv + restart" |

## 五、改进路线建议

**第一阶段（本周可做，合计约 2 人日）**
1. CI + release：GitHub Actions 出 Windows GUI zip（附 wintun.dll 说明）+ Linux musl 静态 hydra-node（P0-1）。

## 六、一句话结论

服务器侧"从裸 VPS 到受守护、可探活、可排障的生产节点"这条链路已经是同类个人项目中的上乘水准，且上一轮评估的整改是真刀真枪落了地的；但**客户端分发（CI/预编译/签名）与监控告警（指标/计数/告警文档）两块仍然是空白**，P0-2 的升级重启陷阱和 P0-3 的文档回归属于低成本高收益的立即可修项。
