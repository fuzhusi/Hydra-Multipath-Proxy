# 开源代理高性能内核与日志实践调研报告

> 调研目的：为 Hydra-Multipath-Proxy（Rust 加密代理）的内核（数据面）优化方案提供「可借鉴点」参考。**只借鉴思路与设计模式，不照抄代码**（sing-box/mihomo 为 GPL-3.0，直接照抄代码会有许可证污染风险）。
>
> 调研对象：sing-box、mihomo(clash.meta)、clash-rs、leaf；Rust 生态日志（tracing / tracing-appender）；quinn/hyper 等高性能网络库。
> 调研时间：2026-10

---

## 一、sing-box（Go，GPL-3.0）

仓库：[SagerNet/sing-box](https://github.com/SagerNet/sing-box)　文档：[sing-box.sagernet.org](https://sing-box.sagernet.org/configuration/log/)

### 数据面关键设计

1. **TUN 双栈可选：gVisor（纯用户态 netstack）与 system（系统栈）+ 混合栈**。gVisor 栈实现完整 TCP 状态机在用户态，兼容性好但吞吐低于直接走内核；system 栈利用系统 TCP 栈（macOS/Windows 上实际是 utun + 本地回环转发），性能更好；`stack: mixed` 则 UDP 走 system、TCP 走 gVisor，取两者之长。启示：数据面应允许「实现完整 TCP 栈」与「借用内核栈」两条路径并存并按平台/场景选择。（参考 [sing-box TUN 性能分析](https://deepwiki.com/shtorm-7/sing-box-extended/17.1-tun-performance-analysis)、[sing-box 文档](https://sing-box.sagernet.org/configuration/inbound/tun/)）
2. **UDP NAT 表带 TTL 生命周期管理**：sing-box 与 mihomo 同源思路，UDP 会话是「无连接」的，必须有超时回收（默认约 60s，按包刷新），避免表无限膨胀。超时通过后台定时扫描 + 惰性删除结合实现，而非每包同步检查。（参考 [sing-box UDP NAT 配置](https://sing-box.sagernet.org/configuration/shared/udp-nat/)）
3. **每连接 buffer 归属单一任务、按需分配、上限封顶**：sing-box 的 `sing-bufio` 提供固定大小 buffer 的复用（sync.Pool 风格）与 `CopyWithTimeout` 类带限速/统计的拷贝原语；拷贝循环里读写共用同一个 buffer，避免每包 malloc。启示：**数据面热路径的关键不是花哨零拷贝，而是「一次分配、循环复用」**。
4. **日志系统：统一门面 + 全局级别 + 时间戳开关 + 输出重定向（stdout/file）**，sing-box 1.x 引入基于 slog 的结构化日志，按上下文携带 inbound/outbound/rule 等字段，便于 GUI 端解析展示；无内置按大小轮转，而是依赖 systemd/logrotate 或 GUI 客户端管理。（参考 [sing-box Log 文档](https://sing-box.sagernet.org/configuration/log/)）
5. **核心/规则解耦**：路由、DNS、出站都是接口抽象，数据面只看到「连接」和「包」两个抽象，热路径不做任何 map 查找以外的动态分配。

## 二、mihomo / clash.meta（Go，GPL-3.0）

仓库：[MetaCubeX/mihomo](https://github.com/MetaCubeX/mihomo)

### 数据面关键设计

1. **UDP NAT 表：以「客户端五元组」为 key 的 `Table`，`GetOrCreate` 原子创建会话**。API 设计值得借鉴：`GetOrCreate(key, maker)` 保证并发下同一 key 只建一个 sender；另有 `GetOrCreateLockForLocalConn` 返回 `*sync.Cond`，用「条件变量占位」避免同一流在会话建立窗口内重复建连或丢包。（参考 [mihomo component/nat 包文档](https://pkg.go.dev/github.com/metacubex/mihomo@v1.19.19/component/nat)，源码 [table.go](https://github.com/metacubex/mihomo/blob/dev/component/nat/table.go)）
2. **UDP 会话超时用「带超时秒表的 map + 定时清理循环」**：`nat/timeoutset` 维护带超时的 key 集合，每包 touch 刷新，独立 goroutine 周期扫描删除。比给每个会话挂 timer 更省资源（万级会话时 timer 数量爆炸）。Hydra 可对应为分桶时间轮或惰性扫描。
3. **UDP 回包路径 `WriteBack` 抽象**：proxy 返回的连接不绑定本地端口，回写时按原始源地址写回（NAT 回程），使「一个上游 socket 服务多个客户端」成为可能——对 Hydra 多路径聚合场景很有参考意义：**聚合 socket 与会话表分离**。
4. **TUN 侧批量读 + 立即写**：mihomo 的 TUN inbound（基于 [tun2socks/sing-tun](https://github.com/metacubex/sing-tun) 思路）单 goroutine 循环读 TUN 设备、解析 IP 包后按流分发；写路径使用 channel 聚合回包再写设备，减少系统调用次数。gVisor netstack 用于需要完整 TCP 语义的场景。
5. **内存占用问题被社区长期关注**（见 [V2EX 讨论](https://global.v2ex.co/t/1018671#reply12)）：经验是 GC 语言里**池化要慎用**，sync.Pool 语义是「GC 时清空」，稳态下 buffer 反复升降级；Rust 侧没有 GC，可以直接用更确定的池策略（对象池 + 显式归还），这是 Rust 实现能比 Go 版本更省内存的结构性优势。

### 日志系统

- 全局 `log level`（silent/error/warning/info/debug）+ `log-format`（text/json），运行时通过 API 热更新级别；
- 日志在连接级打印「起始/关闭 + 上下文链（规则、出口、延迟）」，用「连接结束日志」代替逐包日志——**热路径默认零日志**，这是所有高性能代理的共识；
- 外部 GUI 通过 Clash API 的 log stream（websocket）拿日志，核心本身不做 GUI 展示与环形缓冲，展示职责在客户端。Hydra 若自带 GUI，需要自己补这一层（见第六节）。

## 三、clash-rs / leaf（Rust 代理实现）

### clash-rs（[Watfaq/clash-rs](https://github.com/Watfaq/clash-rs)，Apache/MIT 系）

1. **全 tokio 异步栈，TUN 设备用 `tun` crate 封装为 AsyncDevice**，IP 包读取后交给统一的「流分发器」：TCP 由内嵌 netstack（基于 smoltcp 或 netstack-smoltcp）重组为 `AsyncRead/AsyncWrite` 流，之后与 SOCKS 入口完全同构。启示：**TUN 只是又一个 inbound，数据面应尽早把包世界转成流世界，收敛到单一拷贝循环**。
2. **buffer 复用方式朴素但有效**：主要依赖 `bytes` crate 的 `BytesMut` + `split_to` 语义做读写缓冲，copy loop 中一次性 reserve 到 MTU 级容量后反复利用；没有自研池。启示：Rust 生态下 `bytes::BytesMut` 本身就是引用计数切片，**多数「自研内存池」是过度设计**。
3. **UDP 会话**：以 (源地址, 端口) 为 key 的 map + tokio task per session + 空闲超时（spawn 一个 sleep 循环做超时回收），实现直接，是 Hydra UDP NAT 的最小可行参考。

### leaf（[eycorsican/leaf](https://github.com/eycorsican/leaf)，Apache-2.0）

（README 摘录见 [leaf/README](https://github.com/eycorsican/leaf/blob/master/README.md)）

1. **协议栈可选 lwip 或 smoltcp**：leaf 用 C 的 lwip（FFI）与纯 Rust 的 smoltcp 两套 TCP/IP 栈，C 层用 `Box::into_raw`/callback 边界桥接。启示：完整用户态 TCP 栈选型上，smoltcp 在 Rust 里可直连且可裁剪特性，但大流量下其逐包 `OwnedBox` 分配需要自己加对象池。
2. **自研 AMux 多路复用与 MPTP（多路径聚合）**——leaf 是少数实现了「多路径传输聚合」的开源代理（[MPTP 架构文档](https://github.com/eycorsican/leaf/blob/master/docs/mptp_architecture.md)），其「子流调度 + 帧复用」对 Hydra 的 multipath 场景有直接的概念参考价值（调度策略、按序重组缓冲）。
3. **移动端集成姿态**：leaf 编译为静态库供 iOS/Android 调用，日志通过回调导出给宿主 App。对 Hydra 桌面 GUI 的启示：**核心暴露「日志订阅 API」而不是自己管理 UI 日志**。
4. **性能取向**：leaf 在 QUIC 入口上直接使用 quinn-proto 层（而非 quinn 整库），能自己控制缓冲与调度——说明「用 proto 库、自管 IO」是高级优化路径，成本高，非首选。

## 四、Rust 日志体系最佳实践

### 门面与订阅模型

- **`log` 是门面（宏 + 静态 Logger），`tracing` 是结构化追踪（span/event + subscriber）**。代理核心这种「长任务 + 上下文（连接 ID、路径 ID）」场景应选 tracing：span 让「一个连接从建立到关闭」的所有日志自动携带上下文，不用每行手写 conn_id。（参考 [tracing 文档](https://docs.rs/tracing)、[log vs tracing 对比讨论](https://blog.gitcode.com/2aaf5c91b1332e148e74c199c9725a49.html)）
- **运行时过滤**：`tracing_subscriber::EnvFilter`（`RUST_LOG` 风格语法）支持按模块 target + 级别过滤，如 `hydra_core=debug,hydra_tun=trace,warn`。热重载可用 `tracing_subscriber::reload::Layer` + `Handle::reload`（见 [tracing #2682 示例](https://github.com/tokio-rs/tracing/issues/2682)），GUI 的日志级别开关直接映射到它。
- **双门面兼容**：依赖库多用 `log`，自用 `tracing`，加 `tracing-log` 桥接，避免丢日志。

### 文件轮转与高吞吐

- `tracing-appender`：`rolling::daily/hourly/never` 按时间轮转 + `non_blocking` 异步写入（内部有界 channel + 专用写线程，工作线程只做入队，几乎不阻塞热路径）。**注意 WorkerGuard 必须在 main 里持有**，否则进程退出丢日志（[tracing-appender 文档](https://docs.rs/tracing-appender)、[tracing.rs 镜像](https://tracing.rs/tracing_appender/index.html#non-blocking-writer)）。轮转粒度只有「时间」，无按大小轮转——需要大小上限要自己包一层或轮换文件名。
- **采样**：tracing 没有内建逐事件采样，热路径高频事件应（a）提级别到 debug/trace 由 filter 天然过滤，（b）或自写 Layer 做计数聚合（每秒一条汇总）。这是「高性能日志」最有效的手段——**少打日志比快打日志更重要**。
- **无锁/低锁 appender 思路**：社区库（如 [claris](https://github.com/ceyhn/claris)、环形缓冲类 [duck-ttlog](https://explore.market.dev/ecosystems/rust/projects/duck-ttlog)、[ring-log](https://crates.io/crates/ring-log)）的通用模式是「MPSC 有界通道 + 后台写线程 + 满了丢弃/阻塞策略可选」。对绝大多数应用，tracing-appender 的 non_blocking 已经够用，自研 appender 收益很小。

### GUI 程序日志到内存环形缓冲

- 典型实践：写一个自定义 `tracing` **Layer**（约 50–100 行），把事件格式化后推入 `ringbuf` 或 `VecDeque`（容量如 4096 条）+ `Arc<Mutex<…>>` 或 crossbeam channel；GUI 用定时器/信号量拉取渲染。配合 `Targets`/`EnvFilter` 在这层之前过滤，保证环里只有用户关心的级别。（参考 [ring-log](https://crates.io/crates/ring-log)、[GUI 日志查看器实践（termiHub PR #184）](https://github.com/armaxri/termiHub/pull/184)）
- 关键点：**环缓冲 Layer 挂在 filter 之后**（不占热路径预算）、崩溃前用 `WorkerGuard::flush` 或进程退出钩子把环内未落盘内容刷出。

## 五、quinn / hyper 等高性能 Rust 网络库的零分配实践

1. **`Bytes` / `BytesMut` 作为跨层缓冲货币**：quinn 在 [commit c1902ff](https://github.com/quinn-rs/quinn/commit/c1902ffb71468c32e1d83a4e154675d105ebc495) 中把 `quinn-proto` 的发送接口改为「caller-supplied memory / Bytes 数组」，消除内部打包分配（见 [issue #729](https://github.com/quinn-rs/quinn/issues/729)）。启示：**跨模块边界的 API 一开始就收 `Bytes`/`&mut [u8]`，把「谁拥有缓冲」变成显式契约**，后补的改造成本极大。
2. **写聚合（coalescing）**：quinn 一次 UDP 系统调用写多个 datagram（GSO），hyper 在 body 转发时尽量 `write_vectored`/`write_all` 大块。Hydra 对应做法：TUN 侧多包聚合读（`recvmsg` 循环尽量在单次 epoll 唤醒内清空）、出侧聚合小包。
3. **热路径避免 String/Debug 格式化**：quinn/hyper 的日志全走 `log`/`tracing` 宏，宏在级别被过滤时**参数不会求值**（惰性），所以热路径放 `debug!(?peer, ...)` 零成本——Hydra 必须保证日志宏而非 `format!` 出现在数据面。
4. **缓冲容量分级**：read buffer 按 MTU/segment 预留上限（如 64KB）一次性 reserve，避免 `BytesMut` 反复 grow 拷贝；写完 `clear()` 复用而非 drop。
5. **tokio 使用姿势**：一个连接一个 task（成本 ~几百字节，万级连接可接受），但**每连接不再各自 spawn timer**——统一用「共享的超时轮/清理循环」管理空闲连接，这正是 mihomo/sing-box 的会话表思路在 tokio 下的正确移植。

### 优先级建议（两周内可见效顺序）

1. 先做「零成本」项：#11 #12 #13 #14 #8（接口规范 + 官方库组装，合计约 4 天）；
2. 再做数据面结构性收益最大的：#1 #2 #5（UDP NAT 表 + 超时轮 + buffer 复用，约 5 天）；
3. 之后视 profile 结果推进 #7（写聚合）与 #3（TUN 流边界收敛）；
4. #4 #9 属架构级演进，单独立项。
