### Top 风险

1. **[P0] TUN 通道未就绪期间上行数据被 ACK 后静默丢弃**（tun.rs L831–846）：注释声称的"上游重传兜底"与 smoltcp ACK 机理矛盾，握手窗口内到达的 ClientHello 等字节全部被吞，连接永久挂死且无任何 RST/FIN 反馈。
2. **[P0] TUN 路由部分失败不回滚**（tun.rs apply_routes L260–265）：`0.0.0.0/1 + 128.0.0.0/1` 接管路由已生效但无人读设备，整机断网且进程退出后残留；豁免路由恰恰是最易失败的一条，路径现实。
3. **[P1] hex_decode 跨 UTF-8 char boundary panic**（auth.rs L169–180）：位于 PSK fail-fast 链路，GUI 密钥框误敲一个中文/emoji 即整个进程 abort——fail-fast 改造反成"配置非法即崩溃"。
4. **[P1] NAT 打洞主循环热自旋 + nonce 自连判定失效 + 出站未绑宣告端口**：三者共同导致打洞成功率被结构性低估、单核打满最长 10s、自连场景形成静默回环隧道。
5. **[P1] 节点 pump 按单方向计 idle**：长下载/长上传健康连接在 300s 处被稳定误杀（BT/视频流/大文件可复现）。

## P0/P1 详单

### P0

#### P0-1 [bug] tun.rs step() L831–846：通道未就绪期间的上行数据被读走后丢弃

step() 第 4 步对每条流执行 `sock.recv_slice(&mut buf)` 取走应用发来的数据；当 ProxyDuplex 尚未交付（`link_writer == None`，见 L836 `if let Some(w)`）时这些字节被直接丢弃。注释声称"上游会重传，TCP 可靠性兜底"——机理不成立：smoltcp 的 recv_slice 取走数据后，下一次 `iface.poll()` 就会为这些字节推进 ACK 与接收窗口，对端收到 ACK 后绝不会重传。

触发窗口很宽：握手完成后应用（尤其 TLS 客户端）通常立即发 ClientHello，而 up_task 开代理通道要经 TCP+TLS+Noise 握手，耗时数百毫秒至 OPEN_TIMEOUT 15s 不等，期间到达的上行字节全部被静默吞掉。结果：连接看似建立但永久挂死（TLS 双方互等），无任何 RST/FIN 反馈。回环集成测试未暴露，因 mock_opener 同步建链、数据在 Link 之后才发送。

**修复**：通道未就绪时不要 recv_slice——把 L831 的读取包在 `if let Some(w) = flow.link_writer.as_mut()` 内（数据留在 smoltcp rx 缓冲，靠窗口归零产生真实背压，对端会重传）；或在 Flow 中增加 `up_pending: VecDeque<Vec<u8>>`，Link 交付时先写入积压再进入正常泵送。

#### P0-2 [bug] tun.rs apply_routes() L260–265；run_tun() L914–918：路由部分失败不回滚，造成整机断网残留

apply_routes 逐条执行，任一条失败立即 `?` 返回；此前已添加成功的路由（包括清单最前面的 `0.0.0.0/1` 与 `128.0.0.0/1` 两条接管路由）不会回滚——RouteGuard 在 L919 才构造，错误路径直接 return Err。此时 TUN 设备已创建但栈循环从未启动，无人读取设备：所有流量被 /1 路由吸进黑洞，整机断网，进程退出后残留。L916 日志"未接管流量，无残留"与实际行为相反。豁免路由（指向物理网关的 route add）恰是最易失败的一条（网关解析错、metric 冲突等），路径现实。

**修复**：apply_routes 失败时立即对该 plan 已成功部分执行 cleanup_routes（best-effort 删除已添加前缀）；或在构造 RouteGuard 之后再执行添加、失败由 guard 的 Drop 统一回滚；并修正日志文案。

### P1

#### P1-1 [bug] hydra-protocol/src/auth.rs hex_decode，L169–180：多字节 UTF-8 输入导致 panic，位于 PSK fail-fast 链路

hex_decode 用字节长度 `hex.len().is_multiple_of(2)` 做偶数检查，再按字节下标 `&hex[i..i+2]` 切片。输入含多字节字符时（如 "a中"：字节长 4 通过检查，'中'=E4 B8 AD 占 3 字节），必有切片边界落在字符内部 → `&str` 字节切片跨 char boundary 是 panic 而非 Err。

该函数位于本会话 PSK fail-fast 链路：GUI 编辑密钥框每次输入实时调用 auth_key_from_hex（main.rs:2200/2920），用户误敲一个中文/emoji 即整个 GUI 进程 abort；CLI 启动解析 HYDRA_AUTH_KEY 同理 panic。fail-fast 改造本意是消灭"配置静默不可用"，此处反成"配置非法即崩溃"。

**修复**：改为按字节处理：`let bytes = hex.as_bytes();` 偶数检查用 `bytes.len() % 2`；迭代用 `u8::from_str_radix(std::str::from_utf8(&bytes[i..i+2])..., 16)`，或在入口先拒绝非 ASCII（`!hex.is_ascii() → Err`）。补一条含多字节字符输入的单测。

#### P1-2 [bug] hydra-node/src/tcp_server.rs pump() L273–279（接线 L245–249）：idle 超时按单方向计时，误杀长下载/长上传健康连接

文档注释（L39、L264）声称"双向均无数据达此时长即静默双向关闭"，但实现是在每个 pump 内对各自的 `r.read` 包 `timeout(idle)`（L273），即**每方向独立**计空闲。典型 HTTP GET 下载：客户端发出请求后 c2t 方向可能连续数百秒零字节（纯接收），c2t pump 在默认 300s（HYDRA_IDLE_TIMEOUT_SECS，L40）触发 break → L286 shutdown 目标写端 → 目标服务器读侧见 EOF、发完剩余数据后正常关闭 → 下载在 5 分钟处被静默掐断。大上传（t2c 长时间无数据）同理。直接违背转发层"空闲才断"的设计意图，且是用户可稳定复现的存量连接中断（BT/视频流/大文件）。注意即便 HTTP 层有心跳，TLS 层客户端不发记录就等于 c2t 零字节，应用层 keep-alive 救不了。

**修复**：把 idle 从"每方向独立看门狗"改为"共享最后活跃时间戳"：用 `Arc<Mutex<Instant>>`（或 AtomicU64 毫秒）在两个 pump 间共享，任一方向成功读到 n>0 字节即刷新；每个 pump 循环改为 `if last_active.elapsed() >= idle { break }` 后再做无超时 read（或保留 read 包超时但以共享时间戳判定是否真正全局空闲）。

#### P1-3 [performance] hydra-client/src/nat.rs punch_open_and_verify 主循环，L408、L427–457：connect 通道耗尽后热自旋，单核打满最长 10s

nat.rs:393–408 为每条候选 spawn connect 任务后 `drop(conn_tx)`（L408）。tokio mpsc 在"已关闭且为空"时 `recv()` 立即返回 None。典型时序：所有 connect 在窗口开始后几毫秒内完成（ECONNREFUSED 快速失败或建成转入 verify 任务），此后主循环（L427–457）每次迭代 select 的 `conn_rx.recv()` 分支都立即就绪返回 None，match 臂只做 `{}` 不 break，循环立即重建 4 个 future 再轮询——accept/verified/sleep 三个 pending future 被反复注册/注销，形成无眠忙循环，直至 10s PUNCH_WINDOW 耗尽。量化：每端每次打洞 peg 满一个 CPU 核最长 10s；test_nat.rs:388–395（dead 端口毫秒级 refuse + 2s 窗口）与 loopback 测试的 A 端都在真实执行这段热循环，只是测试进程短未引起注意。

**修复**：为两个 recv 通道引入存活标志：`conn_rx.recv()` 返回 None 时置 `conn_closed=true` 且把该臂从 select 中移除（或 fuse）；当 conn_closed 且 accept_rx 也返回 None 时直接 break。最小改法：`None => { conn_closed = true; }`，select 前若两通道皆关则 break，select 分支用 `r = conn_rx.recv(), if !conn_closed`。

#### P1-4 [bug] hydra-client/src/nat.rs random_nonce（L272–274）与 verify_stream（L312–321），配合 punch_open_and_verify L370：nonce 自连判定完全失效

模块注释（L14、L282–284）与设计文档 §7④ 声称：自连时"回显的正是自己的 nonce"。但 random_nonce() 在 verify_stream（L312）内部按连接调用：自连（本端 connect 命中本端 listener）会在同一进程内产生两个 verify 任务，各自独立生成 32B 随机数——两端 nonce 相同的概率为 2^-256，`theirs == mine`（L316）永不触发；且自连两端都是本实现，回显校验（L325）也必然通过。第一层地址过滤 `Some(peer) == laddr`（L370）只在 loopback 成立：经 NAT hairpin 的自连中对端地址呈现为 NAT 公网映射地址，不等于本端绑定地址。

结果：当候选因 peer_id 撞车/注册表残留等原因指向自身映射地址时，会建成一条自发自收的"直连"隧道并通过校验，后续代理数据在回环中静默无响应，表现为连接挂死且难以排查。Noise-PSK 握手本身拦不住（同一 PSK，client_side/server_side 配对完整）。

**修复**：nonce 改为"每端一次"：在 punch_open_and_verify 顶部生成一个 nonce，作为参数传入所有 spawn_verify/verify_stream（同进程所有验证任务共享同一值）。自连两端必然读到相同 nonce 而被拒；不同进程/对端因随机性必然不同。verify_stream 签名加 `mine: [u8; 32]` 即可，测试也更容易构造自连拒绝分支（当前 test_nat.rs:382 承认该分支无法覆盖）。

#### P1-5 [bug] hydra-client/src/nat.rs 出站 connect L397–398（对照 listener 绑定 L356–364、候选宣告 L522/541；文档假设 L11–13 与设计 §3.1）：出站连接未绑定 local_bind 端口，同时打开退化为依赖 EIF

候选宣告的是 `disc.mapped`（L522），对应 STUN 探测 socket 的本地端口 disc.local；listener 也确实绑回该端口（L356–364、L541）。但出站连接用 `tokio::net::TcpStream::connect(cand)`（L397–398），由 OS 分配另一个临时本地端口——经 EIM NAT 后它获得的是另一个独立的公网映射。于是"同时打开"的本地半边并不占用被宣告的映射：对端发往 mapped 端口的 SYN 只能由 NAT 转发给处于 LISTEN 状态的 listener socket，这条路径能否通完全取决于 NAT 的**过滤行为**（RFC 4787 EIF 才放行；address-dependent / port-dependent filtering 下必被丢弃）。而分类逻辑（design §3.1，nat.rs:164–181）只比较两次映射地址，根本不测过滤行为——"EIM → 可打洞"的推断不成立。机理上正确的做法（RFC 5128 §2.4 同时打开）是让出站 SYN 也从同一本地端口发出，使对端 SYN 与本端 SYN_SENT 在 NAT 映射上相遇。现状在 EIM+非 EIF 的网关（家用路由器中占比可观）上必失败，且每端白烧满 10s 窗口与信令往返后才回落中继；附带效应：测试用假 EIM STUN（test_nat.rs:92–120）按本地端口回填映射，恰好掩盖了这一点。

**修复**：出站连接改用 `tokio::net::TcpSocket::new_v4()` + `set_reuseaddr(true)` + `bind(local_bind)` + `connect(cand)`（Windows 允许与 listener 的 REUSEADDR 绑定共存；Linux 上需将 listener 与出站统一为"先 bind 同端口再二选一"策略，或仅在出站 socket 上做同时打开、放弃独立 listener 兜底 accept）。若平台冲突无法两全，至少在文档与 NatType 输出中如实标注"EIM 判定不含过滤行为，打洞成功率受 EIF 限制"，并考虑失败后缩短二次尝试窗口。

#### P1-6 [bug] hydra-client/src/tun.rs step() 无端点分支 L703–708；超限分支 L712–717：遗弃 SocketHandle，socket 永不移除（128KB/次泄漏），且补挂 port 0 死监听

两个分支调用 `sockets.get_mut(h).abort()` 后用 add_listener 替换 listeners[i]，句柄 h 既未加入 flows，也不再留在 listeners，随后第 5 步的 `sockets.remove(h)` 只遍历 to_remove（仅来自 flows），因此该 socket 永远留在 SocketSet 中。每个 socket 携带 TCP_BUF=64KB rx + 64KB tx 共 128KB 缓冲：端口扫描或 max_flows 长期满载（每秒几十个 RST）场景下每秒泄漏数 MB，512 次 RST 即 ~64MB，且 SocketSet 线性增长也拖慢每次 poll。另外 L706 在 abort() 之后才读 local_endpoint()，此时必为 None，`unwrap_or(0)` 会挂出一个 listen(0) 的死监听（smoltcp 对 port 0 的 listen 不会匹配任何真实连接），该端口从此不再接受新连接直到重启。

**修复**：两个分支在 abort() 前先取出 `let port = sockets.get::<TcpSocket>(h).local_endpoint().map(|e| e.port)`；删除时先 `sockets.remove(h)` 再 add_listener。port 为 0/None 时只 remove、不补挂监听并记 error。

#### P1-7 [bug] hydra-client/src/main.rs main() Ctrl+C 任务 L351–361：固定 300ms 后 process::exit(0)，跳过 RouteGuard Drop，且未处理 Windows 控制台关闭事件

Ctrl+C 任务 cancel 后仅 sleep 300ms 就 `std::process::exit(0)`。process::exit 不运行任何 Drop：若此刻 run_stack 仍阻塞在 step() 内部的 `w.write_all().await`（节点 TCP 窗口满时一次写可阻塞任意久）或 transport.send 慢调用上，栈任务未走到 break，run_tun 的 RouteGuard 未 drop，/1 接管路由全部残留 → 整机断网，只能靠"下次以管理员身份再启动一次"恢复。另外方案 §2 承诺"注册 Windows SetConsoleCtrlHandler"，实现只接了 tokio::signal::ctrl_c（SIGINT/CTRL_C_EVENT）：点 X 关控制台窗口、注销、CTRL_CLOSE_EVENT 会在无 unwind 的情况下直接终止进程，RouteGuard 同样不执行。

**修复**：① Ctrl+C 分支改为 `let _ = tokio::time::timeout(Duration::from_secs(5), tun_task).await;`（保存 spawn 返回的 JoinHandle），确认栈任务退出（guard 已 drop）后再 exit；② 用 ctrl_c 与 tokio::signal::windows::ctrl_close/ctrl_shutdown/ctrl_logoff（或按方案接 SetConsoleCtrlHandler）多路 select，统一走同一停机流程。

#### P1-8 [performance] hydra-client/src/tun.rs step() 第 4 步 L836–843（由 run_stack L648 await）：单流上行 write_all 直接 await 在栈主循环，形成跨流队头阻塞

主循环的 select!（L626）只在每轮迭代边界检查 shutdown.cancelled()；step() 第 4 步对 link_writer 的 `w.write_all(&buf[..n]).await` 是无限等待的写。当某条流对应的节点链路 TCP 拥塞窗口耗尽/链路假死时：① 其余所有 TUN 流的包处理、新连接接受、RST、超时管理全部停摆（跨流队头阻塞——一条 8K 视频流的接收端不读就足以卡死整个透明代理）；② Ctrl+C 的 shutdown 令牌也永远等不到检查点，与 P1-7 的 300ms 退出问题叠加放大路由残留概率。

**修复**：把上行写入移出主循环：为每条流派生独立写任务（flow_tx 通道交付栈侧读出的字节，写失败回发 RST 请求消息），主循环只做非阻塞 try_send；或至少用 `tokio::time::timeout(写超时, write_all)` 兜底并在超时后 abort 该流。

## P2/P3 附录

### P2

#### P2-1 [bug] hydra-protocol/src/tcp_frame.rs read_reply L130–132；关联 hydra-client/src/proxy.rs:370–377、hydra-node/src/tcp_server.rs:231–235：REPLY_DNS_FAIL 折叠进 TargetUnreachable 后不 failover，单节点故障被放大为全客户端黑洞

REPLY_DNS_FAIL 在 tcp_frame.rs:130–132 被映射为 TargetUnreachable，proxy.rs:370–377 对该错误立即 return：不 failover、不 mark_node_offline。error.rs:7–9 的折叠理由"目标在任意节点都不可达"对 connect 失败/SSRF 成立，但对 DNS 不成立——解析按节点出口位置进行（geo-DNS、局部 DNS 污染、节点本地 resolver 故障），节点 A 的 resolver 挂掉不代表节点 B/C 也失败。变体：某节点出口防火墙整体故障时对所有目标回 0x01，客户端每次请求都在第一优先节点短路失败，且"不计节点故障"设计使其对评分系统完全隐形，故障无自愈信号，用户可见失败无限持续。

**修复**：方案一：将 DNS 失败拆为独立错误（如 TargetDnsUnreachable），proxy 层对其继续尝试下一节点但不 mark_node_offline。方案二（保守）：保留现语义，但 proxy 对同一目标维护连续 TargetUnreachable 计数，达阈值（如 3）后允许一次跨节点重试，命中即重置——既保住 R-01 成果又消除单节点故障放大。

#### P2-2 [bug] hydra-node/src/tcp_server.rs pump() L283 `w.write_all(...).await?` 与 L286 shutdown；L248 `tokio::join!`：写错误路径跳过 shutdown，join! 使对侧空挂至 idle 超时放大连接额度占用

#### P3-8 [performance] hydra-client/src/tun.rs step() L824（每步 16KB 分配）；L798–816（pending front 整块 clone）：栈循环持续产生无效内存带宽

① L824 每次调用 step 都新分配 `vec![0u8; 16*1024]`——空闲时 select 的 10ms tick 使 step 以 100 次/秒运行，即空闲态也有 ~1.6MB/s 的分配/memset 纯开销（512 流场景每秒 5120 次分配）。② L803 `flow.pending.front().unwrap().clone()`：下行速度超过应用接收速度时，socket 发送缓冲长期打满，send_slice 返回 0 后 break，但下一次 tick 又把整个 16KB front 块完整 clone 一遍再失败——n 条停 streams 持续产生 n×16KB×100 次/秒 ≈ n×1.6MB/s 的纯 memcpy 垃圾，512 条停 streams 时达 ~800MB/s 内存带宽，挤占真正转发路径。

**修复**：① 把读缓冲提升到 run_stack 循环层创建一次，以 `&mut [u8]` 传入 step；② Flow 增加 `front_offset: usize` 游标，send_slice 用 `&front[front_offset..]`，n 字节后推进/清除游标，彻底消除整块 clone；步进内只在 `!flow.pending.is_empty() || 游标>0` 时尝试写入。
