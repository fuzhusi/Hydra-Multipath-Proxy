# 多路径技术质疑与本项目对策

- 日期：2026-10-05 ｜ 性质：对外技术质疑的正式回应（存档）
- 背景：外部评审指出"多路径代理"三类通病——①TCP 流拆分乱序、②会话 IP 一致性、③UDP 支持残缺。逐条对照本项目现状。

---

## 质疑 1：TCP 流按包拆分到多链路 → 乱序/重传反而降吞吐

**结论：不适用。本项目没有做、也主动移除了这种架构。**

- 本项目曾在 QUIC 时代实现过"单节点多流通道聚合（V3.4：ACK/NACK 重传 + 32MiB 有界乱序重排 + 256MB 强制门校验）"——正是评审所说的"应用层自己补偿乱序"路线。实测维护复杂度高、收益不稳定，TCP 转型时**整体移除**（决策记录见 docs/design/TCP转型与加密选型方案.md §6）。
- 现行"Multipath"语义 = **连接级多节点加权分发**：一条用户连接从头到尾锁定在一个节点上，节点内是单条 TCP 流，**不存在跨链路拆包**，因此乱序/重传问题在架构上就不成立。
- 未来"多节点并行下载（HTTP Range 切块）"也规避此问题：按**文件块**（应用层单元）并行，每块仍是完整独立 TCP 流，乱序发生在应用层拼装处，与传输层无关。

## 质疑 2：会话/Cookie/TLS 绑定 IP，调度到不同上游会失效

**结论：已解决（架构保证）。**

- 调度发生在**连接建立时**（`open_target` 按评分选节点），连接一经建立，整条会话的所有流量走同一节点同一出口 IP，直到连接关闭。
- 连接中途**不做**节点切换：节点故障在建立阶段暴露（握手失败/超时/应答码），切换发生在"换一条新连接"时——浏览器的会话（Cookie/TLS session）天然按域名复用连接，同一会话不会被拆到不同出口。
- 目标不可达（TargetUnreachable）也不会触发跨节点重试（避免污染评分的同时不产生"同一请求走不同出口"的语义混乱）。
- 已知边界（如实标注）：两个节点出口 IP 不同时，用户**不同**连接可能呈现不同出口 IP——对网站而言是"不同访客"，不是"同一访客 IP 漂移"；需要固定出口的用户把流量指向单一节点即可（调度器权重可配）。

## 质疑 3：UDP 转发残缺，不适合 DNS/游戏

**结论：属实，且是有意的设计边界（非残缺），缓解措施与路线图如下。**

- **根因**：立项网络环境（广东移动→境外 VPS）UDP 回程 QoS 丢包，UDP 路线被整体放弃——在本项目的目标环境里，UDP 转发是"不可用"而非"没做好"。
- **现状与缓解**：
  - TUN 模式：UDP 包快速失败（IPv4 丢弃 / IPv6 SYN 回 RST、ICMPv6 不可达），应用立即回落 TCP，不挂起；
  - DNS：TUN 模式下系统 DNS 路由豁免直出（与不装 TUN 一致），文档建议 DoH/DoT；
  - SOCKS 模式：SOCKS5 CONNECT 仅 TCP，无 UDP ASSOCIATE 暴露面。
- **路线图**（需求驱动，未排期）：若确有游戏/语音需求，正确做法是协议层扩展 UDP-over-TCP 中继（每流可靠封装 + 应用层会话超时），代价是吞吐与延迟损耗；或评估 QUIC 子环境恢复后的原生 UDP 转发。当前个人自用场景（网页/视频）无此需求，不做预投入。

---

## 一句话总结

评审的三类通病对应的是"包级多路径拆分"架构；本项目在 TCP 转型时已将该架构整体移除，现行"连接级分发 + 会话内固定出口"从架构上规避了 ①②，③则是明确声明的设计边界（含缓解措施与需求驱动的路线图）。
