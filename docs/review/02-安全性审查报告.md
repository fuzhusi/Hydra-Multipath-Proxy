# Hydra-Multipath-Proxy 安全性审查报告

- **审查日期**: 2026-10-03
- **审查范围**: 全部源码约 4700 行（hydra-protocol / hydra-node / hydra-client / hydra-client-gui）+ Cargo.toml / Cargo.lock / config/default.toml
- **审查性质**: 授权的个人项目防御性安全自查（作者本人项目，白盒代码审计）
- **方法**: 全量通读源码 + `cargo check --workspace`（通过，仅 3 个 dead_code 告警）+ 交叉验证 README 声称特性
- **结论速览**: 节点**当前完全无认证**，客户端**完全跳过 TLS 证书验证**。README Phase 5 声称的认证/限速/校验和体系**全部是死代码，未接入任何数据路径**。历史文档 OPTIMIZATION_PLAN.md 中指出的 "SkipVerification"、"无认证" 两个问题**至今原样存在**。

## 1. 威胁模型假设

| 要素 | 假设 |
|------|------|
| 资产 | 作者自己的 VPS 节点（带宽、云凭证、IP 信誉）、作者本机的浏览隐私、客户端配置/节点链接 |
| 攻击者 A（互联网扫描器） | 可扫描节点 UDP 端口，发起 QUIC 握手并充当"客户端"，目标是白嫖代理带宽、利用节点为跳板攻击第三方（IP 会记在作者 VPS 头上） |
| 攻击者 B（网络路径上的中间人） | 可观测/篡改客户端与节点之间的 UDP 流量（ISP、公共 Wi-Fi、国家级设备），目标是窃取浏览元数据、注入流量 |
| 攻击者 C（节点所在内网/云环境） | 借助节点发起 SSRF：访问 169.254.169.254（云元数据）、127.0.0.1 上的服务、VPC 内网 |
| 攻击者 D（恶意配置来源） | 诱导作者导入恶意分享链接 / 粘贴超大文本 |
| 不在范围内 | 攻击者已持有作者本机或节点 root 权限；QUIC/TLS1.3/ring 原语本身的密码学破解 |
| 客户端侧 | 本地 SOCKS/HTTP 代理默认只对 127.0.0.1 暴露即视为安全；一旦绑定 0.0.0.0 则按攻击者 A 对待 |

## 3. 问题清单

### P0-1 节点完全无认证：公网开放式转发代理（open relay）
- **位置**: `hydra-node/src/server.rs:14-48`（无认证配置）、`hydra-node/src/handler.rs:21-58`（直接 accept_bi 并解析目标地址）、`hydra-node/src/main.rs:9`（`NodeConfig::default()`，监听 `0.0.0.0:8080`）；对照死代码 `hydra-protocol/src/auth.rs`（全模块零引用）
- **描述**: 任何互联网主机只要知道节点 IP:端口，即可完成 QUIC 握手（ALPN `hydra` 在 ClientHello 中明文可见，扫描器可据此精确识别本协议），打开一条双向流，发送 `"host:port"`，节点即代为建立 TCP 连接并双向转发。无 PSK、无 token、无密码。
- **攻击场景**:
  1. 扫描器（如针对 QUIC/UDP 的 masscan 变体）发现 8080/udp → 免费白嫖作者 VPS 带宽；
  2. 攻击者把节点当匿名跳板发起对第三方的攻击/滥发流量 → 滥诉与封禁落到作者 IP 头上，云商可能直接封号；
  3. 攻击者经节点做 SSRF：`169.254.169.254:80`（窃取云厂商临时凭证）、`127.0.0.1:6379` 等本机服务、VPC 内网段（见 P1-3）；
  4. 节点日志 `handler.rs:58` 明文记录所有目标地址，间接泄露使用画像。
- **修复建议**: 短期：在 `HydraServer` 接入 `hydra_protocol::AuthToken`——节点配置 PSK（hex），握手完成后**第一条流的首个 64 字节**必须是通过 `AuthToken::verify(psk, token, client_id, 30)` 的 token，验证失败立即 `connection.close()`；PSK 不设默认值，缺失则拒绝启动。中期：将 token 认证移入 TLS 层（PSK 模式或客户端证书 `with_client_cert_verifier`），避免应用层自研。同步在分享链接中携带 PSK 字段。

### P0-2 客户端 TLS 证书验证被完全跳过（SkipVerification），且服务端证书一次性自签
- **位置**: `hydra-client/src/transport.rs:23-27`（`with_custom_certificate_verifier(Arc::new(SkipVerification))`）、`transport.rs:108-122`（verifier 直接 `Ok(assertion())`）；`hydra-node/src/server.rs:28-30`（每次启动 `rcgen::generate_simple_self_signed(["localhost"])`，证书**进程生命周期内随机**）；两处 Cargo.toml 均启用 `rustls` 的 `dangerous_configuration` feature
- **描述**: 客户端接受任何自签证书。由于 P0-1（无应用层认证），路径上的中间人可出示自己的证书终止 QUIC，再自行连向真节点或假节点：可窃取全部目标地址元数据（SNI/CONNECT 域名虽加密给"节点"，但 MITM 自己就是"节点"）、篡改/注入响应、降级为纯记录器。即使未来启用 HMAC token，token 也不绑定 TLS 通道（无 channel binding / exporter 值参与 HMAC），MITM 可原样转发 token 完成重放式认证穿透。
- **攻击场景**: 公共 Wi-Fi / ISP 侧设备对 UDP 8080 做透明 MITM：客户端无任何告警地连上假节点，全部浏览目标域名被记录。
- **修复建议**:
  1. 短期（TOFU + 持久化）：节点首次启动生成自签证书并**持久化到磁盘**（如 `~/.hydra/node.pem/.key`），输出证书 SHA-256 指纹；客户端配置中保存节点指纹，`SkipVerification` 替换为自定义 verifier：仅当 `end_entity` 指纹等于配置值时返回 `assertion()`，否则返回 `Error::InvalidCertificate(UnknownIssuer)` 类错误。此时可删除 `dangerous_configuration` 依赖之外仍需的 feature（rustls 0.21 自定义 verifier 仍需该 feature，建议直接升级 rustls 0.23 用 `ServerCertVerifier` 的 `pki` 能力）。
  2. 中期：客户端内嵌自签 CA 公钥（节点启动时若无私有 CA 证书则生成并持久化），签发节点叶子证书，客户端走标准 webpki 校验 + 指纹双保险。
  3. 将 token HMAC 输入混入 TLS exporter（`connection.export_keying_material`）实现通道绑定。

### P0-3 节点无任何资源上限：pre-auth 资源耗尽 DoS
- **位置**: `hydra-node/src/server.rs:53-59`（`accept()` 无限循环，每连接无条件 `tokio::spawn`，无信号量/计数）；`hydra-node/src/config.rs:7`（`max_connections` 死字段）；`server.rs:42-45`（TransportConfig 只设了 idle timeout 和 keep-alive，未设 `max_concurrent_bidi_streams` 之外的任何上限，也未启用 stateless retry）；`handler.rs:132-167`（每条流 2 × 64KB 缓冲 + 2 个任务，单连接默认可开 100 条流）；`handler.rs:99-101`（未认证即可触发节点对外 TCP connect，60 秒超时窗口内资源被占用）
- **描述**: 未认证状态下，攻击者可同时：打开数千条 QUIC 连接（无上限）× 每连接 100 条流 × 每流 128KB 缓冲 + 2 tokio 任务，并可让每条流指向慢速/不存在的目标挂起 60 秒。内存与 fd 双耗尽，节点彻底不可用（也殃及作者本人使用）。
- **攻击场景**: 单机脚本维持 2000 条 QUIC 连接各开 100 条流连向 `1.2.3.4:81`（超时目标）→ 节点约需维持 200k 任务、数十 GB 潜在内存，实际在远低于此值处 OOM 或 fd 耗尽。
- **修复建议**: ① 用 `tokio::sync::Semaphore`/`Arc<AtomicUsize>` 实现 `max_connections` 真实生效，超出即 `conn.refuse()`；② 每连接限制并发流数（`transport_config.max_concurrent_bidi_streams(n)`，建议 ≤ 16）并为 QUIC 设置 `stream_receive_window` 上限；③ 未认证连接：认证前只允许读一条流且总字节数 ≤ 128 字节（token 长度），超限即关；④ 缩短认证前 connect 超时（如 10s）；⑤ 启用 quinn 的 stateless retry 缓解地址伪造的握手洪泛。

### P1-1 （若未来启用认证）Nonce 防重放不存在：token 在 30s 窗口内可无限重放
- **位置**: `hydra-protocol/src/auth.rs:57-93`（`verify()` 读出 nonce 后仅参与 HMAC 重算，无任何存储/查重表）
- **描述**: README 明确声称 "Nonce 追踪防重放"，代码中没有。同一 token 在窗口内可被任意次使用——对"每连接认证一次"模型影响有限，但使"一次性凭据/每流认证"等设计目标不可能达成。
- **攻击场景**: 攻击者旁路嗅探到一次 token（在 P0-2 修复前 30s 窗口内明文可见于握手后首条流），在 30 秒内用自己的连接重放，冒充客户端。
- **修复建议**: 节点维护 `Mutex<HashSet<[u8;16]> + 时间分桶>`：`verify()` 成功后插入 nonce，若已存在则拒绝；后台任务按 `max_age_secs + 滞后` 清理过期分桶。并发安全 + 有界内存二选一方案都需写测试。

### P1-2 AuthRateLimiter：既未接线，又与声称不符（非令牌桶），且内存无界
- **位置**: `hydra-protocol/src/auth.rs:117-147`
- **描述**: ① 零调用（README 声称"基于 IP 的令牌桶限速"）；② 算法是固定窗口计数器（`retain` + 计数），窗口边界可双倍突发；③ `attempts` HashMap 条目 `retain` 后留下空 Vec，**key 永不删除**，随唯一源 IP 数量无界增长。
- **攻击场景**: 接线后若放在 accept 路径，攻击者用肉鸡/大量源 IP 触发 `check()` → 节点内存缓慢膨胀（数百万 IP × (IP+Vec 元数据) 可达 GB 级）。
- **修复建议**: 实现真正的令牌桶（每 IP：`tokens: f64, last_refill: Instant`），定期（如每 10 分钟）全量清理；或改用 `moka`/`lru` 有界缓存。限速点应覆盖：QUIC 连接建立、认证尝试、以及每连接新建流速率。

### P1-3 节点转发目标无任何过滤（SSF/元数据地址直达）
- **位置**: `hydra-node/src/handler.rs:61-101`（任意 `SocketAddr`/域名直接 `TcpStream::connect`）
- **描述**: 即使未来加了认证，客户端（或取得 PSK 的攻击者）仍可让节点连接任意地址：`169.254.169.254:80`（AWS/GCP/阿里云元数据，可窃取 `IAM` 临时凭证）、节点自身 `127.0.0.1:*`（redis/ssh/管理面板）、RFC1918 内网。对个人 VPS 而言，云凭证泄露是仅次于"被白嫖"的现实风险。
- **攻击场景**: 拿到 PSK 的前成员/泄露的分享链接 → 请求 `169.254.169.254:80` + `X-aws-ec2-metadata-token` 探测 → 拖走云凭证 → 整个云账号沦陷。
- **修复建议**: 默认黑名单：拒绝 loopback、`169.254.0.0/16`、`10/8`、`172.16/12`、`192.168/16`、`fe80::/10`、`::1`、节点自身地址（对个人翻墙工具，正常目标几乎全是公网；确需内网时用配置开关显式放行）。域名解析结果也要复查（防 DNS rebinding 绕过黑名单）。

### P1-4 `hex_decode` 对非法输入直接 panic（`unwrap`）
- **位置**: `hydra-protocol/src/auth.rs:197-202`
- **描述**: `(0..hex.len()).step_by(2)` 在奇数长度时最后一次 `&hex[i..i+2]` 切片越界 panic；`u8::from_str_radix(...).unwrap()` 遇非 hex 字符 panic。该函数是 PSK 从 hex 配置解码的自然入口——一旦 P0-1 修复接线到配置解析，**畸形的 PSK 字符串会使节点启动即 panic**；若在运行期调用则构成 DoS。
- **修复建议**: 返回 `Result<Vec<u8>, AuthError>`，调用方以清晰错误退出；或直接改用 `hex`/`base16ct` crate。同样注意 `auth.rs:34/39/75` 的 `unwrap()`（SystemTime/SystemRandom）应一并处理。

### P1-5 本地代理可被配置为无鉴权暴露 + 无并发上限 + 请求头无大小上限
- **位置**: `hydra-client/src/proxy.rs:69-95`（accept 循环无限 spawn，无本地连接数上限）、`proxy.rs:545`（SOCKS5 固定回 `0x05 0x00` 无鉴权，无用户名密码选项）、`proxy.rs:150-163`（HTTP 请求头读取循环**无累计大小上限**）、`hydra-client-gui/src/main.rs:753`（GUI 允许把监听地址改成任意值，如 `0.0.0.0:1080`）
- **描述**: 默认 `127.0.0.1:1080` 是安全的；但 GUI 一键即可改成 `0.0.0.0`，变成对整个局域网开放的匿名代理（同 P0-1 的滥用面）。同时：本地每连接 2×64KB 缓冲无总量上限；HTTP 头循环可被灌入任意大内存（绑 0.0.0.0 时为远程可触发的内存 DoS）。
- **修复建议**: ① 监听地址非 loopback 时给出显式红色警告并要求确认；② 为 SOCKS5 增加可选用户名/密码（RFC 1928，与 PSK 同源或独立口令）；③ 请求头累计上限 64KB，超限回 400；④ 本地代理加全局连接数上限（如 1024）。

### P1-6 认证 Token 结构性弱点（前瞻）：reserved 字节不参与 HMAC，client_id 未定义
- **位置**: `hydra-protocol/src/auth.rs:50-53`（token 布局含 8 字节 reserved）、`auth.rs:83-87`（HMAC 输入不含 reserved）
- **描述**: reserved 8 字节可被篡改而不破坏 HMAC（校验仍通过）——虽然当前 verifier 忽略它，但任何未来使用这 8 字节承载语义（版本、分片路由等）的改动都会引入可伪造字段。此外 `client_id: &str` 在客户端代码中**没有任何生成/传递方**，将来接线时容易顺手用空串，使 token 全局共享，抵消按客户端限速/审计能力。token 长度检查 `token.len() < 64` 允许超长 token（尾部垃圾被忽略），应改为 `!= 64`。
- **修复建议**: 布局收紧为 `[8B ts][16B nonce][32B HMAC]`（HMAC 覆盖前 24 字节），总长 56；接入时为每个客户端配置生成稳定 client_id（如 `blake3(psk_label)` 前 8 字节 hex）。

### P2-1 "数据包校验和" 为死代码，且 CRC32 防错不防篡改（语义误导）
- **位置**: `hydra-protocol/src/packet.rs:32-51`（手写 CRC32）、`hydra-client/src/assembler.rs:27`（唯一调用点，而 Assembler 本身死代码）
- **描述**: 真实数据路径是 QUIC 流上的裸字节（proxy.rs:249 / handler.rs:53-57），Packet/checksum 从不经过网络。QUIC 帧本身已受 TLS1.3 AEAD 保护，CRC32 不提供任何增补的完整性。README 把它列为安全特性属于误导；手写位循环实现还有性能成本。
- **修复建议**: 删除 packet.rs 的 checksum 字段或整个 Packet/Assembler/Splitter（若多路径聚合要重做，届时基于 QUIC 流重设计）；文档明确"完整性由 QUIC AEAD 提供"。

### P2-2 日志泄露浏览元数据与节点地址
- **位置**: `hydra-client/src/proxy.rs:165`（完整 HTTP 请求行，含 URL）、`proxy.rs:180,207,248,377,684`（目标域名/IP 明文 info 级）、`hydra-node/src/handler.rs:58,95,172`（目标地址 + 字节数）；`hydra-client/src/main.rs:19`（**硬编码作者 VPS IP** `43.130.251.236:8080`，已随 README/源码公开）
- **描述**: `tracing_subscriber::fmt::init()` 默认 info 级输出到 stdout，个人工具的日志常被重定向到文件或被屏幕共享/录屏带出——目标域名清单是高敏隐私。硬编码的默认节点 IP 等于公开邀请扫描器（结合 P0-1 危险度倍增）。
- **修复建议**: 目标地址日志降为 `debug!` 且默认关闭；或提供 `--log-redact` 开关只记录 `目标长度+端口`；移除源码中的真实 IP，默认节点列表留空；GUI 日志面板同理。

### P2-3 客户端 crypto.rs 为无效设计（一次性随机密钥、无协商、无使用）
- **位置**: `hydra-client/src/crypto.rs:16-42`
- **描述**: 每次 `Crypto::new()` 随机生成 CHACHA20_POLY1305 密钥，**从未与任何对端交换**，全仓库无调用。若未来有人误以为它"加了层加密"而接入，随机密钥的密文对端永远解不开；反之若两端各自随机生成，等于无效加密，属于危险的花瓶代码。
- **修复建议**: 直接删除。传输安全统一由 QUIC/rustls 承担。

### P2-4 NAT 穿透模块：默认配置必然失败 + STUN 响应可伪造
- **位置**: `hydra-client/src/nat_traversal.rs:7-11`（默认服务器为域名 `stun.l.google.com:19302`）、`nat_traversal.rs:113-114`（`server.parse::<SocketAddr>()` 对域名必然 `Err` → 所有默认 STUN 查询直接失败）、`nat_traversal.rs:154-193`（解析响应**不校验 transaction ID**）、`nat_traversal.rs:277-311`（UdpHolePuncher 用固定明文 `HYDRA_PUNCH`，无认证）
- **描述**: 功能坏死（域名需先 `lookup_host`）；若修好，路径上攻击者可抢答伪造的 Binding Response（无 transaction ID 校验），喂给客户端假公网地址，影响打洞对端选择。IPv6 XOR 解码也未与 Magic Cookie+Transaction ID 异或（非标准实现）。当前模块未被 main 链路调用，风险限于未来启用。
- **修复建议**: 用 `tokio::net::lookup_host` 先解析 STUN 域名；按 RFC 5389 校验 transaction ID 并优先取 XOR-MAPPED-ADDRESS；短期建议直接移除该模块（个人客户端→固定 VPS 场景用不到打洞）。

### P2-5 配置体系整体失效：`config/default.toml`、`HYDRA_CONFIG`、`max_connections`、`buffer_size`、`log_level` 全部无人读取
- **位置**: `hydra-node/src/main.rs:9`（`NodeConfig::default()`）、`hydra-client/src/main.rs:10-19`（硬编码）、全仓库无 `toml`/`HYDRA_CONFIG` 引用
- **描述**: README "配置说明" 一节不属实。安全影响：将来接入认证/限速时，若照 README 的假象以为配置已生效，会出现"改了配置以为关了某特性其实没关"的错位；PSK 也无法经由现有配置体系下发。
- **修复建议**: 用 `serde+toml` 真正加载（node 读 `[server]`+`[auth]`，client 读 `[client]`），文件权限提示（Windows ACL/Unix 0600），缺失字段 fail-closed。

### P2-6 GUI 细节：UI 线程阻塞、潜在 panic 点、代理泄漏窗口
- **位置**: `hydra-client-gui/src/main.rs:719`（"测试"按钮 `rx.recv_timeout(5s)` 阻塞 UI 线程）、`hydra-client/src/proxy.rs:104`（`"unknown".parse::<SocketAddr>().unwrap()`——若 `peer_addr()` 失败则 panic）、`main.rs:376-381`（`std::env::set_var` 多线程环境下属已废弃行为，edition 2021 暂安全）、`main.rs:537-542`（`on_exit` 清理系统代理，但进程被 SIGKILL 时系统代理残留指向死端口 → 全系统断网感）
- **描述**: 无命令注入（已验证 `Command::args` 传参，P0 无关）；主要是健壮性/可用性。SIGKILL 残留代理建议提供"看门狗"或文档说明手动清理命令。
- **修复建议**: `"unknown".parse().unwrap()` 改为 `SocketAddr::from(([0,0,0,0],0))` 兜底；"测试"按钮改异步；设置系统代理前写入一个标记文件，下次启动检测残留并提示清理。

### P2-7 依赖版本陈旧
- **位置**: 根 `Cargo.toml`、`Cargo.lock`：quinn 0.10.2 / rustls 0.21.12（已 EOL，官方停止维护）/ ring 0.16.20（经 rcgen 0.10 引入，2020 年版本，不再维护）与 ring 0.17.14 并存；`dangerous_configuration` feature 被三个 crate 启用
- **描述**: rustls 0.21 自 2024 年起不再接收安全修复；双 ring 版本拉长供应链。rustls 0.21 的 `dangerous_configuration` 也是实现 P0-2 的载体。
- **修复建议**: 升级 quinn 0.11 + rustls 0.23（API 变化集中在 ServerConfig/verifier），rcgen 0.13；升级后 ring 统一为 0.17。此改动与 P0-2 的 verifier 重写可一次性完成。

## 4. 加固路线图

### 短期（1-2 天，止血）
1. **P0-1** 节点接入 PSK + AuthToken 首包认证（先应用层，验证失败即关连接）；PSK 无默认值，未配置拒绝启动。
2. **P0-3** `max_connections` 生效（Semaphore）+ 每连接流上限 + 认证前字节配额 + 缩短认证前超时。
3. **P0-2（第一步）** 节点证书持久化 + 客户端指纹 pinning（自定义 verifier 校验 SHA-256），消灭任意证书可用性；同步删除默认硬编码节点 IP。
4. **P1-4** 修 `hex_decode` panic；**P1-5** HTTP 头 64KB 上限 + 非 loopback 监听警告。
5. 目标地址/HTTP 行日志降为 debug（P2-2）。

### 中期（1-2 周，结构化）
1. **P0-2（第二步）** rustls 0.23 + quinn 0.11 升级；自签 CA + 叶子证书 + 标准 webpki 校验；token 混入 TLS exporter 做通道绑定（封死 MITM 转发 token 的路径）。
2. **P1-1** nonce 重放表（有界、并发安全、带测试）；**P1-2** 真正的令牌桶 + 有界 LRU。
3. **P1-3** 目标地址黑名单（loopback/链路本地/内网/元数据），含解析后复查。
4. **P2-5** 真正的配置加载（toml，fail-closed），认证/限速/黑名单全部可配置；分享链接格式加入 `psk`/`fp`（指纹）字段。
5. SOCKS5 可选用户名密码；本地代理连接上限。

### 长期（重构方向）
1. 移除全部花瓶代码（Packet/checksum/Splitter/Assembler/crypto.rs/NatTraversal），或按新协议设计重做——**安全特性宁缺勿假**，文档如实描述。
2. 若确实要多路径聚合：在认证后的多流之上做分片/重组，用 AEAD 会话密钥（TLS exporter 派生）保护跨流完整性，替代 CRC32。
3. 引入模糊测试：`share_link.rs` 解析、SOCKS5 ATYP 解析、handler 首包解析是最佳 `cargo-fuzz` 目标。
4. CI 加 `cargo audit` / `cargo deny` 锁定供应链。
