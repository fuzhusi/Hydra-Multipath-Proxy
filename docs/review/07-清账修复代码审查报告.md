### Top 风险

1. **[P1] PEM 真证书路径丢弃中间链，公共 CA（ACME）部署下 TLS 握手必然失败** — `cert.rs` 只取 `certs[0]`，服务端仅发送叶证书；现有 E2E 用自签+pinned 模式，测试全绿但掩盖缺陷。本轮新增的真证书能力实际不可用。
2. **[P1] IPv6 接管路由（::/1 + 8000::/1，默认开启）把全系统 v6 流量导入仅启用 proto-ipv4 的 smoltcp 栈** — v6 包被静默丢弃、无 RST/ICMPv6/日志，形成全系统 IPv6 黑洞。两路独立审查（TLS 批次与 TUN 批次）一致确认，并经 smoltcp 0.11 源码核对（any-ip 仅 v4 入口生效，v6 入口直接丢弃非本机目的包）。
3. **[P1] TargetUnreachable「命中即重置」未实现** — 06-P2-1 修复承诺"达阈值 3 后允许一次跨节点重试，命中即重置"，实际命中后计数不重置，偶发目标失败被永久放大为每请求 3 节点全握手（最坏 3×35s），且计数表进程级全局，3 个并发请求即可让全进程进入放大态。

## P0/P1 详单

### P1-1 · PEM 真证书路径丢弃中间链，公共 CA 部署 TLS 握手必然失败 【已修复 2026-10-05】

- **位置**：`hydra-node/src/cert.rs`（`parse_pem_pair` :36-43、`load_or_generate` :80-83/:121-166）；`hydra-node/src/server.rs` :85-105；`hydra-node/src/tcp_server.rs` :69、:84
- **类别**：bug
- **机理**：`parse_pem_pair` 明确解析 fullchain（注释"含链"），但 `load_or_generate`（:36-43、:80-83）只返回 `certs[0]` 单张叶证书；`HydraServer::new`（server.rs:85-105）原样传递，`spawn_tcp_listener`（tcp_server.rs:69）随后 `with_single_cert(vec![cert], key)`（:84）只向对端发送叶证书。Let's Encrypt 等 ACME 部署下，客户端 CA 模式（`use_public_ca`）用 webpki 公共根校验时拿不到中间证书，无法构链到根，TLS 握手必败。本轮新增的真证书能力实际不可用。
- **为何测试未发现**：现有 E2E（`hydra-client/tests/test_e2e_gaps.rs:60`）用 rcgen 自签叶 + 客户端 pinned 叶 DER——信任根即叶本身，无需中间链，故测试全绿但掩盖缺陷。
- **修复建议**：`load_or_generate` 返回 `Vec<CertificateDer<'static>>`（整条链），`HydraServer::new` 原样传递，`spawn_tcp_listener` 参数改为链并 `with_single_cert(chain, key)`；`cert_fingerprint` 与日志仍取 `chain[0]`（叶），通道绑定语义不变。

### P1-2 · IPv6 接管路由把全系统 v6 流量导入仅 IPv4 的 smoltcp 栈，形成静默黑洞 【已修复 2026-10-05】

> **修复记录（2026-10-05）**：采纳方案 ①+②。① `TunConfig.ipv6_enabled` 默认改 **false**（`HYDRA_TUN_IPV6=1` 显式开启），默认关闭时启动告警"v6 不经代理直接出网，存在泄漏"；开启接管时也告警"栈仅支持 IPv4，v6 连接将被快速拒绝"。② 主循环 `push_inbound` 前检测 IPv6 包（无 proto-ipv6 特性，手工组包）：TCP SYN 构造 RST|ACK（地址/端口对调、ack=seq+1、RFC1071 校验和含 IPv6 伪首部），其余构造 ICMPv6 destination unreachable（type 1/code 0，引用原包前缀、总长 ≤1280B），不再投喂给栈——应用收到 ECONNRESET/不可达后快速回落 IPv4。`compute_routes_v6` 保留（开关打开即用）。README/CHANGELOG/帮助文本同步。新增 tun.rs `v6_blackhole` 单测组（v6 识别、SYN→RST 字段与校验和自洽、非 SYN 不代答、ICMPv6 引用原包）。

- **位置**：`hydra-client/src/tun.rs`（`compute_routes_v6` :274-298、`build_interface` :813-836、`ChanDevice::receive` :770-776、主循环投喂 :946 `push_inbound`、泄漏告警 :1345）；`hydra-client/Cargo.toml`（smoltcp features :44-49）
- **类别**：bug
- **机理**：本轮按全量清账执行计划 0-4 新增 `::/1` + `8000::/1` 接管路由（`TunConfig.ipv6_enabled` 默认 true，:76），防泄漏目标达成；但 smoltcp 依赖特性仅 `proto-ipv4`（Cargo.toml:44-49），`build_interface`（tun.rs:813-836）只配置 v4 地址与 `add_default_ipv4_route`。核对 smoltcp-0.11.0 源码：any-ip 仅在 v4 入口生效（src/iface/interface/ipv4.rs:107-122），v6 入口（src/iface/interface/ipv6.rs:52-58）对目的地址非本机的包直接丢弃，无 any-ip 路径；`ChanDevice::receive` 对入站包无版本分流，主循环投喂处（tun.rs:946）也无 IPv6 过滤——IPv6 包交给无 proto-ipv6 的 smoltcp 被静默丢弃，不回 RST、不回 ICMPv6 不可达、无日志。
- **影响**：双栈机器上所有 IPv6 连接超时黑洞（浏览器 Happy Eyeballs 可回落 v4，但直连 v6 的应用与 AAAA 优先路径全部挂起），v6 连通性永久丧失且无快速回落 v4 的失败信号；tun.rs:1345 只在显式关闭接管时告警泄漏，对开启后的黑洞零提示。路由层与栈层能力不匹配是本轮新代码引入的可用性回归。
- **修复建议**（择一，至少做 ①+②）：
  1. `ipv6_enabled` 默认改 false，并在双栈环境启动告警（写明 v6 进 TUN 即黑洞）；
  2. 保持接管，在主循环 `push_inbound` 前检测 IPv6 头，对 TCP SYN 自行构造 RST / 代答 ICMPv6 unreachable，使应用快速失败回落 v4；
  3. smoltcp 增加 `proto-ipv6` 特性并在栈内支持 v6 socket/代理路径。

### P1-3 · TargetUnreachable 达阈值后未重置计数——「命中即重置」未实现，偶发目标失败被永久放大为 3 倍跨节点握手 【已修复 2026-10-05】

> **修复记录（2026-10-05）**：新增 `record_and_should_failover`（proxy.rs）统一"记录 + 达阈值判定 + 立即 `clear_target_unreachable` 重置"，`open_target` 命中分支改调该函数——跨节点重试恢复真正的一次性语义。60s 时间窗未叠加（需将计数表改为 `(u32, Instant)` 并改动全部读写路径，收益有限），已在函数注释说明取舍。新增单测 `命中阈值即重置_后续请求不再跨节点重试`（唯一目标名防并行干扰：前 2 次不重试、第 3 次允许一次、重置后第 4 次请求与全新目标均不再重试）。

- **位置**：`hydra-client/src/proxy.rs` `open_target` :420-435（判定 :420-429）；常量注释 :52-55；计数表 :57-80
- **类别**：bug
- **机理**：06-P2-1 修复承诺「达阈值 3 后允许一次跨节点重试，命中即重置」（docs/review/06 报告 L112/L116 明文），但 `open_target` :420-435 命中阈值走 `continue` 分支时没有任何重置：`clear_target_unreachable` 只在连接成功（:393）时调用，`record_target_unreachable` 只增不减。计数一旦 ≥3，此后对该目标的每次请求都会连续尝试最多 3 个候选节点（每次完整 TCP+TLS+Noise 握手，最坏 3×35s），而非设计的一次性行为；真不可达目标或某节点 resolver 整体故障会以 3 倍握手负载持续压向全部节点且无退避。且计数表进程级全局（:58），3 个并发请求即可让全进程进入放大态。
- **修复建议**：在命中阈值分支（:422 `continue` 前）调用 `clear_target_unreachable(target)`（或计数归零），使跨节点重试真正一次性；可再叠加时间窗（如 60s 内失败才计入「连续」）抵御并发突发。

### P2 详单

#### P2-1 · SSRF：IPv4 兼容地址 ::/96（如 ::127.0.0.1）未按内嵌 IPv4 复查，可绕过黑名单 【已修复 2026-10-05】

> **修复记录（2026-10-05）**：抽出 `embedded_ipv4_of_v6(seg)` 小函数统一覆盖三段：::/96（排除 :: 与 ::1 特殊地址）、::ffff:0:0/96（RFC 2765 IPv4-translated，seg[4]==0xffff && seg[5]==0）、64:ff9b::/96——尾 4 字节重组 Ipv4Addr 后递归复查。新增单测：`::127.0.0.1`→loopback、`::10.0.0.1`→RFC1918、`::ffff:0:7f00:1`→loopback；公网内嵌（`::8.8.8.8`、`::ffff:0:808:808`）不拦，`::` 仍归 unspecified。

- **位置**：`hydra-node/src/handler.rs` `classify_blocked_ip` :78-105（::/96 与 ::ffff:0:0/96 段缺失）
- **类别**：security
- **机理**：`classify_blocked_ip` 对 IPv6 只覆盖两类内嵌 IPv4：`::ffff:a.b.c.d`（`v6.to_ipv4_mapped`，:80）与 64:ff9b::/96（:84-92）。IPv4 兼容段 ::/96（前 6 组全 0，如 `[::127.0.0.1]:80`、`[::10.0.0.1]:445`）以及 ::ffff:0:0/96（中间多一组 0，部分栈/NAT64 同样按内嵌 IPv4 处理）不命中任何分支：非 loopback/link-local/ULA/unspecified，直接放行。这类字面量可被 `SocketAddr::parse` 正常解析（handler.rs :154），Linux 内核对 ::x.x.x.x 形式按 v4 兼容语义处理，构成对已认证客户端的 SSRF 绕过向量（本组"新段"修复的同一威胁模型）。
- **修复建议**：在 `to_ipv4_mapped` 检查之后补两个前缀分支：① seg[0..6] 全 0（::/96）→ 取 seg[6]、seg[7] 重组 `Ipv4Addr` 复查；② seg[0]==0xffff && seg[1..3] 全 0（::ffff:0:0/96）→ 同样复查。可把"取尾 4 字节重组 v4 后递归 `classify_blocked_ip`"提成小函数供 mapped/NAT64/两段共用，并为 `::127.0.0.1`、`::ffff:0:7f00:1` 补单测。

#### P2-2 · 私钥文件写入中途失败不回滚半成品，下次启动被「证书/私钥不完整」检查卡死 【已修复 2026-10-05】

> **修复记录（2026-10-05）**：`write_key_file_secure` 将 write_all/flush/**sync_all**（补掉电截断面）包进闭包，任一失败即 `remove_file(key_file)` 回滚半成品并报错，与证书写入失败回滚语义对齐，维持"证书+私钥要么同时存在要么都不存在"不变量。

- **位置**：`hydra-node/src/cert.rs` `load_or_generate` :65 / `write_key_file_secure` :101-110
- **类别**：bug
- **机理**：`load_or_generate` :65 调 `write_key_file_secure` 后，仅当证书文件写入失败才回滚（:66-72）。但 `write_key_file_secure` 内部 `f.write_all(key_der)?` 与 `f.flush()?`（:108-109）失败时直接带 Err 返回，此时磁盘上已留下一个（可能只写了半截的）key 文件。下次启动进入 :19 的"存在即加载"分支，命中 :21 的"证书/私钥不完整，拒绝重新生成"检查，节点从此无法自愈，必须人工发现并手删半成品——对无人值守的远程节点是启动死锁。同理 flush 后未 `sync_all`，掉电可能留下截断密钥但文件存在，效果相同。
- **修复建议**：把 key 写入包一层失败回滚：`let res = (|| -> std::io::Result<()> { f.write_all(key_der)?; f.flush()?; f.sync_all()?; Ok(()) })(); if let Err(e) = res { let _ = fs::remove_file(key_file); return Err(...); }`，与证书写入失败的回滚语义对齐，维持"两者要么同时存在要么都不存在"的不变量。

> **修复记录（2026-10-05）**：`poll_start_receiver` 改为区分 Empty/Disconnected——Disconnected 分支清 `proxy_start_receiver`、置 `proxy_starting=false` 并记日志"代理启动线程异常退出"，恢复可再次启动。顺修 P3-10（同函数 Err 分支置位 stop_flag 后补 `stop_flag = None`，让收敛分支正常接管句柄清理）。

- **类别**：bug

### P3 详单

#### P3-1 · 节点侧未兑现「禁会话恢复两端保持」承诺：ServerConfig 默认仍颁发 session ticket 【已修复 2026-10-05（零成本快修）】

- **位置**：`hydra-node/src/tcp_server.rs` :78-90（`spawn_tcp_listener` 的 ServerConfig 构建）
- **类别**：maintainability
- **机理**：全量清账执行计划语义核查项 ② 明确 "Resumption::disabled() 两端保持"，但 `ServerConfig`（tcp_server.rs:78-90）只清了 ALPN，未设置 session_storage——rustls 0.23 默认启用内存会话缓存并颁发 NewSessionTicket。当前因客户端 `resumption = Resumption::disabled()`（tcp_transport.rs:210）不会实际恢复会话，安全影响趋近于零，但 a) 与设计承诺不符、清账项未闭环；b) 服务端持续下发 session ticket 是可观察的流量差异，与文档承诺相悖。
- **修复建议**：`config.session_storage = Arc::new(rustls::server::NoServerSessionStorage::default());`，或在文档中如实降级"两端保持"的承诺。

#### P3-2 · 信令会话读超时按字节计时，慢速滴入可无限期占用连接槽 【保留 2026-10-05：非零成本，暂不修】

- **位置**：`hydra-node/src/signal.rs` `serve_signal_stream` :211-224（逐字节 read + 每字节 90s 超时）
- **类别**：bug
- **机理**：读循环对每个字节单独包 90s 超时（:214），没有整行或会话级 deadline。已认证客户端可以按每 89s 发 1 字节的节奏无限拖延：MAX_LINE_LEN=4096 时最坏可把一条会话拖约 4.4 天，期间始终占用 TCP listener 的 Semaphore 连接槽位与 fd；只要不凑齐 '\n'，永远不触发任何超时/清理。与 tcp_server 认证阶段"整个 read_exact 包一个 AUTH_TIMEOUT"的做法不一致，属于本轮新增信令面自带的慢速资源占用路径。
- **修复建议**：在会话开始记录一个总期限（如 `Instant::now() + 2×SIGNAL_READ_TIMEOUT`），读循环顶部先检查是否超期；或对"当前行已累积的字节数"按整行限时（首字节起 90s 内未凑齐即断）。两者实现都只需在现有 loop 中加一个 Instant 比较。

#### P3-3 · TargetUnreachable 计数表无回收且阈值触发后语义漂移（节点侧视角） 【保留 2026-10-05：非零成本，暂不修】

- **位置**：`hydra-client/src/proxy.rs` `target_unreach_counts` :57-80；`open_target` 判定 :420-429
- **类别**：bug
- **机理**：`record_target_unreachable` 对每个失败目标在进程级 HashMap 建条目，只有连接成功才 clear（:393）。对"目标真的不可达"（用户访问死站、扫描器构造随机域名经 SOCKS/HTTP 代理进来）永远不会有成功，条目永不回收，key 无上界增长（每个条目含目标字符串），是慢性无界内存。另外 :422 的判定是 `consecutive >= THRESHOLD` 且命中后不重置：一旦某目标累计达 3 次，此后每次请求对每个返回 TargetUnreachable 的节点都 `continue` 全量走完 MAX_NODE_ATTEMPTS，与注释"允许一次跨节点重试"不符——对确死的目标每次请求都多付数个节点的完整 TLS+Noise 握手成本（每个最坏 20s）。（与 P1-3 为同一问题的完整机理描述，P1-3 聚焦重试放大，本条补充计数表无回收维度。）
- **修复建议**：① 条目改为 `(count, Instant)`，读取时对超过如 10 分钟未更新的条目清零/删除，或给 HashMap 加容量上限（如 4096，满则整体清空）；② 达阈值触发 failover 后立即把计数清零（或置为"已重试"标记），恢复"命中即重置、一次跨节点重试"的注释语义。

#### P3-4 · 空闲看门狗用 SystemTime 墙钟，时钟向前跳变会成批误杀在途连接 【保留 2026-10-05：非零成本，暂不修】

- **位置**：`hydra-node/src/tcp_server.rs` pump :324-333 / :362-368；`last_active` 初始化 :265-270
- **类别**：bug
- **机理**：pump 的空闲看门狗基于 SystemTime 毫秒时间戳（:265、:324、:362）。时间被 NTP/手工向前步进 ≥ idle（默认 300s，VM 首次同步、休眠恢复常见秒级到分钟级跳变）时，`now - last` 瞬间超过阈值，所有在途连接在下一轮 budget 到期后被判定空闲并双向关闭；反向跳变因 saturating_sub 已安全。功能上是可用性抖动而非安全问题，但修复成本低——同一文件内本就有"连接级单调时钟"的合适工具。
- **修复建议**：改用单调时钟：连接建立时取 `std::time::Instant::now()` 作原点，AtomicU64 存 `origin.elapsed().as_millis()`，判定改为 `elapsed_ms - last_ms >= idle_ms`。

#### P3-5 · hex_decode 接受带 + 前缀的非法 hex（"+f" 解码为 0x0f） 【已修复 2026-10-05（零成本快修）】

- **位置**：`hydra-protocol/src/auth.rs` `hex_decode` :23-31
- **类别**：bug
- **机理**：本轮字节级重写的实现只做 is_ascii 与偶数长度检查、未校验字符集；`u8::from_str_radix` 对无符号类型接受可选前导 '+'，因此 "+f"、"+0f" 会静默解码成功而非报错（"-f" 被拒，'+' 不会）。违背密钥入口 fail-fast、非法输入显式报错的修复目标。
- **修复建议**：循环前加 `if !bytes.iter().all(|b| b.is_ascii_hexdigit()) { return Err(...) }`，再做配对解码。

#### P3-6 · target_unreach_counts 全局 HashMap 无界增长（客户端侧） 【保留 2026-10-05：非零成本，暂不修】

- **位置**：`hydra-client/src/proxy.rs` `target_unreach_counts` :58-80
- **类别**：bug
- **机理**：条目仅在目标连接成功时移除，对永不成功的目标永久留存。本地 SOCKS/HTTP 监听可无认证（`--listen 0.0.0.0` 场景），任意客户端可用大量随机域名构造失败请求，每个目标字符串占一个 map 条目，长期运行内存无上界。属 06-P2-1 新修复引入的表面。
- **修复建议**：给 map 加容量上限（如 10_000，超限拒增或清最旧）或记录最后失败时间做惰性过期。

#### P3-7 · Windows CTRL_CLOSE_EVENT 约 5 秒宽限可能不够串行清理全部 v4+v6 路由，强杀后 /1 接管路由残留 【已修复（TUN v1 完整版清账）】

- **位置**：`hydra-client/src/tun.rs` `cleanup_routes` / `cleanup_routes_v6`
- **修复**：清理清单重排——`takeover_first` 把前缀 ≤1 的接管路由（0.0.0.0/1、128.0.0.0/1、::/1、8000::/1）稳定排到最前先行删除（危害最大者先行），豁免项保持原相对顺序排后；即使 5s 宽限中途被强杀，最致命的「整机流量进 TUN」路由必已摘除，残留的只是无害豁免项（下次启动幂等清理兜底）。
- **测试**：`cleanup_routes_接管路由先删`、`cleanup_routes_v6_接管路由先删`（乱序清单下断言 /1 两类必居首两条）。
- **残余风险（如实）**：无法在单元测试内模拟 CTRL_CLOSE_EVENT 的真实 5s 强杀时序，清理路径的总耗时仍随豁免条数线性增长；彻底解需异步清理或服务模式，超出本轮范围。

- **位置**：`hydra-client/src/main.rs` 信号任务 :412-440；`RouteGuard::drop`（tun.rs:500-507）
- **类别**：bug
- **机理**：CTRL_CLOSE_EVENT 宽限约 5s，超时进程无论是否 exit 都被强杀。`RouteGuard::drop` 串行 spawn 外部进程：每条 route delete 数十至百余 ms，每条 netsh v6 delete 常达数百 ms；豁免清单（节点 IP + 多条 DNS + HYDRA_TUN_EXCLUDE）较大时总清理时间可超 5s，超时即 /1 接管路由残留导致整机断网。
- **修复建议**：收到关闭信号后先同步删除两条 /1 接管路由（危害最大者先行），v6 清理仅删 ::/1+8000::/1 两条（豁免 /128 残留无害），缩短关键清理路径。

#### P3-8 · Established 仅在 tick 边界观察：握手完成与 FIN 同批到达时流挂 30s 后 RST、数据零转发 【已修复（TUN v1 完整版清账）】

- **位置**：`hydra-client/src/tun.rs` 1.5 节待建立流循环 + 第 4 步 CloseWait 处理
- **修复**：① 1.5 节对 **CloseWait** 流也立即派生 opener（同批到达时不再空等 30s）；② 移除第 4 步「CloseWait → 立即 close() 发 FIN」——该逻辑会拆线主动半关闭（发完请求 + FIN 等响应，FinWait2）的应用的流，写侧收敛统一交给「代理 reader EOF 且 pending 清空 → close()」，异常路径由 LinkErr→abort / 空闲超时兜底，无写侧泄漏。
- **测试**：`栈回环_半关闭同批到达仍建链转发`（客户端发请求后立即半关闭，断言 opener 被调用且响应可达；修复前必红）。

- **位置**：`hydra-client/src/tun.rs` 1.5 节待建立流循环 :1089-1113 与 30s 建立超时 :1097-1106
- **类别**：bug
- **机理**：step 每 tick 一次 `iface.poll` 处理整批入站包。若客户端将最后 ACK+数据+FIN 打包同批到达（小请求+delayed ACK 可出现），smoltcp 同一次 poll 内完成 Established→CloseWait 迁移；下个 tick 的 1.5 节（:1089-1113）看到 CloseWait——既非 Established（不派生 opener）也非 Closed/TimeWait，该已收到完整请求的流挂满 30s 后被中止回 RST，应用连接失败。
- **修复建议**：1.5 节对未 opened 但已过 SynReceived 且 `may_recv()`/缓冲有数据的流（如 CloseWait）也派生建链，而不是等 30s 超时后 abort。

#### P3-9 · 流量采样线程停启竞态：旧线程最后一次写入覆盖新会话缓存 【保留 2026-10-05：非零成本，暂不修】

- **位置**：`hydra-client-gui/src/main.rs` `start_proxy` :747-769
- **类别**：bug
- **机理**：`start_proxy` 先置位旧采样线程 stop，随后 spawn 新采样线程，之后才执行 `*slot = None` 清缓存。旧线程若正 block_on(get_stats)（旧 monitor），可能在清空之后完成最后一轮写入共享缓存槽，导致新会话开始后头 ≤500ms 显示旧会话的累计字节/速率。
- **修复建议**：缓存槽随会话更换：每次 `start_proxy` 新建 `Arc<Mutex<Option<TrafficStats>>>` 存到 self 并克隆给新线程；或线程在写入缓存前复查 stop 标志。

#### P3-10 · 启动失败路径置位 stop_flag 后不清空，代理线程句柄/退出通道永不收敛清理 【已修复 2026-10-05（随 P2-5 零成本顺修）】

- **位置**：`hydra-client-gui/src/main.rs` `poll_start_receiver` Err 分支 :865-870 与 update 收敛分支 :1664
- **类别**：bug
- **机理**：`poll_start_receiver` 的 Err 分支只 `store(true)` 不清 `self.stop_flag`；而 update 中收敛清理 `proxy_thread_handle`/`proxy_exit_receiver` 的分支（:1664）条件是 `!proxy_running && stop_flag.is_none()`，stop_flag 恒为 Some(true) 导致该分支永不执行：JoinHandle/Receiver 泄漏、「代理线程已退出」日志永不出现（线程本身已退出，仅句柄泄漏，量级小但属清理路径失效）。
- **修复建议**：Err 分支在 store 后置 `self.stop_flag = None`，让 :1664 的收敛分支正常接管清理。

#### P3-11 · CHANGELOG 事实不准确：GUI 实际为 5 页导航而非「六区」 【保留 2026-10-05：非零成本，暂不修】

- **类别**：maintainability

### 审查方法

- **TLS 栈升级批次**：审查对象为近期修复批次新写入/大改的 TLS/Noise/证书/传输/测速代码。逐项核实 rustls 0.23 API 迁移、exporter 两端一致性（label + `Some(b"")`）、ALPN 清空、客户端禁恢复、rustls-pemfile 2.x 三分支解析、rcgen 0.13 与 `PrivateKeyDer` 兼容、连接器缓存键（内容指纹含长度前缀，实际不可碰撞）、握手重放防线与 auth.rs hex/属主证明——均正确。
- **节点侧批次**：对 `hydra-node/src/{tcp_server,handler,signal,config,cert}.rs` 逐行精读，并核对 proxy.rs 重试逻辑与 hydra-protocol 侧 proof/应答码实现。重点清单中多数项核实为无实际缺陷：pump 共享 AtomicU64 的读改写竞态无害（两泵均存当前时刻，丢失更新不会造成误杀或漏杀）；信令 registry 的非常量时间 proof 比较不可被外部利用（能到达该比较的 proof 必已先通过 PSK HMAC 复算）；DNS 5s/connect 15s/客户端 20s 预算层次与 0x01/0x02 错误码映射闭环正确；信令属主证明的派生（域分离 HMAC）与常量时间比较（auth.rs `verify_p2p_owner_proof`）实现到位。
- **客户端核心批次**：逐文件精读 `hydra-client/src/{tcp_transport,proxy,nat,main,share_link,lib}.rs`，并与 docs/review/06、hydra-protocol/auth.rs 交叉核对。重点项中 punch 通道关闭守卫、nonce 单源自连检测、出站 bind 降级、TlsTrust Arc 化与连接器缓存、分享链接 32B 双层校验均核对无误。
- **TUN 批次**：精读 `hydra-client/src/tun.rs` 与 main.rs --tun 接线，并核对 smoltcp 0.11 源码（ipv4.rs/ipv6.rs ingress 路径）与设计文档。其余审查重点（RouteGuard 配对、上行写任务独立化与 UpErr/RST 链路、通道满背压、SocketHandle 移除顺序、prefix 钳制、回环测试真实性）均未发现新引入的缺陷。
