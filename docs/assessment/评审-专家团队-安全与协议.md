## 一、总评分与结论

**总评分：7.5 / 10（协议安全核心扎实，工程防探测细节到位；主要短板在"密钥模型全有或全无"、TUN 模式 IPv6 泄漏、信令滥用面与 rekey 缺失。）**

一句话结论：**TCP 转型后的协议核心（NNpsk2 握手 + 双通道 confirm 绑定 + 静默关流 + SSRF 过滤）是本项目安全质量最高的部分，密码学原语选择与实现细节（常数时间比较、PSK 长度 fail-fast、真重放单测）达到可交付水准；遗留风险集中在密钥管理生命周期而非密码学本身。**

## 二、亮点（均有代码/文档证据）

### H1. NNpsk2 模式选择正确，且对"为什么"有清醒记录

`hydra-protocol/src/handshake.rs:37-38` 明确记录选 NNpsk2 而非 IKpsk2 的理由（"IK 静态公钥明文可关联身份"）——这是同类工具常犯的错误（IK 模式的静态公钥构成被动识别指纹），此处规避得当。PSK 位于 msg2 的 psk2 位置，48B 消息长度（32B 临时公钥 + 16B Poly1305 tag）与 snow 0.9.6 实测一致并有注释（handshake.rs:40-44）。

### H2. confirm 双通道绑定设计正确且实现完整

`handshake.rs:153-168`：confirm = HKDF-SHA256(ikm=handshake_hash, salt=cert_fp‖exporter, info=方向域分离)。两条通道各司其职：

- **证书指纹**绑定节点身份，且**取 TLS 实际协商出的对端叶证书**（`hydra-client/src/tcp_transport.rs:127-139` `peer_leaf_cert`、:260 `cert_fingerprint(&peer_leaf)`）——从结构上消灭了"多节点证书按客户端配置配对错误"整类故障，证书轮换不破坏绑定（README.md:216，与代码一致）；
- **TLS exporter**（`tcp_server.rs:154-164` 服务端 / `tcp_transport.rs:235-246` 客户端，同 label/context）绑定 TLS 会话，跨连接转发握手字节即失效——这是对 QUIC 时代 P0-2 MITM 问题的根治。

方向域分离（`INFO_C2S`/`INFO_S2C`，handshake.rs:49-50）防反射攻击；比对使用 `ring::constant_time::verify_slices_are_equal`（handshake.rs:170-172）。

### H3. 抗重放不是口头声明，有真重放测试

`handshake.rs:344-414` `replayed_client_transcript_is_rejected`：录制第一轮客户端全部出站字节（0x03+msg1+confirm_c），原样重放到全新服务端实例，断言必被拒绝。原理成立（服务端临时 e 新鲜 → handshake hash 不同），测试是真的 transcript 级重放而非 mock。另有 PSK 错误、证书指纹不一致、exporter 不一致三个独立失败向量的双向测试（handshake.rs:289-339）。

### H4. PSK 入口 fail-fast，消除了"合法配置静默不可用"陷阱

`handshake.rs:127-151`：PSK 恰好 32 字节在 `build()` 入口校验；`share_link.rs:198-214` 在链接导入层同样校验；`share_link.rs:123-132` 生成层 assert 兜底。三层一致，错误信息可直接指导用户修复（"64 个 hex 字符"）。这源于历史审查 R-05（文档曾允许 ≥16B），修复闭环完整。

### H5. 防主动探测语义一致且贯彻

- 版本字节非 0x03 / TLS 握手失败 / Noise 失败 / 地址帧失败 → 一律**零字节静默关流**，仅 debug 级日志（`tcp_server.rs:144-152, 181-199`），握手错误统一折叠为 ProtocolError 不回显差异（`handshake.rs:113-116`）；
- SSRF 拒绝与"目标连不上"折叠为同一应答码 0x01（`handler.rs:303-311`、`tcp_frame.rs:37-39`），不给探测者区分原因的指纹；
- 连接额度满时 `try_acquire_owned` 快速丢弃而非 backlog 排队（`tcp_server.rs:105-108`）；
- TLS 握手 10s 超时 + 认证段 10s 超时 + 连接级 idle 看门狗（默认 300s，双向共享时间戳防长下载误杀，`tcp_server.rs:33-51, 246-331`）——认证前 slowloris 与认证后资源占用两条耗尽路径都有防护。

### H6. SSRF 过滤覆盖面高于平均水平

`handler.rs:43-87`：loopback（v4/v6 全段）、链路本地、RFC1918、ULA fc00::/7、0.0.0.0/8、::，且对 **IPv4-mapped（::ffff:a.b.c.d）与 NAT64（64:ff9b::/96）内嵌 IPv4 做二次复查**——这两个是多数同类实现遗漏的绕过向量。过滤点在 DNS 解析之后对解析结果统一执行（`handler.rs:295-312`），同时覆盖字面 IP 与域名两条路径。单测覆盖边界（172.16/12 上下界、内嵌公网放行）。

### H7. 日志脱敏架构正确

`hydra-protocol/src/log.rs:13-25`：目标地址 info 级一律 SHA-256 前 8 hex 字符，明文仅 `RUST_LOG=debug` 可见（`handler.rs:239-241`）；客户端侧同样（`tcp_transport.rs:288-293`）。节点侧 DNS 失败、SSRF 拒绝等错误路径均走脱敏日志。

### H8. DNS 隐私承诺兑现

客户端源码中**无任何 `lookup_host` 调用**（grep 证实），域名只经加密地址帧交节点解析——docs/review/03 中 F12"回退裸 UDP 53 泄漏"已随 TCP 转型彻底移除，无残留。

### H9. 密钥文件化与落盘权限

`hydra-node/src/config.rs:271-298` 密钥文件（0600 告警）、`cert.rs:121-159` 自签私钥 0600/证书 0644 强制 + 既有私钥权限过宽告警、`hydra-client-gui/src/config.rs:248-263, 408-413` GUI 配置文件 0600 且有权限断言测试。

### H10. 分享链接的"链接=交出节点"模型有明确安全声明

`share_link.rs:63-66`："完整链接（含 k/cc）= 持有该节点，等同账号密码……严禁粘贴到不可信渠道；仅含 cf 指纹的紧凑链接不泄露密钥"。文档（README.md:40, 266）与代码声明一致，GUI 有导入提示。知边界并明示，好于沉默。

### H11. docs/review/03（防追踪性审查）的 QUIC 时代高危项已基本闭合

## 三、问题清单（按优先级）

### P1-1【高】TUN 模式 IPv6 流量完全旁路，用户真实 IP 明文直连泄漏

- **证据**：`hydra-client/src/tun.rs:43-70` 整个 TunConfig/路由体系仅 `Ipv4Addr`（`exclude_routes: Vec<Ipv4Addr>`、`addr: Ipv4Addr`）；路由接管仅 `0.0.0.0/1 + 128.0.0.0/1`（tun.rs 模块注释与 README.md:130-131）。IPv6 默认路由不受影响——**双栈网络下所有 IPv6 目标（含大量大站的 v6 优先/Happy Eyeballs）直接从物理网卡明文直连，出口真实 IP，且与经节点的 v4 流量并存形成强关联特征**。
- **影响**：对匿名性/防追踪目标是致命的：用户以为"全局代理"，实际一半流量实名直出。README v1 边界声明（README.md:135-138）列了"仅 TCP、无 DNS 劫持、端口列表"，**唯独未提 IPv6 旁路**。
- **建议**：①短期（文档级，半天）：README/TUN 文档红色警告"TUN v1 不接管 IPv6，双栈环境存在真实 IP 泄漏，建议系统禁用 IPv6 后使用"；②中期（代码级）：增加 `::/1` 接管或至少"检测到全局 IPv6 且未禁用时启动告警/可选自动阻断 v6 默认路由"；③TUN 端口列表外 RST（tun.rs:18-20）同样意味着大量应用静默失败，建议回 ICMP unreachable 或文档强化。

### P1-2【高】密钥模型"全有或全无"：全局单 PSK，无吊销、无 per-user 派生，分享链接无有效期

- **证据**：全协议单一 `HYDRA_AUTH_KEY`（`hydra-node/src/config.rs`、`handler.rs:202` auth_key: Vec\<u8\> 全节点唯一）；分享链接完整模式直接携带该 PSK 原字节（`share_link.rs:56, 123-132`）；无过期字段、无密钥 ID/版本、无节点侧多 PSK 支持。
- **影响**：分享体系越方便（扫码即用），凭据扩散越快；任一接收者泄漏链接（进群聊/截图/GitHub）= 只能全量换 key，所有已分发链接同时失效，实际运维中会导致用户倾向"不换"——凭据泄漏的期望存续时间被拉长。这也是"信令滥用面"（见 P2-2）的根子：任何持链接者都是完全同级成员。
- **建议**：①P1 步：节点支持多 PSK（`[[users]] id/key` 表 + Noise 握手后上报 key-id 以便审计区分来源）；②P2 步：分享链接支持从主 key HKDF 派生子密钥（`k` 为子密钥，节点持有主密钥可验证可吊销）；③给链接加 `exp` 时间戳字段（客户端导入时校验，节点侧可选强制）。

### P1-3【高】数据面无 rekey，长连接密钥材料不轮换（文档承诺 V3.3 未兑现）

- **证据**：`handshake.rs:22` "rekey 推迟：V3.3 处理（如实标注，本期未实现）"且注释自认"snow 传输态即弃，数据面照旧走模式标签"（:24, :177）——即数据面机密性**完全依赖单条 TLS 1.3 会话**。rustls 0.21 不会自动发起 TLS KeyUpdate，节点 `HYDRA_IDLE_TIMEOUT_SECS` 上限可到 86400s（`tcp_server.rs:49`），单连接可承载数十 GB 流量而不换密钥。
- **影响**：单条记录层密钥长期使用增大"密钥碰撞/密码分析进展/内存取证"下的暴露面；也是实现层对"前向安全"宣传（README.md:18）的折损——FS 只覆盖握手与连接粒度，不覆盖"已断开连接的密钥仍长期有效期内被取证"以外的细粒度。风险真实但非紧急（TLS 1.3 记录层本身有序号防重放、有 AEAD）。
- **建议**：①低成本版：客户端/节点在连接传输量达到阈值（如 1GB）或时长阈值（如 1h）时主动关闭并重连（上层已有故障切换，用户无感）；②完整版：实现 TLS KeyUpdate 触发（rustls 0.21 支持发送端 `send_key_update` 需要核对可用性，不行则走 ①）；③文档把"前向安全"的表述收敛为"握手前向安全 + 连接级密钥"。

### P1-4【中高】信令（P2P NAT 穿透）滥用面：peer_id 无属主证明，可劫持、可枚举在线状态、cand 不校验

- **证据**：`hydra-node/src/signal.rs:87-107` `register` 为纯 upsert——**任何通过 Noise 握手的客户端可覆盖任意 peer_id 的注册**（"重复注册同一 peer_id = 心跳/地址更新"），原属主的下行端被静默顶替；`handle_line` 的 invite/accept 对不在线目标回 `peer_offline` 错误（:269-272）——**可探测任意 peer_id 是否在线**；invite 的 `cand: Vec<String>` 不经任何合法性校验即转发给对端（:264-285，仅 4096B 行限），客户端 `nat.rs:680` 会对候选地址发起直连——恶意同级成员可令对端向任意 ip:port 发起 TCP 连接（打洞探针/内网探测中转）。
- **影响**：NAT 穿透是实验性功能且需 `HYDRA_P2P_SIGNAL=1` 显式开启（默认关闭），故实际暴露面有限；但一旦开启：①peer_id 劫持 = 会话中间人入口（invite/accept 与候选地址均可被顶替者改写）；②在线状态侧信道；③cand 注入让客户端变成按需发包器。同 PSK 模型下攻击者=已获凭据者，威胁等级中，但该功能的设计目标恰是"把节点信任分发给对等端"，与威胁重合度高。
- **建议**：①首注册锁定 + 后续 register/invite 需对 peer_id 派生挑战应答（如 `HKDF(PSK, peer_id)` 的 HMAC 证明，改动小）；②注册/invite 限速（每 peer 每分钟 N 次）；③cand 校验：仅公网 IP、条数上限（现在无条数限制，仅行长限制）、格式严格校验；④对 peer_offline 错误加均匀随机延迟或在节点侧对同一查询者限频，弱化枚举。

### P2-1【中】CA 模式信任模型：硬 pin 是可选而非默认

- **证据**：`tcp_transport.rs:97-125` `TlsTrust::public_ca(leaf_pin_sha256_hex: Option<String>)`——`HYDRA_TRUST=ca` 时信任全部 webpki 根（:162-171），`HYDRA_CERT_SHA256` 叶 pin 可选（README.md:92-94"可选加固"）。
- **缓解事实（评审必须如实指出）**：CA 误签发/恶意 CA 场景下，MITM **仍无法完成 Noise-PSK 握手**（confirm 双通道绑定 + PSK 未知），因此不能解密或篡改代理内容；实际风险收敛为：假节点可让客户端反复建连-失败（DoS/探测行为分析），以及客户端在 ca+无 pin 模式下对"我连的是谁"失去密码学确认。这比典型的"CA 模式=可被 MITM"结论要好，是 PSK 第二道防线的真实价值。
- **建议**：①分享链接在 tp=tcp + ca 模式下默认携带 `cf`（叶指纹）并在导入时自动填充 `HYDRA_CERT_SHA256`（`with_cert_fp` 已有该字段，`share_link.rs:141-145`，只差 ca 模式消费逻辑——当前 cf 只用于 pin 模式核对）；②GUI 尚不支持 ca 模式（README.md:269），补齐时把"ca 无 pin"做成带黄标的次选默认。

### P2-2【中】日志脱敏的两处残余风险

- **证据**：①`mask_target`（`log.rs:13-25`）为**无盐** SHA-256 截断 8 hex——对可枚举域名（Alexa Top 100 万离线字典）可批量反查，短哈希"不可逆"只在熵足够时成立；②明文仅 debug 级可见（`handler.rs:241,262,276`）是对的，但节点部署指南未把"生产严禁 RUST_LOG=debug"列为检查项。
- **建议**：①改为 HMAC-SHA256(key=节点启动时随机生成仅存于内存的 salt)，牺牲跨重启可关联性换取不可离线反查（诊断场景可接受）；②部署指南排障表加一行"生产环境 RUST_LOG 上限 info"。

### P2-3【中】PSK/密钥内存不擦除

- **证据**：全仓库无 zeroize（grep 证实）；`handler.rs:202 auth_key: Vec<u8>`、客户端握手密钥同样驻留普通堆内存；GUI 配置文件持久化明文密钥（0600 已做，`hydra-client-gui/src/config.rs:248-263`）。
- **影响**：内存取证/swap/崩溃转储场景下 PSK 可恢复；与"密钥文件化"的威胁模型（README.md:36 防 env 泄漏）不对称——防了入口没防驻留。
- **建议**：接入 `zeroize` crate（PSK 的 Vec 与派生缓冲 Drop 即擦）；GUI 密钥可考虑 OS keychain（Windows Credential Manager / libsecret），配置文件只存引用。优先级中：攻击者需已拿到本机内存/磁盘访问，此时游戏基本已输，但属廉价加固。

### P2-4【中】SSRF 黑名单缺口：CGNAT、基准测试段、组播/广播

- **证据**：`handler.rs:43-87` 覆盖了 loopback/link-local/RFC1918/ULA/0/8/::/mapped/NAT64，但未覆盖：`100.64.0.0/10`（CGNAT，部分云内网走此段）、`198.18.0.0/15`（RFC2544 基准，部分云 metadata 变体部署）、`224.0.0.0/4` 与 `255.255.255.255`（组播/广播目标，connect 通常失败但属防御纵深）、IPv6 组播 `ff00::/8`。
- **建议**：`classify_blocked_ip` 补上述网段（各一条 match 分支 + 测试用例），半小时工作量，纯加固。

### P2-5【中】抗探测剩余缺口：443 上"TLS 后零响应"与自签指纹（README 已如实声明，给出可执行收敛路径）

- **证据**：未认证 TLS 连接发送任意字节 → 零字节关流（`tcp_server.rs:144-152`）；自签证书固有指纹（README.md:258-259 承认）；"非认证 IP 反代静态页待实施"（README.md:268）。
- **分析**：真证书路线（ca 模式）下主动探测者看到的 TLS 层与普通站点不可区分，剩余指纹是"TLS 完成后发非 0x03 数据 → 连接无任何应用层响应即关闭"——真实 HTTPS 服务在 TLS 后总有 HTTP 响应或 alert，"沉默关闭"本身是一个二阶特征。自签路线则 TLS 层即暴露（自签+非浏览器 SNI）。
- **建议**：①优先级中：对 TLS 完成但版本字节非 0x03 的连接，回一个最小合法 HTTP/1.1 404（几十行，无需 h3），对齐 Trojan/Hysteria2 的 masquerade 思路；②部署文档把"长期部署推荐 ACME 真证书"的推荐等级提高（当前是"可选"）。

### P3-1【低】`HYDRA_ALLOW_PRIVATE_TARGETS` 按 per-stream 读 env

- **证据**：`handler.rs:31-36` 自注释承认"每次调用读取 env（per-stream 一次）"。行为一致性 OK（测试需要），但 env 可被同机其他进程通过 `/proc` 注入的场景（Linux 同 uid）会实时改变安全边界。建议启动时读入 ConnectionHandler 持有，测试改用构造参数注入。
- **处置**：【已修复 2026-10-05 Wave 3】改为 `OnceLock<bool>` 首次调用时固化——运行期 env 注入不再能实时改变安全边界；进程内测试仍可在首次调用前设置 env 注入，无需构造参数改造。

### P3-2【低】STUN/NAT 实验路径明文暴露

- **证据**：`hydra-client/src/nat.rs` 明文 STUN（UDP 3478 类）到公共服务器；docs/review/03 §1.5 已指出"在用穿透工具"可识别。实验性 + 默认关闭，风险自洽，但文档应在 NAT穿透方案.md 顶部显式加"该路径无抗检测设计，对抗审查环境勿用"的边界声明。
- **处置**：【已修复 2026-10-05 Wave 3（文档类）】nat.rs 模块头新增**安全边界声明**（明文交互、无抗检测设计、对抗环境勿启用——不设 `HYDRA_STUN_ADDRS` 即整体关闭）。

### P3-3【低】分享链接 legacy 字段残留增加攻击/混淆面

- **证据**：`share_link.rs:52, 60, 88-90` 仍保留 `mode=obfs`/`ok=`（obfs 第二密码）字段且随 QUIC 删除已成死语义（`transport_choice()` 对 `tp=obfs` 显式报错，`tcp_transport.rs:49-58`）；保留兼容解析可以理解，但 `ok` 字段是**纯死数据**，链接中携带只会误导。建议导入时对携带 `ok`/`mode=obfs` 的链接警告"字段已废弃"并在生成侧永远不写。
- **处置**：【已修复 2026-10-05 Wave 3】导入解析 `ok=` 字段时 `tracing::warn`"legacy obfs 字段已废弃、无运行时效果"；生成侧永不写（既有行为）；`mode=obfs` 解析保留且非法值显式报错（分享链接兼容解析路径）。

## 四、改进路线建议

### 第一梯队（1~2 周内，均为小改动、高安全收益）

1. **TUN IPv6 泄漏**：文档红色警告 + 启动时双栈检测告警（P1-1）。这是当前最可能造成真实用户伤害的一项。
2. **SSRF 黑名单补段**（P2-4）+ `ALLOW_PRIVATE_TARGETS` 启动时固化（P3-1）。
3. **日志反查加固**：mask_target 换 HMAC + 部署指南加 RUST_LOG 检查项（P2-2）。
4. **zeroize 接入**（P2-3）。
5. **未认证连接 HTTP 404 masquerade**（P2-5①）。

### 第二梯队（1~2 月，结构性改进）

6. **多 PSK / 子密钥派生 + 链接有效期**（P1-2）——分享体系从"交出主权"演进为"授权可回收"，这是把分享 v2 从便利功能升级为安全功能的关键一步。
7. **信令 peer_id 属主证明 + cand 校验 + 限速**（P1-4），随 NAT 穿透脱离"实验"标签前必须完成。
8. **数据面 rekey**：先做"阈值重连"（P1-3①），KeyUpdate 作为调研项。
9. **ca 模式默认携带/校验叶指纹**：分享链接 cf 字段接入 ca 模式消费逻辑 + GUI 支持真证书部署时黄标无 pin 状态（P2-1）。
10. **形成对 TUN/信令/订阅三块新面的系统化威胁模型文档**：docs/review/03 覆盖的是传输与 DPI 面；建议新写 docs/review/07-凭据与多租户威胁模型（谁能吊销谁、泄漏半径、peer_id 信任模型），把本报告 P1-2/P1-4 的假设显式化。

### 第三梯队（长期）

11. ClientHello 指纹模仿（ja-tools 路线，README 已列）——Rust 生态无 uTLS 是硬约束，建议先做"指纹收敛度量化"（用 ja3/ja4 工具自测并与浏览器比对）再决定投入。
12. REALITY 式证书借用/真站前置——与 masquerade 404 形成梯度：先 404（便宜），再静态反代（中），再 SNI 分流真站（贵）。

## 五、给报告阅读者的三句话总结

1. **密码学实现层面没有发现可利用缺陷**：NNpsk2 用法、HKDF 域分离、常数时间比较、真重放测试、TLS exporter 绑定均正确，PSK 第二道防线让 CA 误签发的实际风险远小于表面。
2. **最大的真实风险不在协议而在运营面**：全局单 PSK 无法吊销（P1-2）与 TUN 模式 IPv6 直连泄漏（P1-1）——前者决定泄漏半径，后者直接破防匿名目标。
3. **docs/review/03 的历史结论已大面积失效（以修复方式）**，当前防探测的主要剩余缺口收敛为 ClientHello 指纹与"TLS 后沉默"二阶特征，项目文档对此的如实标注值得肯定。
