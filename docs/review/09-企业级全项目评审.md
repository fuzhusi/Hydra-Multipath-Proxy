## 一、执行摘要

### 1.1 总体质量结论

本项目整体质量**处于企业级产品的高水准区间**。核心判断依据如下：

1. **协议编解码与密码学集成层扎实**。长度字段上界、严格解码、溢出防护、STUN 事务 ID/XOR-MAPPED-ADDRESS 语义、Noise-PSK 消息序与 confirm 常时比较、通道绑定 exporter 两端一致性，经逐字段核查均正确，未发现整数溢出或长度信任类漏洞。
2. **安全面高度加固**。SSRF 判定单源化且覆盖完整、无 DNS rebinding TOCTOU、认证分流均在 Noise-PSK 握手之后、常时比较到位、响应头零注入、日志脱敏、配置 fail-fast——未发现可利用的认证旁路或 SSRF 绕过。
3. **并发与资源纪律良好**。热路径零锁化、缓冲固定复用、队列/缓存/会话表均有界、锁不跨 await、无死锁路径。
4. **剩余缺陷均为局部性、可定位、可修复问题**，且不涉及字节级组包错误或死锁。

**总体评级：良好（B+），核心数据面与安全面达到可发布水准，存在 2 个 P1 级 Android 端缺陷建议在下一版本发布前修复。**

### 1.3 建议修复顺序

1. **第一批（P1，版本发布前必须）**：SEC-01、SEC-02。两者均为 Android 端局部改动，触发条件简单、影响直观（断网 / 真实 IP 泄漏），修复成本可控。
2. **第二批（P2，紧随其后）**：TUN-01（用户可感知的静默丢包）、SEC-03（供应链一次性加固，改动极小）、PERF-01/PERF-02（最热路径性能，改动局部）。
3. **第三批（P2 剩余 + P3）**：PROTO-01 与 TUN-02（会话状态机完备性）、LOGIC-01/LOGIC-02（行为一致性与状态管理），其余 P3 按迭代节奏消化，建议 P3 中「带日志缺失、现场不可诊断」类（TUN-02 的日志子项、PROTO-04）优先，因其直接影响线上排障能力。

## 三、P1 详单（2 项）

### SEC-01 [P1/安全] VPN 一次会话后，本地代理模式所有出站连接被进程级 protect 钩子永久中止

- **位置**：`android/app/src/main/kotlin/dev/hydra/vpn/HydraVpnService.kt:448`（onDestroy 置空 VpnProtectHolder.handler）× `hydra-core/src/socket_protect.rs:23-28`（OnceLock 进程级首装固化）
- **机理**：Rust 侧保护钩子是进程级 OnceLock、仅首次安装生效且永不撤销；VPN 服务销毁时把 Kotlin 侧 handler 置 null（fail-closed）。之后同进程内启动 EngineService（M1 本地代理，`start(null)` 不安装自己的钩子），所有到节点的出站连接仍会命中已固化的钩子 → handler 为 null → protect 返回 false → hydra-core 按「防回环」契约立即中止每一条出站连接。
- **影响**：一次 VPN 会话之后，本地端口模式完全断网：UI 显示「✓ 引擎已就绪」，但随后自动连通性自检报「节点连通失败」，浏览器全部无法出网；用户重启 App 才能恢复。触发条件简单（先用一次 VPN 再切本地模式），属高频路径。
- **修复方案**：① onDestroy 不再置空 handler，改持 applicationContext 引用的静态保护实现（保存最近实例的 protect 能力，服务停止但 protect 可继续成功——无 TUN 时 protect 成功无害）；或 ② 将 PROTECT_HOOK 改为可重装（RwLock/AtomicSwap），HydraVpnService.onDestroy 与 EngineService.start 时分别安装/撤销各自钩子。
- **来源**：GUI 与 Android 绑定专项

### SEC-02 [P1/安全] 数据面运行中死亡时未建立黑洞 TUN：kill switch 形同虚设，退避窗口真实 IP 直连泄漏

- **位置**：`android/app/src/main/kotlin/dev/hydra/vpn/HydraVpnService.kt:90-115`（StackExitCb.onStackExit）
- **机理**：`run_stack` 异常返回后回调进入重连分支：先 `stopVpn()`（关闭 Rust runtime → FdTransport drop → TUN fd 关闭 → 系统路由回落物理网卡），再 `delay(backoff)`（2–10s）后重建。黑洞 TUN（holdTun）只在「建连失败」的重试循环里建立，数据面中途死亡路径完全未建立；此窗口内应用流量直连。
- **影响**：kill switch 开启（默认开）的用户在节点/网络抖动导致数据面崩溃时，真实 IP 与 DNS 以明文直连暴露 2–10 秒，且 UI/通知仍显示「已接管全部流量」，用户毫无感知——与该功能声明的「防真实 IP 泄漏」承诺直接矛盾。
- **修复方案**：在 StackExitCb 内、调用 stopVpn() 之前，若 cfg.vpnKillSwitch 且未被 userStopRequested/代际失效：先 establish(cfg)（失败回退 APP_FILTER_ALL，复用既有回退逻辑）写入 holdTun 再清 Rust 句柄，使退避窗口维持阻断；重建成功路径已有 releaseHoldTun() 毫秒级切换，无需额外改动。
- **来源**：GUI 与 Android 绑定专项

## 四、P2 详单（8 项）

### PROTO-01 [P2/逻辑] UDP 会话死亡通知与空闲回收的 close 下发均无世代绑定，可误杀刚重建的同 sid 会话

- **位置**：`hydra-node/src/udp_relay.rs:436-448`（dead 分支）与 :396-416（reaper），对照 :641-666（重建路径）
- **机理**：会话死亡通知只携带 session_id（`dead_tx: mpsc::UnboundedSender<u16>`），不携带世代/身份；主循环收到 dead 事件时无条件按 sid 执行 `table.remove(sid)` 并下行 close。select 随机分支使「Data 帧先重建同 sid 会话、dead 事件后到」成为可能：重建路径（target 不同或旧句柄 try_send Closed）先移除旧表项并 spawn 新 session_task，随后 stale dead 事件仍会把新表项删掉。reaper 同理：reap_expired 已按过期快照摘除表项后、在取 writer 锁写 close 前存在窗口，主循环可用同 sid 建新会话，close 帧仍照发。
- **影响**：低频但真实的会话状态机漏洞：会话任务异常退出（socket 收发错误/下行写失败）后的 dead 事件是滞后的；若客户端在此期间换目标或重发数据（uplink_data:620-666 走摘旧建新路径），随后到达的 stale dead 事件会把刚重建的健康会话从表里摘除并下行 close（udp_relay.rs:439-444），客户端收到 close 解除映射，该目标的在途回包全部丢失。量化：每次会话任务异常死亡 + 竞态窗口内重建 = 1 个活跃会话被误杀，客户端侧表现为该目标短暂黑洞直至下一个上行包重建。
- **修复方案**：给会话引入世代号：SessionHandle 增加 `generation: u64`，每次重建 +1；session_task 携带 (sid, generation)，dead_tx 改发 (sid, generation)；主循环与 reaper 下发 close 前先重查表，仅当表内存在且世代/句柄匹配（如比较 tx 同渠道，参考 signal.rs:137-146 remove_if_downlink 的 same_channel 判定）才摘除并下行 close。
- **来源**：协议与状态机专项

### PERF-01 [P2/性能] 节点 UDP 中继每数据报 2–3 次 String 堆分配，仅为目标串相等比较

- **位置**：`hydra-node/src/udp_relay.rs:582-586, 678-682, 119-126`
- **机理**：上行读循环对每一个 Data 帧执行：① `t.get(session_id).map(|h| h.target().to_string())` 分配一个 String 仅为与帧内 target 做相等比较；② 投递路径 `clone_handle()` 再次 `self.target.clone()` 分配一个 String。目标串在会话生命周期内根本不变，比较结果几乎恒等，两次分配纯属浪费。
- **影响**：QUIC/DNS 高包率场景（TUN 全流量接管下单连接数千至上万 pps）每秒产生数 MB 级无效分配器流量与 free-list 压力，单核转发吞吐下降、尾延迟上升；同时每帧 3–4 次对 table Mutex 的加锁/解锁（existing_target、判满、回填、clone_handle）可合并。
- **修复方案**：SessionHandle.target 改为 `Arc<str>`；UdpSessionTable 增加 `has_target(sid, target: &str) -> bool` 在锁内直接比较，替代 to_string 后的字符串比较；clone_handle 只克隆 Arc。同时可将一帧内对 table 的多次 lock 合并。
- **来源**：性能与资源专项

### PERF-02 [P2/性能] 每个入站 v6 TCP 包全量遍历 SocketSet 构建 protected HashSet，地址已挂载时工作全部白做

- **位置**：`hydra-client/src/tun.rs:1982-2002`（run_stack v6 TCP 分发分支）
- **机理**：对每个入站 IPv6 TCP 包（含已建立流的纯 ACK/数据包），先遍历整个 SocketSet（可达 max_flows=512 个 socket，每个含 listener/握手/数据流）过滤 local_endpoint 构建 `HashSet<Ipv6Addr>`，随后才调 ensure_v6_dst——而 ensure_v6_dst 第一行就检查 has_ip_addr 直接返回。即 99% 的包白白付出 O(n) 遍历 + 一次堆分配。
- **影响**：v6 流量高 pps 时主循环每秒执行数百万次 socket 遍历与数百次堆分配，拉长单次 step() 耗时，拖慢所有流的下行泵与 poll 节奏（主循环是单点）。
- **修复方案**：在构建 protected 之前先 `if iface.has_ip_addr(IpAddress::Ipv6(dst.into()))` 命中即直接 push_inbound 返回（绝大多数包命中此快路径）；或维护与流生命周期同步的增量式 protected 集合，仅在 ensure_v6_dst 真正需要淘汰时才做全量 SocketSet 扫描。
- **来源**：性能与资源专项

### TUN-01 [P2/健壮性] UDP 中继回包不做 MTU/长度钳制，超限帧注入 TUN 被静默丢弃且无 ICMP 差错引导

- **位置**：`hydra-client/src/tun.rs` build_udp_reply_v4/build_udp_reply_v6（tun.rs:1663-1728），注入点 udp_relay_task（tun.rs:1571-1575）
- **机理**：两个回包构造函数直接以节点中继下行的 datagram 长度组帧，既不检查 20+udp_len(v4)/40+udp_len(v6) 是否超过 TUN MTU（默认 1500），v6 侧 `udp_len = 8 + payload.len()` 后 `as u16` 也无上限检查（>65527 时回绕）。超 MTU 帧交给 transport.send 后被 TUN 驱动丢弃/报错，客户端应用收不到任何差错（也不会回 ICMPv4 frag-needed），只能靠应用层超时。
- **影响**：触发：节点中继返回大于 1472B（MTU 1500 − 20 IPv4 − 8 UDP）的 datagram（大 UDP DNS 响应、QUIC 大块、节点侧 recv 缓冲 ≥2048B 的任意回包）。后果：a) v4/v6 帧长 > MTU 时 Wintun/tun 驱动拒收或静默丢帧，且不会生成 ICMP fragmentation-needed（type 3/code 4），QUIC/DTLS 的路径 MTU 探测与 UDP 大包业务表现为无限重传；b) v6 载荷 > 65527B 时 udp_len 回绕为小值，构造出 payload_len 与实际帧长不符的畸形包，宿主栈按长度截断/丢弃。量化：每个超 MTU 回包 = 应用一次完全无反馈的丢包。
- **修复方案**：在 udp_relay_task 注入前按 cfg.mtu 钳制：datagram 长度 > mtu−28(v4)/mtu−48(v6) 时丢弃该回包，并对 v4 回 ICMPv4 type 3 / code 4（fragmentation needed，MTU 字段填 TUN MTU 1500）让 QUIC/DTLS 的 PMTUD 立即收敛；v6 侧对 udp_len > 65535 直接丢弃并 debug 日志。也可在通道侧将节点单包读上限钳到 1472/1452。
- **来源**：TUN 与网络正确性专项

### TUN-02 [P2/逻辑] IPv6 动态 AnyIP 池仅 5 槽 = 并发 v6 目的地址硬上限；池满时新 v6 SYN 静默丢弃且无日志

- **位置**：`hydra-client/src/tun.rs` V6_DYNAMIC_SLOTS / ensure_v6_dst（tun.rs:1362-1413），调用点 run_stack（tun.rs:1995-2003）
- **机理**：地址表 8 槽（iface-max-addr-count-8）减 3 个静态地址后动态池仅 5 槽。protected 集合按 SocketSet 的 local_endpoint 计算（覆盖握手期，机制正确），但只要 5 个槽上的 v6 目的都存在未关闭 socket（包括 CloseWait/TimeWait 期），ensure_v6_dst 即走「池满且全部活跃 → return」分支，SYN 静默丢弃、且该目的地址不挂载；地址仅在流关闭后靠 LRU 被动淘汰，新目的只能等 TCP 重传撞上空槽。
- **影响**：触发：>5 个并发活跃 v6 目的地（现代浏览器/下载器对多站点并发 v6 连接很常见）。后果：第 6 个及以后目的地的首个 SYN 静默丢弃，该连接建连延迟增加 1–3 秒（等重传或等某活跃流关闭），最坏（5 条长连接持续 + 无重传窗口运气差）反复秒级延迟；且丢弃发生时没有任何日志（「放弃挂载」的 debug 在池满全活跃分支有，但逐包重试无聚合告警），现场表现为「v6 偶发连不上」无法诊断。
- **修复方案**：① 池满静默丢弃分支补 debug 日志（当前该路径无日志，现场不可诊断）；② 启用 smoltcp 更大的 iface-max-addr-count-* feature（如 16/32）把动态槽扩到 13/29；③ 或按目的地址做 LRU：流关闭（to_remove 清理处）时主动将该目的地址出池并从接口摘除，而不是等 LRU 轮转，保证稳态下池中只挂活跃流地址。
- **来源**：TUN 与网络正确性专项

### SEC-03 [P2/安全] wintun.dll 供应链：Authenticode 签名校验只打印不拦截，未 pin 哈希

- **位置**：`.github/workflows/release.yml:58-65`（下载 wintun.dll 步骤）
- **机理**：CI 从 `https://www.wintun.net/builds/wintun-0.14.1.zip` 下载后仅执行 `Get-AuthenticodeSignature dist/wintun.dll | Select-Object Status, SignerCertificate`——这只是把签名状态打印到日志，PowerShell 步骤恒以 0 退出；签名状态为 NotSigned/HashMismatch/Revoked 时构建照常继续。且 zip 本身无 SHA-256 pin（仅有版本号注释）。该 DLL 随后被同时打进管理员权限运行的 GUI 安装包（hydra.nsi:40 `File "..\dist\wintun.dll"`）与便携 zip，TUN 模式下由管理员进程加载。
- **影响**：wintun.net 被入侵/域名劫持/CDN 供应链污染，或上游 zip 被替换为未签名/恶意重编译版时，恶意 DLL 将被静默打进 release 产物，最终由管理员权限客户端加载执行——等于用户机器上的任意代码执行，且构建日志中的签名状态极易被忽略。
- **修复方案**：下载步骤改为硬校验并失败即退出：`$sig = Get-AuthenticodeSignature dist/wintun.dll; if ($sig.Status -ne 'Valid' -or $sig.SignerCertificate.Subject -notmatch 'WireGuard') { exit 1 }`；同时对 0.14.1 amd64 wintun.dll（或整个 zip）写入固定 SHA-256 期望值并用 Get-FileHash 比对，双保险。
- **来源**：安全专项

### LOGIC-01 [P2/逻辑] 运行中切换 runMode 不停另一模式服务，停止按钮打错目标，UI 状态被互相覆写

- **位置**：`android/app/src/main/kotlin/dev/hydra/vpn/MainActivity.kt:985-1000`（运行模式 FilterChip 即时切 mode）与 :342-352（onStop 按 cfg.runMode 选目标服务）
- **机理**：两个服务共用同一 EngineState 单例；VPN 运行中把 runMode 切到 local 后，首页「停止」按 cfg.runMode 发 ACTION_STOP 给 EngineService（未运行，no-op），HydraVpnService 从未收到停止指令，TUN 依旧全局接管；再点「启动」会叠加拉起 EngineService，两端同时写 EngineState 互相覆写状态。
- **影响**：用户以为已切到本地模式并停止，实际全局 VPN 仍在捕获全部流量（含 DNS）；继续点「启动」会出现双数据面并存。VPN 侧只能通过通知栏停止按钮或杀进程退出。
- **修复方案**：模式切换回调里先发 ACTION_STOP 给另一模式的服务（或检测 EngineState.ui.running/transition 非空闲时拒绝切换并提示先停止）；停止逻辑按「当前实际运行的服务」而非当前 cfg.runMode 路由（可让两个服务把自身模式写入 EngineState）。
- **来源**：GUI 与 Android 绑定专项

### LOGIC-02 [P2/健壮性] EngineService.onDestroy 在主线程同步调用阻塞 FFI（stop 内 runtime.shutdown_timeout 最长 3s），ANR 风险

- **位置**：`android/app/src/main/kotlin/dev/hydra/vpn/EngineService.kt:261`（onDestroy 中 engine.stop(); engine.close()）
- **机理**：HydraEngine.stop() → Rust 侧 `runtime.shutdown_timeout(3s)`：持 state 锁同步等待 accept 任务与在途连接收敛，正常停机也常占数百毫秒；有长连接在传时打满 3s。同仓库 HydraVpnService.onRevoke/onDestroy 已明确注释「stop_vpn FFI 持锁 shutdown 最长 3s——移出主线程」并照做，唯独 EngineService.onDestroy 遗漏。
- **影响**：系统回收服务/用户从最近任务划掉 App 时主线程卡住最长 3s+；叠加 close 的 JNI 释放可逼近 ANR 阈值（5s），表现为划掉应用瞬间界面冻结或「应用无响应」。
- **修复方案**：与同类 HydraVpnService.onDestroy(:444) 对齐：把 stop/close 移入独立守护线程执行，onDestroy 只做 scope.cancel 与状态复位；close 的释放保证可交由 stop 的幂等 stop_vpn 收敛。
- **来源**：GUI 与 Android 绑定专项
