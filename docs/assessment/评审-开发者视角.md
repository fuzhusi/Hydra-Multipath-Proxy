## 二、亮点（均有实证）

### 1. 架构分层清晰，依赖方向正确
- workspace 四 crate：`hydra-protocol`（协议/握手/帧/STUN/脱敏）→ `hydra-node`（服务端）与 `hydra-client`（客户端库+CLI）→ `hydra-client-gui`（前端）。README "项目结构"节（L220-236）与实际目录一一对应，无越层引用：`hydra-node` 与 `hydra-client` 互不依赖、都只依赖 protocol（各 crate Cargo.toml 可证）。
- GUI 不直接碰协议：GUI 通过 `hydra-client` 的 `ProxyServer`/`TrafficMonitor` 抽象消费能力，`hydra-client` 提供 feature `tun` 开关（`hydra-client/Cargo.toml:15`），`--no-default-features` 可编出最小客户端——这是正确的可裁剪设计。
- QUIC→TCP 转型的删除是动真格的：Cargo.lock 已无 quinn（05 号报告 R-10 指出的死依赖已清），`hydra-obfs` crate 整体移除，README L238 如实注明。

### 2. 审查→修复闭环真实存在，且可验证
这是本项目最突出的工程文化亮点。05 号报告列 36 项，附录 B 逐条记录当轮修复项；06 号报告附录记录 P0×2 + P1×8 全部修复并伴随 9 条新增测试（169 通过）。本评审抽查核实：
- **R-01（P0 目标失败误判节点离线）已修**：`tcp_frame.rs:126-132` 现将 0x01/0x02 映射为带语义的 `HydraError::TargetUnreachable`，`proxy.rs:370-384` 据此不再 `mark_node_offline`。
- **R-08/R-09（明文日志泄漏）已修**：`hydra-client/src/tcp_transport.rs:291` 成功路径已用 `mask_target`，grep 全 client/src 无 `info!("✓ ... target ...")` 明文残留。
- **R-11（TCP_NODELAY）已修**：`tcp_transport.rs:233`、`nat.rs:117/292`、`hydra-node/src/handler.rs:325` 均已设置。
- **N-01/N-02（节点握手超时 + idle 看门狗）已修**：`hydra-node/src/tcp_server.rs:40-48` 有 idle 参数与共享活跃时间戳实现（对应 06 号 P1-2 的共享时间戳方案），README L29 同步声明。
- 修复不是"改了就算"，多数伴随回归测试（06 号附录明确列 169 通过）。

### 3. 测试是真实有效的集成测试，不是凑数
README L246-252 与 `hydra-client/tests/test_tcp_transport.rs` 对照核实：10MB E2E 回显走 SOCKS5 全链路、错 PSK 静默关流、半关闭语义、SSRF 拒绝、恢复探测、STUN 编解码、loopback 打洞端到端。当前源码中 `#[test]`/`#[tokio::test]` 属性共 167 处，与 README/审查报告宣称的量级一致。这些测试覆盖的是协议行为而非函数名，是真正能挡回归的测试。

### 4. 文档诚实度罕见地高
README "已知限制"节（L262-269）逐条如实标注：单流无聚合、分流无 GeoIP、TUN 不支持 UDP/DNS 劫持、TLS 指纹与浏览器有差异、GUI 仅支持 pin 模式。06 号报告"未覆盖声明"（L250-256）明确承认 loopback 测试结构性无法暴露真实 NAT 失效模式。这种"以 README 所述为准，未列即为未实现"的自我约束（README L7）在个人项目中极为少见，直接降低了使用者的误判成本。

### 5. 部署侧工程质量好
05 号报告附录 A 对 deploy 的结论（systemd `ProtectSystem=strict`、`CAP_NET_BIND_SERVICE`、Docker 非 root + `cap_drop ALL`）与本轮核实一致；BBR+fq 一键配置（`deploy/99-hydra-bbr.conf`）是少见的运维完成度。敏感文件卫生也到位：仓库根虽存在运行产生的 `hydra-node-cert.der`/`hydra-node-key.der`，但 `.gitignore` 已覆盖且 `git ls-files` 确认未入库。

## 三、问题清单（带优先级，均经当前代码核实）

### P0（阻塞长期维护，须立即处理）

**F-01 完全没有 CI，170 项测试没有任何强制执行点**
- 证据：仓库根无 `.github/` 目录（已核实），无任何 CI 配置；README 唯一的质量门禁是手工 `cargo test --workspace`。
- 影响：审查报告的修复"全绿合入"完全依赖人肉纪律；07 号改动随时可能无测试就合入。对一个以安全为卖点的项目，无 CI 意味着所有"测试通过"声明都不可复核。
- 建议：一个 50 行的 GitHub Actions（`cargo fmt --check` + `cargo clippy --workspace -- -D warnings` + `cargo test --workspace` + `cargo build -p hydra-client --no-default-features` 验证 feature 裁剪）即可解决，半天工作量，是全仓投入产出比最高的一项。

### P1（高优先）

**F-02 rustls 0.21 / tokio-rustls 0.24 已 EOL，且 ring 0.16 + 0.17 双栈并存**
- 证据：`hydra-protocol/Cargo.toml:14`、`hydra-client/Cargo.toml:19-21`、`hydra-node/Cargo.toml:12-14` 均为 rustls 0.21 / tokio-rustls 0.24（Cargo.toml:17 注释自己承认"已 EOL"）；`Cargo.lock:3885-3901` 显示 ring 0.16.20 与 0.17.14 同时在锁（两份汇编静态编入每个二进制）；lock 中 rustls 0.23.45 也存在（GUI 侧依赖带入），即两代 rustls 并存。
- 影响：安全修复不再回移，这是安全产品的实质风险，不是风格问题；双 ring 徒增体积与审计面。
- 建议：按 05 号 R-31 路线执行——先 `[workspace.dependencies]` 统一版本，再一次性升 rustls 0.23 + tokio-rustls 0.26 + ring 0.17 单栈（snow 的 ring-resolver 随之去重）。这是一个 1-2 人日的机械升级，拖得越久 diff 越大。

**F-03 `hydra-client-gui/src/main.rs` 已达 3031 行 / 140KB，是事实上的巨石**
- 证据：实测 3031 行（workspace 内最大文件，第二名为 `tun.rs` 56KB）；06 号报告引用行号已到 L2920 仍在同一文件。
- 影响：任何 GUI 改动都在巨石上做合并；审查成本高（05 号 R-06/R-34/R-35/R-36/R-37/R-38 六项全在此文件，不是偶然）。
- 建议：按既有导航六区拆模块：`ui/{overview,nodes,subscriptions,share,settings,logs}.rs` + `system_proxy.rs` + `state.rs`，GUI 逻辑（egui 绘制）与动作（系统代理注册表、托盘）分离。每拆一块提交一次，不需要一次重构到位。

**F-04 审查 06 号报告遗留 19 项未修复，其中 P1-8 是架构性缺陷**
- 证据：06 号报告附录明确"未修复（待排期）：P1-8 与全部 P2×10、P3×8"；本评审核实 P1-8（TUN 单流 `write_all` 阻塞栈主循环造成跨流队头阻塞，`tun.rs` step 第 4 步）代码原样。P2 中 `P2-5`（CA 模式无 pin 无告警，`main.rs trust_from_env`）、`P2-3`（节点 DNS 解析无超时，`handler.rs` lookup_host）、`P2-6`（NAT 信令来源不校验 from）均确认未修。
- 影响：P1-8 意味着一条卡住的下载流可冻结整个 TUN 透明代理——TUN 标着"实验"可接受，但 P2-5/P2-6 是安全告警与校验缺失，成本只有几行。
- 建议：先清 P2-5、P2-6、P2-3（合计 <1 人日），P1-8 按 06 号给的写任务拆分方案排入下个迭代。

**F-05 05 号报告的 P2 遗留项同样未清账**
- 证据（抽查核实）：
  - R-29 配置非原子写：`hydra-client-gui/src/config.rs` 中 grep 无 `tmp`/`rename` 原子写实现，仍是直写——崩溃可丢全部配置（含明文密钥）。
  - R-24 运行期 `set_var` UB 风险：`main.rs:801-805` 五个 `set_var` 仍在 UI 线程执行。
  - R-06 GUI 每帧 `block_in_place + block_on`：`main.rs:2084-2085` 原样存在。
  - R-31 无 `[workspace.dependencies]`：根 `Cargo.toml` 实测仅 7 行 members+resolver，四个 crate 各自声明 tokio/rustls 版本，且 tokio 全部 `features=["full"]`（各 Cargo.toml 实证）。
- 建议：R-29（原子写 + 0600 tmp）与 R-31（workspace.dependencies + tokio feature 收敛）是半天级改动，优先做；R-06 随 F-03 拆分一并处理。

### P2（中优先）

**F-06 QUIC 死代码清理不彻底**
- 证据：`hydra-protocol/src/packet.rs`、`session.rs`、`hydra-client/src/splitter.rs`、`transport.rs` 仍存在（实测文件清单）；05 号 R-30/R-32 指出这些零生产引用且 `packet.rs` 内含逐位软件 CRC32 等性能地雷。
- 建议：一次性删除并清 lib.rs re-export 与对应测试，属于 Wave 3 的收尾欠账。

**F-07 测试数字在文档间漂移，且覆盖缺口自认未补**
- 证据：README L3 称"125 项"，L246 称"153 通过"，06 号报告称"169 通过"，源码实测 167 个 test 属性——三处口径互不一致。05 号 R-42 列出的缺口（HTTP 代理路径约 240 行零测试、SOCKS5 畸形/粘包/拆段零测试、故障切换 E2E 缺失）在 `hydra-client/tests/` 现状中仍未补。
- 影响：对"170 项测试"的外部宣称，数字对不上会直接损伤文档公信力；R-42 缺口恰在"回归风险最高处"（A6 刚修过 HTTP lossy 转码 bug 的那条路径无测试）。
- 建议：① README 测试数字改为"以 CI 最新一轮为准"或固定口径；② 按 R-42 优先补 HTTP 代理 + SOCKS5 畸形输入两组（本地 echo 目标服务器即可，无需外网）。

**F-08 本地构建体验缺少最基本的统一入口**
- 证据：无 `justfile`/`Makefile`/`xtask`；`cargo build --release` 会连 GUI（egui 全量编译）一起编，想快速验证协议改动没有轻量入口；`--no-default-features` 降级路径只写在 Cargo.toml 注释里。
- 建议：README "开发"节补三行常用命令（`cargo test -p hydra-protocol -p hydra-node`、无 TUN 最小构建、clippy），可选加 justfile。

### P3（低优先 / 记录在案）

**F-09 错误处理基础设施一致性**（05 号 R-43 未修）：`traffic.rs` 三处 `lock().expect("poisoned")` 与热路径的容忍式写法并存；`probe_connect` 返回 `Result<_, String>` 与全仓 `HydraError` 风格割裂（`speedtest.rs`）。
**F-10 README 与代码的漂移点仍有存量**：06 号 P2-7 证实 `HYDRA_TRANSPORT=quic` 告警回退（README L172）未接线或已失效路径的描述仍在文档中；此类"文档先行于实现"的条目建议每次发版做一次 env 表逐项核对。
**F-11 仓库根遗留运行产物**：`reg.log`（751KB）、`tcp.log`、根目录 `.der` 密钥文件虽未入库但散在工作区，建议统一收进 `.runtime/`（已 ignore）或删。

## 五、结语

从开发者视角看，Hydra 的**协议实现、安全自觉性与文档诚实度**达到了远超个人项目平均线的水平；两轮 64 项审查加当轮修复闭环的做法本身就是良好的工程文化。它当前的短板高度集中且可枚举：**没有 CI、依赖栈停在 EOL、GUI 巨石、审查遗留 19+ 项排期未动**。这些短板没有一项是"难"的——全部是时间投入问题。按第一梯队清单干满两天，这个项目的工程基建就能追上它的功能完成度；届时总评分可到 8.5+。
