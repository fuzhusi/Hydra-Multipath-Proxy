# 02 · Hydra 握手密码学设计草案（协议 v3 认证层）

- 日期: 2026-10-03 ｜ 状态: 草案（密码学评审稿） ｜ 前置: [docs/review/02-安全性审查报告.md](../../review/02-安全性审查报告.md)
- 命名: 任务书所称"握手 v2"即认证机制第二代；线协议版本字节取 **0x03（v3）**——0x02 已被现行 PSK+HMAC token 占用。Domain separation 统一 `hydra v3 *` 前缀。
- 总原则: **绝不自造密码学原语**。原语全部来自标准实现（ring/RustCrypto）；"自研"只存在于消息流设计、密钥调度顺序、握手状态机——即 Noise 框架划定的合法空间（先例：WireGuard = Noise_IKpsk2）。

## 0. 硬性红线：允许的积木与禁止清单

**只允许**：X25519（`ring::agreement`）、ChaCha20-Poly1305 / AES-256-GCM（`ring::aead`）、HKDF-SHA256（`ring::hkdf`）、HMAC-SHA256（`ring::hmac`）、SHA-256（`ring::digest`）；BLAKE3（blake3 crate）仅限非安全核心的标识用途（node_id / 分享链接指纹）。握手安全核心统一 SHA-256 族，减少原语数量。

**禁止清单**（任何 PR 违反即打回）：

| 禁止项 | 为什么 |
|---|---|
| 自造 AEAD 模式（如"ChaCha20 + 自己拼 MAC"） | AEAD 的安全性证明绑定具体组合（RFC 8439 / NIST SP 800-38D）；自拼几乎必然犯加密与认证顺序（encrypt-then-MAC 之外的排列均有已知攻击）、长度编码、AAD 边界错误 |
| 自造 KDF（自己迭代哈希） | 缺 domain separation → 同一密钥跨上下文复用；有长度扩展/双 Hash 歧义类陷阱。HKDF（RFC 5869）已被充分分析且 ring 有实现 |
| 自造签名方案 | 签名随机数偏差即私钥泄露（PS3、Android 比特币钱包事故）；且本项目威胁模型根本不需要签名 |
| 把 HMAC 当加密用 | HMAC 只提供认证不提供机密性；任何"HMAC 派生密钥流 + XOR"等价于自造流密码 = 密钥流复用灾难 |
| nonce 复用 / 随机 nonce 用于 AEAD | ChaCha20-Poly1305 nonce 复用 = 密钥流重用 + Poly1305 认证密钥可被恢复 → 明文与完整性同时崩溃；nonce 必须是每密钥唯一计数器 |
| MD5/SHA1、ECB、静态 IV、自造分组链接 | 均为已被攻破或无 IND-CPA 保证的构造 |
| 同一原语引入两套实现并存 | ring 0.16/0.17 双版本的供应链教训（review P2-7）；升级时必须收敛为单一版本 |

## 1. 承接的威胁模型与要修的洞

沿用 review 02 的攻击者 A/B/C 分层。v3 握手要修掉 v2 认证的四个结构性弱点：
1. **静态长期 PSK 无前向安全**：PSK 泄露 ⇒ 所有历史流量（若被录）可解。
2. **token 明文暴露 PSK 证据**：token 是可嗅探、可重放（30s 窗口内）的凭据，且不绑定 TLS 通道（P0-2 提到的 MITM 转发穿透）。
3. **无 nonce 重放表**（P1-1）。
4. **PSK 直接当 HMAC 在线密钥**：身份根被在线协议直接消费，应只作 HKDF 输入。

## 2. 密钥层级（L0–L3）

| 层 | 内容 | 输入 → 输出 | HKDF 约定 |
|---|---|---|---|
| L0 身份根 | PSK，32B，静态双端持有 | 配置 hex 解码 → 32B | 只作为握手 MixKey 输入；不再直接做任何在线 HMAC。cookie 密钥例外：`HKDF-Expand(psk, "hydra v3 cookie", 32)` 且混入启动随机数 |
| L1 握手密钥 | 每连接瞬时，Noise 链内 | `ck ← Extract(ck, DH(e_c,e_s))`，再 `MixKey(PSK)` | 由 snow（Noise）内部按规范处理：protocol_name = `"Noise_NNpsk2_25519_ChaChaPoly_SHA256"` |
| L2 会话密钥 | c2s / s2c AEAD 密钥，32B×2 | `HKDF-Extract(salt=tls_exporter(32B), ikm=handshake_hash)` → `Expand` | info 分别为 `"hydra v3 data c2s"` / `"hydra v3 data s2c"`；另 Expand `"hydra v3 rekey"` 得 L3 根 |
| L3 更新密钥 | rekey 棘轮 | `rk_{n+1} = HKDF-Expand(rk_n, "hydra v3 rekey step", 32)`；本轮数据密钥 `Expand(rk_n, "hydra v3 data c2s/s2c", 32)` | 触发：2^24 帧 / 1 GB / 10 min 任一先到；旧密钥立即 zeroize |

- 握手初始化（防降级）：`h₀ = SHA-256("hydra v3 handshake" ‖ version(1B) ‖ offered_suite_list)`，之后按 Noise 逐消息 MixHash（含密文），`handshake_hash` 即最终 transcript。
- AEAD nonce（96-bit）：`epoch(24b) ‖ dir(8b) ‖ seq(64b)`，每密钥内单调递增绝不复用；rekey 阈值远早于回绕点。
- 注意选 **NNpsk2 而非 IKpsk2**：IK 会把静态公钥放明文 = 可关联的身份标识，违背防追踪目标；单租户下 PSK 本身即身份，NNpsk2 暴露面最小。

## 3. 握手消息流（一次往返）

```
C→S  msg1 明文:  0x03 | suite_id(1) | ts_c(8) | c_nonce(16) | e_c(32)          [MixHash 全部]
S→C  msg2:       0x03 | e_s(32) | ct2 = AEAD(k2){ cert_fp(32) | ts_s(8) | s_nonce(16) | conf_s(32) }
C→S  msg3:       ct3 = AEAD(k3){ conf_c(32) | 首个业务请求 }
```

- `msg1 → msg2` 即 Noise **NNpsk2**（`-> e`，`<- e, ee, psk`）：服务端临时 X25519 后做 `ee` 与 `psk` 两次 MixKey，`k2/k3` 由链派生并混入 QUIC TLS exporter（`export_keying_material`，label `"hydra v3 tls-bind"`）——应用握手被钉死在当前 TLS 会话上。
- **PSK 证明在加密通道内**：明文中不出现任何 PSK 派生凭据；"知道 PSK"由隐式证明承担——无 PSK 不可能产出 k2/k3 下的合法 AEAD 密文。`conf_s/conf_c = HMAC(temp, handshake_hash)` 也在密文内，作为显式 transcript 确认。
- **前向安全**：`ee` 用双方临时 X25519；握手结束即销毁临时私钥。事后泄露 PSK 或证书均无法解出过去会话。
- **抗重放**：每次握手服务端贡献全新 `e_s`，捕获的 msg2/ct3 在新连接上必然解密失败——重放在密码学层面不可行。`ts_c + c_nonce` + 服务端有界 LRU nonce 表（review P1-1 方案）用于压制 msg1 重放造成的 pre-auth 搅动与限流记账。
- **防降级**：version 与 suite 列表进 `h₀`，两端 conf MAC 覆盖最终 transcript；客户端校验服务端所选 suite ∈ 自己的 offered 列表。改字节 = conf 必然失败。v3 客户端**永不**发送 0x00（见 §6），降级只能靠改客户端配置。
- **通道绑定（防 MITM 转发）**：`cert_fp = SHA-256(节点 SPKI DER)` 在 ct2 密文内并随 transcript 承诺；客户端核对 pin。结果：MITM ① 自持证书终结 → 无 PSK 过不了 ct2；② 逐字节转发 → exporter 绑定使另一条 TLS 会话的握手字节失效，只剩"纯哑管道"（等价于网线，机密性不破）。
- **防握手放大**：认证完成前服务端只回 ≈130B（对 ≈60B 的 msg1，比例 < 3×），与 QUIC 反放大上限一致；后续数据仅在 `conf_c` 验证后流动。

## 4. Cookie / 挑战机制

- 主防线交给 QUIC 本身：**启用 quinn stateless retry**（review P0-3 建议），地址验证与放大防护在传输层解决，握手洪泛无法积累服务端状态。
- 应用层 cookie 为**过载卸载与未来 raw-UDP 模式预留**：服务端过载时可回 `retry{ cookie_tag = HMAC(ck_cookie, ip ‖ ts_bucket ‖ h₁)(16) }`，客户端重发 msg1 并附 cookie；无状态验证，服务端零存储。本期可暂不实现（标注 MVP-外）。

## 5. 与 QUIC/TLS 的关系

- **v3 握手跑在 QUIC 双向流内**（连接建立后的第一条流），不在 UDP 原始层。理由：① 不自造传输层——拥塞控制/重传/反放大全部复用 QUIC，自造等于重写一个协议栈（红线）；② QUIC Retry 白嫖地址验证；③ 保持 ALPN `h3` 伪装。
- **TLS 保留**：rustls 0.23 + 现有 pinning 并存，不旁路。TLS 提供传输加密与 h3 伪装；**PSK 经 NNpsk2 成为唯一认证根**。
- **证书 pinning 的位置：并存且双重角色**。传输层 pinning 把 MITM 挡在握手之前；握手内 `cert_fp` 绑定修复"凭据不绑通道"的历史穿透面。若未来启用 ACME 真证书（pinning 弱化为域名验证），握手内的 PSK 认证仍然独立成立——两层解耦。

## 6. 迁移：新旧并存与版本协商

- 第一条流首字节即版本：`0x00` → 旧 v2 路径（64B token；时间戳大端最高字节恒 0x00，与 0x03 天然无冲突）；`0x03` → v3 握手。
- 服务端 `auth_mode = auto | v3 | v2`（默认 auto 双栈）；客户端按节点配置选择。分享链接增加 `v=3` 字段。
- 收敛策略：观测 2 个发布周期后 auto 变 v3-only；v2 路径整体删除。v2 存续期的弱点（无 FS/可重放）由"客户端只对声明 v3 的节点发起 v3"限制，不存在明文可篡改的协商降级（版本进 transcript）。

## 7. 实现映射

| 需求 | ring 0.17（先完成 review P2-7 的 0.16→0.17 升级） | 结论 |
|---|---|---|
| X25519 / ChaCha20-Poly1305 / AES-256-GCM / HKDF-SHA256 / HMAC-SHA256 / SHA-256 / 常量时间 / CSPRNG | `agreement` `aead` `hkdf` `hmac` `digest` `constant_time` `rand` | **全部具备，无缺口** |
| BLAKE3 | ring 无 | blake3 crate（可砍） |
| Noise NNpsk2 状态机 | 不在 ring 范围 | **建议引 snow**（`Noise_NNpsk2_25519_ChaChaPoly_SHA256`，ring resolver；psk2 修饰符与 §3 完全对应），握手结束后取 `handshake_hash` 自行 HKDF 出 L2/L3 |

- **自写 vs 引 crate**：自写 Noise 核心约 400–600 行 + 互操作/模糊测试，安全打磨需 1–2 周（MixKey/MixHash 顺序等细微错误不显性报错）；snow 集成约 2–4 天。结论：**核心状态机用 snow，自研留在合法空间**——消息封包、版本协商、cookie、rekey 策略、重放表、与 quinn 流的接驳。
- 工作量合计 ≈ 1 人周：握手集成 2 天，nonce 表/限流记账 1 天，rekey 0.5 天，迁移开关 0.5 天，测试（重放/降级/篡改/两代并存）2–3 天。

## 8. 开放问题

1. BLAKE3 是否值得为一个 node_id 引依赖（倾向：否，用 SHA-256）。
2. 应用层 cookie 本期实现与否（倾向：暂缓，依赖 QUIC Retry）。
3. PSK 轮换策略（分享链接重发即轮换，协议无需额外机制；可在 v3 落地后再议）。
