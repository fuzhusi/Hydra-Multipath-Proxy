# Hydra 内核优化方案 v1 —— 从可用到企业级

> 日期：2026-10-11 ｜ 状态：提案待拍板（选方向后进入 设计→评审→实施 流程）
> 基线：master 4823805（0.2.6+，363 测试，TCP 转型 + TUN 全端口动态接流 + UDP 中继 + 三端 UI）

---

## 一、现状盘点

### 强项（已达到或接近企业级）
- 协议安全：TLS 1.3 + Noise-PSK（confirm 常时比较、通道绑定 exporter）、证书双信任路线、ClientHello 指纹近似
- 并发纪律：锁不跨 await、热路径零锁计数、有界队列、任务生命周期全覆盖（企业评审 27 项发现全部闭环）
- 可观测性：结构化日志脱敏、Prometheus metrics v2、协议层丢弃计数
- 工程质量：363 测试、clippy 零告警、双平台 CI、四平台 release 自动化、keystore 签名链

### 短板（企业级差距，按严重度）
| # | 短板 | 影响 |
|---|---|---|
| S1 | **单用户 PSK**——节点只能服务一个密钥（一个用户） | 企业级最大硬伤：无法多用户/多设备差异化运营 |
| S2 | **无密钥轮换**：PSK 长期不变；泄露只能手工换全端 | 安全合规硬伤 |
| S3 | **单 TCP 连接承载全部流量**——队头阻塞（HOL）：一个大流量传输会拖慢同连接上的交互流量；连接抖动 = 全部会话瞬间掉线 | 体验/可靠性核心短板 |
| S4 | **热路径分配**：UDP 中继每数据报 2-3 次 String/Vec 堆分配（企业评审 PERF-01 修复不彻底）、中继泵逐帧 Vec 拷贝 | 吞吐上限、尾延迟 |
| S5 | **重连成本高**：全握手（TLS 1.3 + Noise）断线重连数百 ms、无会话恢复 | 移动端/弱网友 experiences |
| S6 | **协议解码器零模糊测试**——企业安全审计必查项 | 安全信任缺口 |
| S7 | 无零停机重启（节点升级断全部连接）、配置热重载不完整 | 运维体验 |

## 二、优化提案（按层级）

### L1 性能层（吃掉 S4，预计吞吐 +30-80%）

#### 1.1 热路径零分配改造 ⏱ 3-5 天
- `udp_relay`：`target` 字段改 `Arc<str>`（PERF-01 遗留的 has_target 锁内比较 + clone_handle 零克隆）；数据报路径 `Vec<u8>` → `bytes::Bytes` 切片化（零拷贝）
- 中继双向泵：`tokio::io::copy_bidirectional` 已在用，剩余分配点用 `Vec::with_capacity` 复用缓冲
- 验收： criterion 基准测试（改造前后吞吐/分配数对比），pprof 火焰图入 docs

#### 1.2 发送聚合（sendmmsg 风格）⏱ 2-3 天
- UDP 下行帧合并写：mpsc 攒批（≤1ms 或 ≤16 帧）一次 `write_all`，减少 TLS 帧开销与系统调用
- 风险低（纯节点侧优化）

### L2 可靠性/企业运维层

#### 2.1 多用户 PSK 表（吃掉 S1）⏱ 5-8 天 ⭐ 企业级核心
- 节点侧：PSK 表（`user_id → psk`，配置文件/toml），握手时按 key id 查表（Noise psk0 改 pskN 或握手首字节携带 key_id）
- 每用户：独立限速（令牌桶）、连接数配额、流量统计（Prometheus per-user 指标）
- 撤销：删除表项即吊销（配合 2.2 更优雅）
- 客户端：无感知（仍单 PSK，key_id 握手协商）
- 风险：协议变更需两端同步升级（版本协商已有基建）

#### 2.2 Rekey 密钥棘轮（吃掉 S2）⏱ 4-6 天
- 已有方案（docs）：基于 Noise 的 handshaking 重协商——每 N GB 或 T 分钟触发新 Noise 握手（旧密钥前向保密），PSK 轮换由 2.1 的表驱动
- 与 2.1 同协议批次实施（一次两端升级）

#### 2.3 零停机重启 + 配置热重载（吃掉 S7）⏱ 2-3 天
- 节点：SO_REUSEPORT 双进程交接（新进程起监听 → 旧进程 systemd 停止），或 SD_NOTIFY 平滑方案
- 配置：SIGHUP / inotify 热重载（PSK 表/限速/日志级别即时生效）

#### 2.4 协议解码器 cargo-fuzz ⏱ 2 天 ⭐ 安全审计硬通货
- udp_frame/tcp_frame/stun/handshake 四个解码器 fuzz target（企业评审遗留）
- 产出：fuzz 报告入 docs/review（对外可展示的安全证据）

### L3 协议演进层（吃掉 S3/S5，特色竞争力）

#### 3.1 多通道并发（拆 HOL）⏱ 8-12 天 ⭐⭐ 大工程
- 客户端↔节点维持 2-4 条并发 TLS 连接，会话按哈希分片（交互流量走低延迟通道、批量流量走高吞吐通道）
- Happy Eyeballs 思路：节点延迟探测选主通道，其余热备
- 依赖：会话迁移语义（连接死亡 → 会话在备用通道重建，UI 无感）
- 收益：单连接抖动不再全量掉线、交互流量不被批量流量饿死

#### 3.2 断线会话保持（连接迁移 lite）⏱ 3-4 天
- 客户端重连后：节点侧对「同 PSK + 同目标」的 UDP 会话保留 T 秒可重挂（TCP 会话无法迁移，UDP/DNS 可）
- 与 3.1 互补

### L4 差异化亮点层（可选，市场竞争力）

#### 4.1 智能分流（规则路由）⏱ 5-7 天
- TUN 模式下：GeoIP/域名规则 → 直连/代理/拒绝（Clash 核心能力的子集）
- 依赖：规则引擎（domain-suffix/keyword/ip-cidr 三类足够）+ GeoIP 库（可选内置精简 CN 列表）
- 用户感知强，是代理工具的「标配期望」

#### 4.2 链式代理（级联）⏱ 4-6 天
- 节点→上游代理（支持 hydra/SOCKS5 上游），场景：多跳隐匿
- 风险：延迟叠加，小众需求

## 三、优先级矩阵（收益 × 成本）

| 提案 | 企业级收益 | 工作量 | 风险 | 建议批次 |
|---|---|---|---|---|
| 2.4 fuzz | 安全证据 | 2 天 | 零 | **第一批** |
| 2.1 多用户 PSK | ⭐⭐⭐ 核心 | 5-8 天 | 协议变更 | **第一批** |
| 1.1 零分配 | 性能 | 3-5 天 | 低 | 第一批 |
| 2.2 Rekey | 安全 | 4-6 天 | 与 2.1 耦合 | 第二批（随 2.1） |
| 1.2 发送聚合 | 性能 | 2-3 天 | 低 | 第二批 |
| 2.3 零停机 | 运维 | 2-3 天 | 中 | 第二批 |
| 3.2 UDP 会话保持 | 体验 | 3-4 天 | 中 | 第三批 |
| 3.1 多通道并发 | ⭐⭐ 架构 | 8-12 天 | 高（两端协议） | 第三批 |
| 4.1 智能分流 | 用户感知 | 5-7 天 | 中 | 按需求 |
| 4.2 链式代理 | 小众 | 4-6 天 | 中 | 按需求 |

**建议第一打包**（约 10-15 天）：2.4 fuzz + 2.1 多用户 + 1.1 零分配——
交付即具备「多用户企业运营 + 安全审计证据 + 性能基准」三张企业级门票。

## 四、需要你拍板的三件事

1. **多用户 PSK（2.1）做不做？** 这是「个人工具 → 企业可运营」的分水岭，协议要动（两端同步升级，旧客户端需兼容期）
2. **性能基线**：要不要先建 criterion 基准（1.1 的前置，1 天）——有基准的优化才有说服力
3. **批次顺序**认不认可（第一包：fuzz + 多用户 + 零分配）？或者你有别的优先项（比如先做 4.1 智能分流这种用户感知强的）
