# 2. 与 RFC v1.0 的偏差记录（重要）

v1 是项目初创时的**多链路聚合**设想。实现过程中基于企业级评审与实际需求做了方向性调整，逐项如实记录：

| v1 设想 | 现状 | 偏差原因 |
|---|---|---|
| QUIC（quinn）传输 | **TCP 443 + TLS 1.3 伪装** | QUIC/UDP 特征在受限网络下易被识别与阻断；TCP 443 与普通 HTTPS 流量不可区分（后续 ClientHello 指纹近似进一步强化） |
| 多节点 Chunk 分片 + 乱序重组 | **单节点自动调度**（最低延迟优选 + 健康检查 + 故障切换） | 分片重组引入的复杂度/乱序开销在代理场景收益为负（流式流量无法乱序交付）；企业评审判定「聚合」非首批价值 |
| protobuf/flatbuffers | 自定义紧凑二进制帧（长度前缀） | 更少的依赖与更小的攻击面 |
| Hydra 协议帧（Chunk/Offset/Checksum） | Noise-PSK 加密帧（加密层自带完整性） | 应用层校验冗余 |
| Phase 4：用户管理/面板 | 单 PSK（多用户架构已**预留**：握手 key_id 字节位 + PSKSource enum） | 个人工具先行；多用户为企业化门槛项，规划见 §6 |
| 「Multipath」命名 | 保留项目名；多路径聚合**转长期方向**（§6 重评估条目） | 单路径调度已满足当前需求；聚合需协议 v2 与调度研究 |

**继承自 v1 并已实现**：加密通信 ✓、自动线路选择（延迟优选）✓、节点故障切换 ✓、NAT 穿透场景的基础（TUN/代理双模式覆盖）✓。
**继承自 v1 未做**：带宽聚合、数据分片重组、BBR/AI 调度、P2P 共享、面板系统——全部转入 §6 规划。

# 3. 现行架构（实际代码）

```
┌────────────────────────────────────────────────┐
│ 三端 UI                                        │
│  Windows egui(4主题) │ Linux egui │ Android M3 │
└──────────┬─────────────────────┬───────────────┘
           │ FFI(uniffi)         │
┌──────────▼──────────┐  ┌───────▼────────┐
│ hydra-client-gui    │  │ hydra-android  │
│ proxy_control/配置  │  │ VPN Service    │
└──────────┬──────────┘  └───────┬────────┘
           │                     │
┌──────────▼─────────────────────▼──────────────┐
│ hydra-client（TUN 数据面 / 本地代理 / 调度）  │
│   ├─ 智能分流 RuleEngine（双模：IP + 域名）    │
│   ├─ TUN：全端口接流 + UDP 直发池（双形态）    │
│   └─ 本地代理：SOCKS5/HTTP + 域名直连          │
├───────────────────────────────────────────────┤
│ hydra-core（协议/加密/通道/路由/保护钩子）     │
├───────────────────────────────────────────────┤
│ hydra-protocol（帧编解码） │ hydra-fetch      │
└───────────────────┬───────────────────────────┘
                    │ TCP 443（TLS1.3 伪装 + Noise-PSK）
              ┌─────▼─────┐
              │ hydra-node │ → Internet
              └───────────┘
```

安全设计要点（贯穿三端）：

- **直连失败一律回退节点**——分流永不导致断网
- 出站 socket 统一经 protect 钩子（安卓 `VpnService.protect` / 桌面透传）——防回环
- 规则文件损坏 → 降级内置 CN 表（日志 + UI 如实告知）
- 日志脱敏（目标地址打码）、无新增 Android 权限、规则文件仅沙箱可读

# 7. 非目标

- 不做匿名网络（Tor 类）——Hydra 是代理加速与安全通道，不是 anonymity 网络
- 不做流量破解/绕过深度检测的对抗研究——伪装目标是「与正常 HTTPS 不可区分」，非主动对抗
- 不内置机场商业化运营能力——多用户表为企业自部署场景

---

# 8. 结论

Hydra 已从 v1 的多链路聚合原型设想，演进为**安全优先、规则驱动、三端一致的加密代理系统**：

> 安全的通道（TLS 伪装 + Noise-PSK）、智能的路径（统一规则分流）、
> 一致的体验（三端同口径）、可信的工程（评审台账 + 416 测试 + CI 全绿）。

下一步以「真机验证 → v0.2.8 → SNI 嗅探 → 热重载」为主线推进；
多路径聚合作为原始愿景保留在长期规划中，待协议 v2 与真实需求重评估。
