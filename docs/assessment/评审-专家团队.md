## 一、密码学与协议安全（整合自第一份分报告）

**总评分：7.5/10** —— 协议安全核心扎实，工程防探测细节到位；主要短板在"密钥模型全有或全无"、TUN 模式 IPv6 泄漏、信令滥用面与 rekey 缺失。

一句话结论：**TCP 转型后的协议核心（NNpsk2 握手 + 双通道 confirm 绑定 + 静默关流 + SSRF 过滤）是本项目安全质量最高的部分，密码学原语选择与实现细节达到可交付水准；遗留风险集中在密钥管理生命周期而非密码学本身。**

分层评分：Noise-PSK 握手 9/10；私有帧协议 8/10；真/自签双信任路线 7.5/10；密钥/凭据生命周期 5.5/10；TUN 安全边界 5/10；日志脱敏 7/10；威胁模型完整性 7.5/10。

### 亮点

1. **NNpsk2 模式选择正确且有清醒记录**：明确记录弃用 IKpsk2 的理由（IK 静态公钥构成被动识别指纹），规避了同类工具常犯的错误（handshake.rs:37-38）。
2. **confirm 双通道绑定完整**：HKDF-SHA256 同时绑定证书指纹（取 TLS 实际协商的叶证书，从结构上消灭多节点证书配对错误）与 TLS exporter（跨连接转发握手字节即失效，根治 QUIC 时代 P0-2 MITM）；方向域分离防反射，常数时间比较（handshake.rs:153-172）。
3. **抗重放有真重放测试**：transcript 级原样重放必被拒绝（handshake.rs:344-414），另有 PSK 错误、指纹不一致、exporter 不一致三个独立失败向量的双向测试。
4. **PSK 入口 fail-fast**：build() 入口、链接导入层、生成层三层一致校验"恰好 32 字节"，修复闭环完整。
5. **防主动探测语义一致**：失败一律零字节静默关流、错误折叠不回显差异、SSRF 拒绝与连不上同应答码、额度满快速丢弃、slowloris 与 idle 看门狗双防护。
6. **SSRF 过滤高于平均**：覆盖 loopback/link-local/RFC1918/ULA/0/8/::，并对 IPv4-mapped 与 NAT64 内嵌 IPv4 二次复查——多数实现遗漏的绕过向量。
7. **日志脱敏架构正确**：info 级 SHA-256 短哈希，debug 明文逃生门；客户端无任何 `lookup_host`，域名只经加密地址帧交节点解析（DNS 隐私承诺兑现）。
8. **密钥文件化与落盘权限**：节点密钥/自签私钥 0600 强制、GUI 配置 0600 且有权限断言测试。
9. **分享链接"链接=交出节点"模型有明确安全声明**，知边界并明示，好于沉默。

### 对 docs/review/03 的核验结论

QUIC 时代高危项已**基本以修复方式闭合**：F1 ALPN、F2 SNI 硬编码、F3 自签证书重生成、F4 SkipVerification、F5 开放中继、F12 DNS 回退泄漏、F13 硬编码 IP、F7 心跳 beacon 均已修复/随 QUIC 移除；F6（内层帧签名）部分缓解（PSK 模型固有边界，已如实声明）。剩余有效缺口收敛为 F8（ClientHello TLS 指纹，README 已如实声明）与"非认证 IP 反代静态页待实施"。

## 二、运维与可靠性（整合自第二份分报告）

**总评分：7.5/10** —— 服务器侧运维闭环已成型，客户端分发与监控告警是主要短板。

结论：上一轮《部署运维评估》列出的 P0 项**基本全部真实落实且有据可查**：systemd unit（含 WorkingDirectory 证书陷阱修复、非 root + CAP_NET_BIND_SERVICE、EnvironmentFile、全套沙箱加固）、install.sh 一键安装（幂等、密钥不覆盖）、Docker/compose、/health 健康端点、防火墙与三类静默故障排障表、升级流程文档均已交付。资源耗尽防护四件套（Semaphore 快速失败、TLS 握手 10s、认证 10s、300s idle 看门狗）在源码中真实存在。BBR 部署有降级反馈而非静默失败；`--auth-key` CLI 参数移除，代码与文档口径一致。

### 亮点

1. **systemd unit 质量高于同类自建项目平均**：`ProtectSystem=strict` + `ReadWritePaths` + `PrivateTmp` + `RestrictAddressFamilies` 完整沙箱，显式修掉 CWD 证书陷阱——很多正式项目做不到这个完整度。
2. **install.sh 幂等且密钥安全**：升级不覆盖密钥与证书；`openssl rand -hex 32` 自动生成、600 权限。
3. **资源耗尽防护四件套真实落地**，额度满主动 shedding 并注释客户端故障切换兜底。
4. **BBR sysctl 安装后回读验证**，不支持时警告保持 CUBIC——运维脚本应有的姿态。
5. **排障文档直击"静默关流"自设计痛点**：把四种日志上看起来一样的故障做成症状→确认（tcpdump/ss/openssl fingerprint）→修复对照表，可用 /health 先区分"进程死"与"链路断"。
6. **健康端点小而正确**：默认只绑 127.0.0.1，绑定失败显式退出而非吞掉；读 1KB 上限 + 5s 超时。
7. **对上一轮评估的改进是可验证的**：原评估缺失清单 8 项中大部分已落实，toml 死代码反转为可用的分层配置（`--config > env > node.toml > 默认值`，显式报错不静默回落）。**总评：原评估 P0 全部兑现，P1 兑现一半，整改真实而非纸面。**

## 三、产品与工程管理（整合自第三份分报告）

**综合评分：5.6/10** —— 一个"文档与自省质量远超平均水平、但产品叙事与发布工程严重脱节"的个人项目。

分维度：产品定位与差异化 5.5；路线图合理性 6.5；单人+AI 开发可持续性 7；**发布工程成熟度 2**；合规与自用边界 7。

核心判断：这个项目最大的资产不是代码，而是**它敢说真话的文档体系**；最大的风险也不是某个技术缺陷，而是 **README 头部"v1.0 可交付产品"叙事与仓库工程现实（全 crate 0.1.0、零 CI、零 CHANGELOG、零发布产物）之间的信誉裂缝**——对一个靠"宁缺勿假"立身的项目，这恰恰是最不该出现的问题。

### 亮点

1. **"宁缺勿假"已从口号变成可验证的文档实践**：docs/review/00 主动系统证伪"核心能力大部分是死代码"（12 项逐条）；README"已知限制"逐条如实；终端用户评估自评"便捷性 3/10"不护短——这种自我证伪在个人项目里极为罕见。
2. **设计方案质量高，决策链与非目标声明完整**：TCP 转型从真实约束（UDP 回程 QoS 丢包实证）出发，四方案对比弃选理由完整，保留方案修订与定版过程；NAT/TUN 方案的"非目标"与"实施偏差如实记录"堪称教科书级。
3. **差异化定位有真实支点**（虽未兑现）：多节点加权分发 + 故障自愈 + 测速动态调度已交付且有专项测试；TCP 转型 §6 正式放弃字节级聚合后，把**多节点并行下载**定为"Xray/Trojan/REALITY 均无此能力"的新差异化方向——判断在技术上成立。
4. **审查与测试体系具备"守得住"的雏形**：7 份审查报告逐轮销号机制、45 项审查 + P0/P1 修复闭环、测试从 125 → 153（TUN 方案记录 160）持续增长。

## 专家团队综合结论

### 共识优点

1. 【共识】**协议核心是全项目质量最高、可交付的部分**：安全专家确认 NNpsk2 + 双通道 confirm 绑定 + 真重放测试 + 防探测语义**无密码学缺陷**；运维专家独立验证了其中的资源耗尽防护四件套"真实落地"；产品专家确认协议转型决策链完整、方案修订如实记录。三方交叉印证。
2. 【共识】**文档诚实文化真实且系统化**："宁缺勿假"不只是口号——历史审查主动证伪、已知限制逐条声明、非目标教科书级、QUIC 时代高危项"以修复方式闭合"后旧报告结论如实失效。三位专家均将此列为首要亮点。
3. 【共识】**上一轮评估的整改是真实而非纸面的**：运维专家逐项销号确认原部署评估 P0 全部兑现；安全专家逐项核验确认 docs/review/03 高危项基本以修复方式闭合；产品专家确认 45 项审查 + P0/P1 修复闭环机制存在。
4. 【共识】**服务器侧交付链路是同类个人项目的上乘水准**：systemd 沙箱加固、幂等安装、BBR 降级反馈、静默故障排障表，两个技术角色分别从安全与可靠性角度独立给出高评价。

### 共识的 Top 问题

1. 【强共识】**零 CI、零发布产物是当前单点最大短板**：运维 P0-1、产品 P0-1/P1-4 从不同角度指向同一事实——仓库无 `.github/`，153 项测试与 7 份审查报告只能靠"记得跑"维持效力，Windows GUI 目标用户实际拿不到可用产物。三方均给出"约 1 天工作量、ROI 最高"的同一定性。
2. 【强共识】**对外叙事与工程现实脱节是第二优先级风险**：产品 P0-1（"v1.0 可交付" vs 全 0.1.0/零 CHANGELOG）与运维 P0-3（env.example 密钥长度文档回归）同属"名实不符"家族——对一个以"如实"立身的项目，文档回归的代价远高于普通项目。
3. 【共识】**TUN 模式 IPv6 直连泄漏是唯一可能造成真实用户伤害的技术缺陷**（安全 P1-1），且 README 的 v1 边界声明唯独漏了这一条——"文档诚实"项目的唯一显著例外。
4. 【共识】**凭据模型（全局单 PSK、无吊销）决定泄漏半径**（安全 P1-2），运维侧的 P0-3（密钥文档错误导致静默关流）与信令滥用面（安全 P1-4）均以此根子延伸。
5. 【共识】**监控告警与可观测性空白**（运维 P1-1~P1-5）与**Multipath 名实脱钩 + 真正差异化（并行下载）停在纸面**（产品 P0-2）分别构成两个角色的"长期结构性"问题。

### 分歧与张力

- 【分歧】**评审基准差异**：两个技术角色给 7.5/10，产品角色给 5.6/10。这不是事实分歧而是基准差异：技术角色按"同类项目工程水准"评分（协议实现、部署链路均属上乘），产品角色按"项目自我声明的交付标准"评分（"v1.0 可交付产品"的叙事无工程支撑）。合并观点：**代码质量与工程治理严重不对称**——这正是三份报告拼在一起后最完整的画像。
- 【分歧】**路线图优先级**：安全专家的第二梯队把多 PSK/凭据体系、信令属主证明列为结构必做项；产品专家主张路线图首位应是反代静态页与并行下载。合并观点：两者不冲突——反代静态页同时出现在安全 P2-5① 与产品 P1-2 建议中，是跨角色的交集项；凭据体系与并行下载分属"安全地基"与"差异化兑现"两条线，可并行。
- 【细微出入】测试总数：产品报告记录 125/153/160 三个数字并存本身即为其 P1-3 问题的一部分，属事实待核（以 `cargo test --workspace` 最新结果为准）。

### 结语

三位专家的结论可以合成一句话：**这个项目的协议安全实现与服务器侧工程已经达到可交付水准且无密码学缺陷，但它此刻最需要的不是新功能，而是把对外的每一句陈述都变成工程上可验证的事实**——最小 CI + 版本化 + 名实澄清约 2-3 天即可完成这笔当前性价比最高的投入；随后按 P0/P1/P2 路线依次补上 TUN IPv6 泄漏、凭据生命周期与监控告警三块真实短板。对一个以"宁缺勿假"立身的项目，名实相符不是洁癖，是生存底线。
