# Hydra V3 协议架构草案：自研协议身份路线

- 日期：2026-10-03 ｜ 角色：协议架构师 ｜ 状态：草案（待评审）
- 背景：老板需求——"协议和加密都是开源的（标准 QUIC/TLS），能不能有一套我们自己的东西"。约束：个人维护 + AI 协作，人力有限。
- 前置输入：docs/review/00（审查总览）、docs/review/03（防追踪性）、docs/Hydra-Multipath-Proxy-RFC-v1.md（多链路聚合原始梦想）、README（V2 现状）

## 0. "自研"的边界（先回答老板的问题）

我们的"自有协议身份"由三样东西构成，全部不碰密码学：
1. **线缆身份（V3.1）**：hydra-wrap 报文混淆层——UDP 线上载荷是均匀随机字节，与一切"裸 QUIC"工具可区分（也不可被 DPI 识别）；
2. **握手身份（V3.2）**：Hydra-Noise-PSK v2——自研握手流程与状态机，替换现静态 HMAC token，获得前向安全；
3. **调度身份（V3.3）**：会话层多路径聚合算法，兑现 RFC v1 核心卖点。

密码学积木全部使用验证过的标准件（crate：snow / ring / blake3）：
X25519、ChaCha20-Poly1305、AES-256-GCM、HKDF-SHA256、HMAC-SHA256、BLAKE3。
**允许自研的只有：帧格式、握手流程、状态机、混淆层、调度算法。**

## 1. 设计红线（任何阶段不得违反）

- R1 禁止自造密码学原语（含"改一下轮数/换个常数"级别的事），只许按标准模式组合上列原语。
- R2 混淆层/握手解密失败 → 静默丢弃，任何情况不产生可区分回应（保住 03 报告的主动探测抵抗结论）。
- R3 每个 V3 特性必须有 off 开关，保证与 V2 节点全程共存；README 只描述真实启用的能力。
- R4 视频流量永远可直通单路径；聚合只给下载/大文件（审查总览执行原则 2）。
- R5 工作量以人日诚实标注；单阶段 >25 人日必须再拆。

## 2. 三条路线评估

### 2.1 路线 A：QUIC 外套自研混淆层（hydra-wrap）

分层草图（自下而上）：

```
UDP → [hydra-wrap: 每报文 ChaCha20-Poly1305 变换] → quinn(QUIC+TLS1.3+webpki pinning) → V2 流协议(HMAC token + 地址帧 + 裸转发)
```

- 报文格式：`[12B nonce] + ChaCha20-Poly1305(wrap_key, nonce, 完整 QUIC 报文)`，输出为随机字节（参考 Hysteria2 Salamander 思路，但用标准 AEAD）；每包开销 28B（nonce 12 + tag 16）。
- wrap_key = HKDF-SHA256(ikm=PSK, salt=UTC 日期, info="hydra-wrap-v1")，双端各自按日期派生，无需带内同步；解密时依次试昨/今/明 3 把，容忍 ±1 天时钟偏差。12B 随机 nonce + 日密钥：按 1 万包/秒计，日包数远低于 2^32 birthday 界。
- 实现要点：quinn 0.10 的 `AsyncUdpSocket` 抽象（`Endpoint::new_with_abstract_socket`），包一层 `quinn_udp::UdpSocketState`，在 poll_send/poll_recv 里做变换；传输参数 `max_udp_payload_size` 降至 1200，1200+28 < IPv6 最小 MTU 1280，避免分片。
- 垃圾包处理：解密失败静默丢 + 每源 IP 令牌桶，零回应（R2）。
- 与 pinning/认证叠加：wrap 位于 TLS 之下，webpki pinning、首包 HMAC 认证原样保留；wrap_key 与 auth 用同一 PSK 不同 HKDF info，密钥分离互不泄露。
- 性能：每包一次 AEAD，吞吐损失 <5%（支持 AES-NI 的机器可选 AES-256-GCM，近零开销）。
- 新模块：`hydra-obfs`（变换、密钥派生、限速）约 600 行。
- 衔接点：`hydra-client/src/transport.rs::create_shared_endpoint`、`hydra-node/src/server.rs::new`、`NodeOptions` 加 obfs 配置、新增 `HYDRA_OBFS_KEY`（缺省复用 HYDRA_AUTH_KEY 派生）。
- 工作量：**5–8 人日**。
- 风险：① 对垃圾 UDP 无回应这一点可与真 h3 站点区分（发随机包看回包），残余风险如实记录；② quinn 升级 0.11 时 AsyncUdpSocket API 需跟改（约半天）。

### 2.2 路线 B：完全自研 UDP 传输协议（Noise-PSK + 帧 + ARQ + 拥塞控制 + 原生多路径）

分层草图：`UDP → hydra-wrap(仍然需要！) → Hydra Transport(握手/帧复用/ARQ/CC) → 会话层多路径`

要重造的轮子（诚实清单）：

| 轮子 | 内容 | 人日 |
|---|---|---|
| 握手与状态机 | Noise_IKpsk2 重传、超时、版本协商 | 3–5 |
| 帧编解码 | stream/chunk/ack/ping 帧 + PMTUD | 3–5 |
| 可靠性 | SACK、RTO/PTO、快速重传 | 5–10 |
| 拥塞控制 | CUBIC 起步；BBR 是调优无底洞 | 10–20 |
| 流复用与乱序交付 | 多流调度、流控窗口 | 5–8 |
| 运维面 | keepalive、连接迁移、MTU 探测 | 5–10 |
| 多路径调度 | 真正的目标，但依赖以上全部 | 10–15 |

合计 **41–73 人日到"实验室可用"**；要达到视频级（4K、跨境丢包链路）稳定，100+ 人日加长尾 bug。且自制协议明文结构本身就是新指纹，外层还得再套路线 A 的混淆层——等于先做 B 再做 A。
结论：**近期否决**。唯一不可替代的优点是原生多路径，但 V3.3 的应用层聚合能拿到约 80% 收益。保留为远期选项（V4+）。

### 2.3 路线 C：渐进混合（推荐）

A 打底（线缆身份）→ QUIC 流上自研握手 v2（协议身份）→ 应用层多路径聚合（兑现 RFC）。
每步独立可用、独立回滚、与 V2 节点全程共存，完全贴合单人维护的现实。

## 3. 分阶段推荐路线与验收标准

| 阶段 | 内容 | 工作量 | 验收标准（全部可测） |
|---|---|---|---|
| V3.1 | hydra-wrap 混淆层（路线 A 全量） | 5–8 人日 | ① Wireshark 抓包读不出 QUIC Initial/ALPN/SNI，载荷通过随机性卡方检验；② 吞吐损失 <5%，现有 64KB 大块往返测试不回归；③ obfs=off 时与 V2 节点互通回归通过；④ 1 万垃圾 UDP 包：零回应、内存/CPU 平稳 |
| V3.2 | Hydra-Noise-PSK v2 握手（替换静态 token） | 8–12 人日 | ① snow 标准测试向量通过；重放整段旧握手报文被拒；② 篡改任一字节 → 握手失败且静默关流；③ 握手密钥与 rustls TLS exporter（export_keying_material）绑定，跨连接转发/重放 token 无效；④ 节点双模式共存：首字节 0x03=v3 握手，V2 token 首 8B 为大端时间戳（首字节恒 0x00），判别无冲突；⑤ 消除现 30s 时间窗的时钟依赖 |
| V3.3 | 会话层多路径聚合（RFC v1 兑现） | 15–25 人日 | ① 两好一差三节点聚合吞吐 ≥ 最优单节点 ×2；② 聚合中途杀 1 节点，传输不中断、1GB 往返校验和零损坏（未确认 chunk 超时重发）；③ 乱序窗口有界、分片超时回收（修审查 P2 遗留的 Assembler 无超时无窗口问题）；④ 各路径独立 pacing 与去相关抖动，规避"多五元组强同步"最强特征（03 报告 F15）；⑤ 视频流量默认走直通路径 |

### 迁移策略（不可能一夜全换）

1. PSK 一把到底不换；V3.1 起分享链接加 `?v=3&cap=wrap,noise` 能力字段（顺带修 F14"链接无凭据"问题：加入证书指纹字段）。
2. 升级顺序：客户端先升级（对 V2 节点行为不变）→ 逐节点开 wrap → 全量后开 v2 握手 → 聚合按需 opt-in。
3. 每阶段结束跑一次三维度复审（审查总览执行原则 4）。

## 4. 明确不做（本轮）

- 自造任何 AEAD/哈希/KDF/密钥交换。
- 浏览器级 TLS 指纹模拟（Rust 生态无 uTLS 等价物，架构级约束，见 03 报告 F8）。
- REALITY 式证书借用/站点前置（远期另立项）；NAT 穿透（另立项）。

## 5. 开放问题

- 日派生 wrap_key 的时钟偏差容忍取几天（当前 ±1）。
- 依赖升级（quinn 0.11 / rustls 0.23，Phase B 已列）与 V3.1 的先后：建议 wrap 先行（两改动不相交）；rustls 0.23 的 exporter 接口对 V3.2 有利，可并行评估。
- V3.3 调度权重沿用 RFC §6 的 bandwidth/latency/loss 评分模型，参数靠 Phase B 测速数据校准。
