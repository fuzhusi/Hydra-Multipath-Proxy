# 11 - 安卓无网审计：v0.2.6 → v0.2.7 全局模式数据面回归排查

> 日期：2026-10-18 ｜ 审计人：DSH 子代理（只读审计，**未修改任何代码**）
> 范围：`git diff v0.2.6 v0.2.7`（daada83 → 6ca1f65）对**安卓全局模式（`rule_engine = None`）数据面**的影响
> 症状：安卓 VPN 已连接 + 节点直连 TCP 可通 + 所有网站打不开
> 结论先行：**未发现 v0.2.6 → v0.2.7 的全局模式代码回归**；等价性逐点核查通过（唯一实质差异是 UDP 回包校验和修复，方向为「修好」）

## 2. 逐项核对（A–G）

### A. UDP 校验和修复（2d428ac）：是否引入新问题？

**修复内容（`hydra-client/src/tun.rs`，v0.2.6 → v0.2.7）**

```diff
@@ build_udp_reply_v4
     pkt[24..26].copy_from_slice(&(udp_len as u16).to_be_bytes());
-    // 伪首部校验和
+    // ⚠ 载荷必须在算校验和**之前**写入（审查 P0-1：此前先算校验和再拷载荷，
+    // 校验和覆盖的是全零载荷 → 所有非空回包被本机栈校验失败丢弃，
+    // UDP 直连与既有中继回包全链路静默失效）
+    pkt[28..].copy_from_slice(payload);
+    // 伪首部校验和（RFC 768：伪首部 + UDP 头 + 载荷）
     let mut pseudo = Vec::with_capacity(12 + udp_len);
     ...
     let uc = checksum16(&pseudo);
     pkt[26..28].copy_from_slice(&uc.to_be_bytes());
-    pkt[28..].copy_from_slice(payload);
```

v6 同理，并追加 RFC 2460 要求：

```diff
+    let uc = if uc == 0 { 0xFFFF } else { uc };
```

**边界核查结果**

| 检查点 | 结论 |
|---|---|
| v4 载荷写入顺序 | 正确。`pkt` 长度 = `20 + udp_len` = `28 + payload.len()`，`pkt[28..]` 精确匹配，无越界、无截断 |
| v6 载荷写入顺序 | 正确。`pkt` 长度 = `40 + udp_len` = `48 + payload.len()` |
| v6 `0 → 0xFFFF` 改写 | **正确且必需**。发送 0xFFFF 时接收端反码和折叠为 0xFFFF → 校验通过；若发 0 则 v6 视为「无校验和」，必丢 |
| `checksum16` 奇数长度 | 正确（奇字节左移 8 位补零，符合网络字节序）；v0.2.6 → v0.2.7 **未改动** |
| IP 头校验和 | 不受影响（仅覆盖 `pkt[..20]`，与载荷无关） |
| v4 未做 `0 → 0xFFFF` | 见 §3 **P3-1**：RFC 768 建议同改，但 v4 允许 0 表示「未计算」，概率 1/65536，影响可忽略 |

**关键推断（为什么它不可能造成「无网」）**：该修复只影响**回包注入 TUN 的校验字段**。安卓侧 DNS 只有两种可能路径，二者都排除它是元凶：

1. **解析器绕过 TUN**（项目 logcat 实证，见 §3 P0-1）：DNS 报文根本不进中继 → 修复对 DNS 完全不可见；
2. **DNS 报文进 TUN 走节点中继**：修复只会让此前**全部被丢弃**的 DNS 回包变得合法 → 是**修好**而不是弄坏。

⇒ 方向单调，不存在「修复后反而断网」的路径。

> 项目自身评审（`docs/review/10-智能分流实施评审与修复.md` L74-81）原文佐证：
> 「校验和覆盖的是全零载荷 → 所有非空回包校验和错误 → 本机 IP 栈静默丢弃」，
> 且 v0.2.6 的中继回包调用点（`v0.2.6:hydra-client/src/tun.rs:1563`）与直连回包
> 共用同一函数 → **v0.2.6 的 UDP-over-隧道 回包是全废的**。

### B. `try_forward_udp` 新增规则分支：`rule_engine = None` 时是否完全短路？

**签名变化（v0.2.7）**：改为返回 boxed future（async），新增 `rule` / `direct` / `dns_direct` 三个参数。
**调用点**：两处（v6 分支、v4 分支）均为 `try_forward_udp(...).await;`，返回的 `bool`
**被忽略** —— 与 v0.2.6 一致（v0.2.6 调用点为 `try_forward_udp(pkt, tx);`，同样忽略返回值）。

**新增分支（v0.2.7，原文）**：

```rust
let rule_mode = rule.is_some() && direct.is_some();
let allow_private = private_targets_allowed() || rule_mode;
...
if let (Some(rule), Some(direct)) = (rule, direct) {
    let decision = rule.decide(dst);
    let force_dns_direct = dns_direct && dst.port() == 53;
    if decision == Decision::Direct || force_dns_direct {
        if direct.forward(src, dst, payload).await { return true; }
        debug!("TUN UDP 直连不可用（{} → {}），回落节点中继", src, dst);
    }
}
let flow = format!("{src}|{dst}");
cmd_tx.try_send(UdpCmd::Send { flow, dst, src, data: pkt[off..off + len].to_vec() }).is_ok()
```

**逐点核对（`rule = None` / `direct = None`，即安卓全局模式）**：

| 子项 | v0.2.6 | v0.2.7（rule_mode=false） | 等价 |
|---|---|---|---|
| 规则判定块 | 无 | `if let (Some, Some)` 不匹配 → **整体跳过** | ✅ |
| `allow_private` | `private_targets_allowed()` | `private_targets_allowed() \|\| false` = 同值 | ✅ |
| `excluded`（v4） | `private_like \|\| is_broadcast \|\| is_multicast` | 追加 `\|\| is_unspecified()` | ⚠ 见 P2-2 |
| `excluded`（v6） | `private_like \|\| is_multicast` | **逐字相同** | ✅ |
| `cmd_tx.try_send(...)` | 同 | 逐字相同，`.is_ok()` 返回语义保留 | ✅ |
| 返回值消费方 | 忽略 | 忽略 | ✅ |

v4 的 `private_like` 本身已含 `v4.octets()[0] == 0`，故 `is_unspecified()` 在
`allow_private == false` 分支是**恒等增强**；只有 `HYDRA_ALLOW_PRIVATE_TARGETS=1`
或规则模式（`allow_private == true`）时才改变行为 → 安卓两者都不满足（见 §3 P2-2）。

v4 分发的**外层**过滤同样保持：

```diff
-                            || (private && !allow_private);
+                            || (private && !allow_private && !rule_mode);
```

`rule_mode = cfg.rule_engine.is_some() && udp_direct.is_some()`，安卓全局模式恒 `false` → 与 v0.2.6 同值。

## 3. 嫌疑点清单（P0–P3）

### P0-1 ｜ VpnBuilder 未声明 DNS → VPN 网络 DNS 列表为空 → 解析绕过 TUN（**头号嫌疑，非区间回归**）

- **证据 1（代码，双 tag 相同）**：`android/.../HydraVpnService.kt` 的 `establish()` 无任何
  `addDnsServer(...)`；`hydra-android` tag 代码 `dns_via_proxy: true` + `exclude_routes` 空。
- **证据 2（真实 logcat，项目自记）**：工作树 `HydraVpnService.kt` 的修复注释原文：
  > 「全局模式必须显式设置 DNS（修「已连接但没网」）：VpnBuilder 不调 addDnsServer 时 VPN
  > 网络 DNS 列表为空（logcat：`Setting DNS servers for network 102 to []`），Android
  > 解析器回落到物理网络 DNS 并按底层网络路由直接发出——**绕过 TUN**，墙内环境被 GFW
  > 污染（A→Facebook IP、AAAA→1001::1），应用连假地址经节点全部不可达回 RST =
  > UI 已连接但「没网」。」
- **机理链**：DNS 空列表 → 解析走物理网络 → 污染答案/无答案 → 应用向假 IP 发起连接 →
  仍进 TUN（`0/1`+`128/1` 全接管）→ 交节点 → 节点连假 IP 失败/RST → 全部站点打不开。
  同时完美解释「节点直连 TCP 测试可通」（该测试不经系统解析器/或直连节点 IP）。
- **为什么表现为「v0.2.6 好、v0.2.7 坏」**：两版**代码相同**，差异只在探针环境（见 P1-2）。
- **影响**：真机 + 污染 DNS 环境 = 全网不可用；模拟器/干净 DNS 环境 = 看似正常。
- **优先级：P0（但定性为「v0.2.6 既有缺陷在真机场景暴露」，不是 v0.2.6→v0.2.7 回归）**。
- **修复方向（供父级决策，本次未改）**：全局模式显式 `addDnsServer(...)`（真机 = VPN 网络
  内路由，查询进 TUN 由数据面经节点解析）；或将 DNS 直连联动按需求接入。

### P0-2 ｜ v0.2.7 release APK 无 tracing subscriber → 内核日志全丢（**诊断阻塞**）

- **证据 1**：`hydra-android/Cargo.toml`（v0.2.7 tag）依赖仅 `tracing`，**无** `android_logger`
  或 `tracing-subscriber`；`git grep -n "tracing_subscriber|set_global_default|log::set"`
  （限 `hydra-android` / `hydra-client/src` / `hydra-core/src`）**只命中 CLI**
  （`hydra-client/src/main.rs:393-398`）与测试 → **安卓进程内没有任何 subscriber**。
- **证据 2（APK 字节级）**：v0.2.7 release APK 的 `.so` 搜不到 `RUST_LOG` / `hydra.log` /
  `tracing_subscriber` 标记；今日构建的 debug APK（含在途改动）三个标记齐全。
- **影响**：`hydra_client::tun` / `hydra_core::proxy` 的 `info!/warn!/debug!` 事件

  → 无法区分「DNS 空列表」「kill switch 阻断」「栈退出」三种假说。
- **优先级：P0（阻塞真机定位）**。工作树已含同款诊断补丁（`hydra-android/src/lib.rs:575-600`
  写 `/data/user/0/dev.hydra.vpn/files/hydra.log`），建议纳入下一版诊断包。

### P1-1 ｜ kill switch / 数据面退出后自动重连可能整网阻断

- **证据**：`HydraVpnService.kt`（v0.2.7，区间内未改）在数据面退出回调里：
  `"✗ 数据面退出（$reason）——自动重连（第 $restartCount 次）"`、
  `"✗ 连续 5 次数据面退出——停止自动重连…"`、
  `"🛡 kill switch：数据面中断——已阻断流量防泄漏"`。
  若 kill switch 处于阻断态而 UI 仍显示「已连接」，症状完全吻合。
- **区间差异核查**：本文件未改动；且已逐点核查 v0.2.6→v0.2.7 全局模式**没有新增退出/panic 路径**：
  - `try_forward_udp` 转 async 后仅 `try_send`（不 await 通道、不 panic）；
  - `build_udp_reply_*` 载荷写入长度精确（A 已证）；
  - 规则分支、janitor、直连 NAT 全部被 `rule_engine` 门控（B/C/D 已证）。
- **优先级：P1**（需 P0-2 解除阻塞后用日志排除；若无数据面退出日志，可降为 P3）。

### P1-2 ｜「v0.2.6 全网可用」基线不可靠（**必须告知回流**）

- **证据 1（验证环境 = 模拟器）**：`CHANGELOG.md`（HEAD）原文：
  > 「### 真机验证结论（**Medium_Phone_API_37 模拟器** + 真实节点 43.133.91.218）
  > - ✅ M2 全局 VPN 端到端打通：`tun0` UP（10.7.0.1/30），隧道 **RX 30MB/TX 688KB** 实测流量」

  README 同口径：「真机端到端验证（v0.2.6，**模拟器** + 真实 VPS）」。
  模拟器的底层网络 DNS 来自宿主机（通常干净/未被污染）→ **恰好掩盖 P0-1**。
- **证据 2（30MB 是 TCP）**：同期 UDP 中继回包因 A 项缺陷**全废**（项目评审原文），
  说明 30MB 隧道流量是 TCP 贡献，v0.2.6 从未验证 UDP/DNS 通路。
- **证据 3（APK 物证）**：`hydra-android-v0.2.6-signed.apk`
  = versionName `0.2.6`；`addDnsServer`/`runRuleMode`/`rules.txt`/`vpnRuleModeDegraded` 标记**全无**

- **优先级：P1（结论可信度问题——「v0.2.6 可用」不能作为回归判据）**。

### P2-1 ｜ `DIRECT_CONNECT_TIMEOUT` 10s → 3s（proxy.rs:155）

- 可达性分析：安卓 `routing_engine = None` → `try_direct` 走 `routing::is_direct_target(target)`；
  该函数首行 `if !split_enabled() { return false; }`，而 `split_enabled()` 只读环境变量
  `HYDRA_SPLIT`（`routing.rs:190`），**全仓无任何安卓侧写入 `HYDRA_SPLIT` 的代码**
  （`hydra-android` 中 `HYDRA_SPLIT`/`set_var` 零命中）→ 恒 `false`；
  且 TUN 侧 target 恒为 `ip:port`，`host_part()` 对 IP 字面量返回 `None` → 再返 `false`。
- **结论：安卓数据面不可达，无影响。**（`try_direct` 在 `should_direct == false` 时立即返回
  `None`，不进入任何 connect/超时路径。）
- 优先级：P2（仅记录；桌面 SOCKS/HTTP 路径的行为变化需另评）。

### P2-2 ｜ v4 UDP 过滤新增 `is_unspecified()`（tun.rs:2219/2221）

- 仅 `allow_private == true` 分支行为变化；`allow_private = private_targets_allowed() || rule_mode`，
  安卓全局模式两者均假（`HYDRA_ALLOW_PRIVATE_TARGETS` 未设、`rule_engine = None`）
  → 与 v0.2.6 逐字等价（`private_like` 已含 `v4.octets()[0] == 0`）。
- 顺带发现**不对称**（仅 env/规则模式可达）：v4 `allow_private` 分支新增排除 unspecified，
  v6 `allow_private` 分支**未**排除 `is_unspecified()`（其 `private_like` 未参与该分支）
  → 建议后续对齐（与本次症状无关）。
- 优先级：P2。

### P3-1 ｜ v4 UDP 校验和为 0 时未改写 `0xFFFF`

- v6 已按 RFC 2460 改写；v4 未做（RFC 768 亦建议 0 → 0xFFFF，但 0 在 v4 语义为「未计算校验和」，
  主流栈接受）。触发概率 1/65536，影响可忽略。
- 优先级：P3（建议后续与 v6 对齐，顺手消除潜在兼容问题）。

### P3-2 ｜「DNS 联动伪兜底」在 tag 间净变化为零（中间态提示）

- `docs/review/10` 记载：「P2-5 伪兜底——已修复（本轮）：原实现仅改本函数局部
  `cfg.dns_via_proxy` 再打一条误导性 info」。该「伪兜底」由 **68f5611 引入**、由 **2d428ac 删除**
  → 在 `v0.2.6..v0.2.7` 的**净 diff 中不可见**（这也是「tag 间 diff ≠ 区间逐提交历史」的典型例）。
- **提示**：若现场或历史构建产物来自区间**中间态**（68f5611..2d428ac），其 `dns_via_proxy`
  局部改写会让 `run_stack` 内的豁免判定与实际不符——v0.2.7 tag 本身**干净**。
- 优先级：P3（历史构建溯源提示）。

## 5. 下一步真机诊断建议

### 5.1 三个判别实验（按性价比排序，均不需改代码）

1. **DNS 判别（最强，5 分钟）**：在设备上分别访问「字面 IP 的 HTTPS 站点」与「同一站点的域名」。
   - 例：浏览器打开 `https://223.5.5.5/`（阿里公共 DNS 的 IP，跳过 DNS 解析）——若可打开，
     而 `https://www.baidu.com/` 打不开 → **DNS 链路问题确证**（对应 P0-1）；
   - 若连字面 IP 也打不开 → 数据面/隧道问题，转 5.1.2。
   - 也可用 `adb shell` 直接发起：`adb shell "toybox wget -O /dev/null http://223.5.5.5"`（视设备工具而定）。
2. **VPN DNS 列表核查（确证 P0-1 的关键字）**：
   ```powershell
   adb logcat -c; adb logcat -v time -s Vpn:V ConnectivityService:V resolv:V netd:V DnsResolver:V DnsResolverService:V
   # 关键字：Setting DNS servers for network <N> to []      ← 空列表 = P0-1 确证
   adb shell dumpsys connectivity | Select-String -Pattern "VPN|Dns|LinkProperties"
   adb shell ip -br addr; adb shell ip route show table all; adb shell ip rule
   ```
   关注：`tun0` 是否 UP、`LinkProperties` 里 VPN 网络的 `DnsAddresses` 是否为空、
  是否出现 `Private DNS` 设置干扰。
3. **物理 vs 隧道对照**：`adb shell ping -c2 <物理网关>`（应通，不经 TUN）、
   `adb shell ping -c2 <节点 IP>`（ICMP 不被用户态栈接管，通**不代表**隧道正常），
   再用 5.1.1 的 IP 直连实验区分「隧道坏」还是「DNS 坏」。
