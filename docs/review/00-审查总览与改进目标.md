## 1. 最重要的一个发现：文档与实现严重脱节

三组审查**独立得出同一结论**（互相印证，可信度高）：

**README 与 RFC 宣称的核心能力，大部分是死代码，不在真实数据路径上。**

| README 宣称 | 代码实际 | 结论 |
|---|---|---|
| 多节点并行传输（分片/重组） | Splitter/Assembler 零引用，所有流量走单节点单流裸转发 | ❌ 未实现 |
| HMAC Token 认证 + nonce 防重放 | auth.rs 实现存在但**全仓库零调用**，节点完全无认证 | ❌ 未接线 |
| nonce 追踪防重放 | verify() 读出 nonce 从不存储，30s 窗口内可无限重放 | ❌ 不存在 |
| PBKDF2 密码哈希 | 实现正确但零调用 | ❌ 未接线 |
| IP 令牌桶限速 | 实为固定窗口计数器，且零调用 | ❌ 未接线 |
| 数据包校验和 | 真实路径无数据包结构（裸字节流），CRC32 是死代码 | ❌ 未接线 |
| QUIC 加密传输 | quinn + rustls，ALPN 双侧已设 | ✅ 属实 |
| 证书验证 | **完全跳过**（SkipVerification），服务端证书每次启动随机自签 | ❌ 无效 |
| 流量统计 | TrafficMonitor 记录方法零调用，GUI 显示恒 0 | ❌ 未接线 |
| 配置文件 default.toml / HYDRA_CONFIG | 无任何代码读取 | ❌ 不存在 |
| 自动测速 | speedtest 把 JSON 发给节点当"地址"，测的是失败应答 | ❌ 逻辑失效 |
| NAT 穿透 | 未接线 | ❌ 未实现 |

**真实数据流**（逐行验证）：

```
浏览器 → SOCKS5/HTTP 代理 → scheduler.get_best_node()（静态同分，恒选同一节点）
  → 连接池在该节点的一条 QUIC 连接上开 1 条流
  → 裸文本发送 "host:port"（无长度前缀）→ 节点单次 read 收地址
  → 节点侧 DNS → TCP connect → 双向 2×64KB 裸转发 → 目标网站
```

即：**Hydra 当前本质上是一个"单节点 QUIC 隧道代理"**。好消息是简单路径上没有乱序头阻塞；坏消息是项目的核心卖点（带宽聚合、故障恢复）目前不存在。

**建议的第一原则：宁缺勿假。** 先删除或明确标注全部花瓶代码，让文档只描述真实存在的行为，再按下面的路线图逐项把能力做成真的。

## 2. 三维度现状评级与目标

| 维度 | 现状评级 | 一句话结论 | 目标（Phase C 结束时） |
|---|---|---|---|
| **稳定性**（视频传输为重点） | **D** | 单节点无切换：节点一挂全部请求持续失败；错误被静默吞掉伪装成正常关闭；Windows 系统代理完全不生效且谎报成功 | 节点故障 30s 内自动切换且视频不中断；故障时下游收到明确错误而非静默截断 |
| **安全性** | **F** | 公网开放中继（任何人可白嫖/借刀攻击/SSRF）+ 客户端跳过证书校验（MITM 零门槛）+ 无资源上限（pre-auth DoS 到 OOM） | 无凭据扫描者无法转发任何字节；链路可抵御 MITM；节点可抵御资源耗尽 |
| **防追踪性** | **E** | 被动 DPI 解密 QUIC Initial（密钥公开可算）读出 ALPN="hydra" + SNI="localhost" 即 100% 识别；主动探测一跳拿自签证书 + 开放中继行为实锤 | 被动观察无法用单一规则区分于"浏览器访问普通 HTTPS 站点"；主动探测无法区分节点与普通 QUIC 网站 |

**正面确认**（三组共同验证无问题的点）：SOCKS5 ATYP 边界处理、share_link 解析无 panic、GUI 设置系统代理无命令注入（`Command::args` 传参）、代码中无硬编码密钥、时间窗数学与常量时间比较本身实现正确。

### P1（一个月内，共 14 项，摘要）

- 协议健壮性：目标地址无长度前缀 + 节点单次 read；节点侧故障被静默转成正常 FIN，播放器无法区分"播完"与"故障"（`handler.rs:140,159`）；无半关闭传播，select! 后另一方向任务脱管（稳定 P1-7/8/9）
- 超时体系不一致，客户端握手应答读取无超时——DNS 卡住时浏览器无限悬挂（`proxy.rs:694`，稳定 P1-10）
- 连接池写锁跨 await，全局串行化取流（`pool.rs:94-116`，稳定 P1-11）
- HTTP 明文代理用 `from_utf8_lossy` 重组报文，损坏二进制 body（稳定 P1-12）
- 客户端 "DNS 失败重试"协议节点侧从未实现，重试永远失败（稳定 P1-6）
- nonce 防重放不存在；限速器未接线且内存无界（安全 P1-1/2）
- 节点转发目标无过滤：`169.254.169.254` 云元数据 / 内网 / `127.0.0.1` 直达（安全 P1-3）
- `hex_decode` 对非法输入直接 panic（安全 P1-4）
- 本地代理可被配置绑 `0.0.0.0` 成 LAN 开放代理；HTTP 请求头无大小上限（安全 P1-5）
- 流量统计未接线，GUI 恒 0；GUI 首次点"启动代理"必然失败（稳定 P1-13/14）
- 日志泄露浏览 URL 与节点地址（安全 P2-2）
- 依赖陈旧：rustls 0.21 已 EOL、ring 0.16 双版本（安全 P2-7）

### P2（择期，摘要）

死代码群（Packet/checksum/crypto.rs/NatTraversal/serde_json 测速包）；Assembler 无超时无窗口（未来接线前必须修）；NAT 模块默认配置必然失败 + STUN 响应可伪造；配置体系整体失效；GUI 细节（UI 阻塞、退出竞态）；`"unknown".parse().unwrap()` 必然 panic 兜底；硬编码作者节点公网 IP 进了源码和 README；`hydra://` 分享链接格式独特性；rustls/quinn 客户端 TLS 指纹（无 GREASE，与 Chrome 差异大）。

## 4. 改进目标与路线图

### 总目标（用户三问的量化验收标准）

**稳定性（视频传输为重点）**
1. 杀掉当前节点，正在播放的视频在 30 秒内自动切换到备用节点且播放不中断（集成测试可复现验证）
2. 4K 视频跨境链路（RTT ≥ 150ms）连续播放 30 分钟不断流
3. 任何故障都让下游（浏览器/播放器）收到明确错误或可感知的连接重置，**绝不静默截断伪装成正常结束**
4. Windows 下 GUI 一键设置系统代理真实生效（注册表可验证），失败显式报错

**安全性**
1. 无凭据的扫描者对节点做任何探测，节点不转发任何字节、不回显可区分的错误信息
2. 节点在 10k 并发恶意连接下不 OOM、不拒绝正常认证用户（Semaphore 资源上限可测）
3. 客户端到节点链路可抵御中间人：删除 SkipVerification，证书指纹 pinning，MITM 实验无法解密或篡改

**防追踪性**
1. 被动 DPI 拿不到任何"单一规则即可精准识别"的特征（ALPN/SNI/端口/证书/心跳周期全部正常化）
2. 无凭据主动探测无法区分 Hydra 节点与"一个部署了普通 QUIC 网站的服务器"（认证失败静默关流）
3. 目标域名永不以明文离开本机（删除裸 53 回退；域名只在 QUIC 加密通道内传输）

### Phase A：止血（约 1 周，不加新特性，性价比最高的 8 件事）

| # | 动作 | 对应问题 | 预估工作量 |
|---|---|---|---|
| A1 | 节点接通首包认证（复用现有 auth.rs：PSK/HMAC token），**认证失败静默关流**，不回显 0x01/0x02 这类可区分错误码 | P0-1 + 防追踪 F5 | 1-2 天 |
| A2 | 节点资源上限：`Semaphore` 让 `max_connections` 真实生效 + 认证前字节配额（如 1KB 超限断流） | P0-6 | 0.5 天 |
| A3 | 证书体系：节点持久化自签证书（首次生成存盘）→ 客户端 SPKI SHA-256 指纹 pinning，删除 SkipVerification；**ALPN 改 "h3"、SNI 用真实域名、监听 443/UDP**（各一行改动，防追踪收益极大） | P0-2 + P0-7 | 1-2 天 |
| A4 | 故障切换闭环：取流失败 → 标记节点 Degraded → 立即换节点重试；`Transport::connect` 加超时；客户端握手应答读加 5s 超时 | P0-3、P1 超时项 | 1 天 |
| A5 | Windows 系统代理：写注册表 `Internet Settings` + `InternetSetOption` 刷新，失败显式报错（不再谎报） | P0-5 | 1 天 |
| A6 | 删除 DNS 裸 53 回退：客户端不解析域名，域名经 QUIC 加密通道交节点解析（同时修掉"重试协议未实现"的悬空逻辑） | P0-8 | 0.5 天 |
| A7 | 删除全部花瓶死代码（Packet/checksum/crypto.rs/NatTraversal/旧 Speedtest），README 如实重写 | P2 死代码群 | 0.5 天 |
| A8 | keepalive 去固定 10s 周期，加随机抖动；禁用会话恢复 ticket（阻断跨连接关联） | P0-7 部分 | 0.5 天 |

### Phase B：结构化加固（2-4 周）

1. **测速重写**：带超时的握手测延迟 + 定长下载测吞吐，结果写回 Scheduler，随 ProxyServer 常驻（P0-4）
2. **协议健壮性**：目标地址加 2 字节长度前缀 + 循环补读；节点侧错误用 reset(error_code) 传播而非静默 FIN；半关闭双向传播（P1 协议组）
3. **认证补强**：nonce 有界重放表；真正的令牌桶限速（LRU 有界）；`hex_decode` 返回 Result
4. **SSRF 防护**：节点目标地址黑名单（loopback/169.254/RFC1918），DNS 解析后复查防 rebinding
5. **日志脱敏** + 配置系统真实化（真正读取 default.toml）+ 本地代理默认绑 127.0.0.1
6. **依赖升级**：rustls 0.23（标准证书校验 + TLS exporter 通道绑定，认证与 TLS 会话绑定防转发穿透）
7. **测试体系重建**：修复 4 个遗留集成测试；新增故障切换测试、30 分钟长流模拟、Windows 系统代理集成测试、认证探测抵抗测试

### Phase C：能力兑现与长期演进（1-2 月）

1. **真多路径聚合**（RFC 核心卖点）：
   - 架构选择：**单 QUIC 连接多 stream 分发**，而非多五元组分发——后者本身就是比任何 Magic 字段都强的流量特征（同一逻辑流的包出现在多条五元组上）
   - 前置条件：乱序窗口 + 分片超时重传做对之前，**不为视频流量启用**（视频走单路径直通，下载/大文件走聚合）
2. **流量整形**：padding 策略、启动期预热突发平滑
3. **TLS 指纹**：现实约束——Rust 生态没有 uTLS 等价物，浏览器级指纹模拟是架构级约束。先做 GREASE 与套件序对齐，再评估换栈/改 rustls 的成本收益
4. BBR 拥塞控制、ACME 真证书自动化、配置面板

## 5. 执行原则（团队共识）

1. **宁缺勿假**：任何写进 README 的特性必须在真实数据路径上可验证；死代码直接删除而不是留着"以后用"
2. **视频优先**：每个稳定性改动都要问"4K 长视频场景下会怎样"；聚合能力与视频稳定性冲突时，视频优先（视频走直通，聚合只给下载）
3. **静默失败是最大敌人**：错误要么传播到下游，要么显式报错，绝不吞掉后谎报成功（Windows 系统代理谎报是本次审查最典型的反面教材）
4. **每个 Phase 结束跑一次三组复审**：本次的三份报告就是复审基线，逐条销号
