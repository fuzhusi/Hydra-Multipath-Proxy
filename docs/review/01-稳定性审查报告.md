## 2. 架构现状速写：一个 SOCKS5 请求的真实数据流

**结论（明确）："分片 + 多节点并行传输 + 乱序重组"没有在真实数据路径中使用。当前系统是一个"单节点、单 QUIC 流的裸中继代理"。带宽聚合这一核心卖点实际不存在。**

真实路径（每一跳都经代码验证）：

```
浏览器/SOCKS5 客户端
  │  TCP
  ▼
proxy.rs handle_socks5()                          ← 解析 SOCKS5（无认证，恒答 0x00 免认证）
  │
  ▼
scheduler.get_best_node()                         ← 所有节点以完全相同的静态默认值入库
  │                                                  (proxy.rs:50-59: bandwidth=100/latency=10/loss=0.01)
  │                                                  分数恒等 → 恒定选中同一个节点（非负载均衡）
  ▼
pool.get_stream_with_retry(node, 3)               ← 从该节点的某条 QUIC 连接上开 1 条双向流；
  │                                                  失败只重试同一节点 3 次，不换节点
  ▼
send.write_all("host:port")                       ← 裸文本、无长度前缀（proxy.rs:685）
  │
  ▼  QUIC（quinn 0.10，TLS 为 QUIC 内建；自定义 Packet/Chunk/校验和完全未用）
hydra-node handler.rs handle_stream()
  │  recv.read(&mut buf[256]) 单次读取收地址（handler.rs:52-57）
  │  优先 IPv4 DNS 解析（无超时，handler.rs:66）
  │  TCP connect 目标（60s 超时，handler.rs:99）
  ▼
双向 2×64KB 缓冲裸转发（tokio::join! 等两方向，handler.rs:132-170）
```

**不在路径上的模块（死代码 / 未启动）**：

| 模块 | README 声称 | 实际状态 |
|---|---|---|
| Splitter / Assembler（分片/重组） | ✅ Phase 2 | 零引用（仅测试文件 import），proxy.rs 无任何调用 |
| Scheduler 动态评分 | ✅ Phase 3 | `update_node_stats/update_node_status` 仅被 Speedtest 调用，而 Speedtest 从未被 `main.rs`/GUI 启动；调度分数永远静态同值 |
| Speedtest 自动测速 | ✅ Phase 3 | 从未启动；且实现本身失效（见 P0-3） |
| BufPool 缓冲池 | ✅ Phase 5 | 零引用；中继各自 `vec![0u8; 65536]` |
| AuthConfig / AuthToken（HMAC+PBKDF2） | ✅ Phase 5 | 未接线；节点接受任意连接（开放中继） |
| Crypto（CHACHA20_POLY1305） | ✅ 加密通信 | 零引用；且每次 `new()` 随机密钥，即使接线也无法互解（加密实际仅靠 QUIC 内建 TLS） |
| NAT 穿透（STUN+打洞） | ✅ Phase 6 | 零引用 |
| TrafficMonitor 流量统计 | ✅ Phase 6 | `record_sent/record_received/connection_opened` 全工程零调用 → GUI 流量统计永远显示 0 |
| SessionManager / Session | ✅ 协议核心 | 零引用 |
| Packet（chunk_id/offset/checksum） | ✅ 协议核心 | 仅 Speedtest 和测试发过 JSON 序列化的 Packet，节点按"目标地址"解析，从未按协议解析 |
| config/default.toml / HYDRA_CONFIG | ✅ 配置文件 | 无任何代码读取（无 toml/config 依赖），全部硬编码默认值 |

**对视频传输的直接影响**：
- 好消息：当前路径反而没有分片乱序重组带来的头阻塞/丢片卡死风险——数据是 QUIC 单流有序字节流。
- 坏消息：没有带宽聚合、没有节点级冗余；单节点故障 = 视频流直接断且不可恢复；单节点带宽 = 视频可用带宽上限。

## 3. 问题清单

严重度定义：P0 = 核心 功能缺失/必然失效或必然的视频中断；P1 = 显著稳定性/正确性缺陷；P2 = 边界条件/质量问题。

### P0-1 多路径分片聚合未实现，真实路径为单节点裸转发
- 【位置】`hydra-client/src/proxy.rs:647-772`（SOCKS5）、`proxy.rs:222-338`（HTTP）、`hydra-node/src/handler.rs:47-178`；`splitter.rs`、`assembler.rs` 全工程零引用
- 【描述】如第 2 节所述，每个 SOCKS5/HTTP 连接只选一个节点、开一条 QUIC 流裸转发。RFC 第 7 节的 Chunk1→Node A / Chunk2→Node B 模式、Packet 协议头（magic/session/chunk/offset/checksum）均未参与数据面。
- 【视频影响】无带宽聚合（多节点带宽无法叠加）；也无多路径冗余。1080p/4K 高码率场景单节点带宽即天花板。
- 【建议】短期先承认现状（修正 README 与 GUI 文案）；若要实现真多路径，见第 7 节长期目标——必须以"字节流序号 + 会话层重传 + 乱序窗口超时"完整设计，否则宁可不启用。

### P0-2 调度器无反馈、无故障切换：节点挂掉后所有请求持续失败
- 【位置】`hydra-client/src/proxy.rs:647`（仅调 `get_best_node`，从不更新调度器）；`scheduler.rs:45-75`（更新方法无人调用）；`pool.rs:139-161`（`get_stream_with_retry` 只重试同一地址）；`proxy.rs:50-59`（所有节点同一静态分数）
- 【描述】请求失败后：① 不把失败节点标记 Offline/Degraded；② 不尝试其他节点。速度上 `get_stream_with_retry` 对同一死节点重试 3 次（每次间隔 100ms，连接超时 10s）后直接把 502/SOCKS 错误回给浏览器。
- 【视频影响】观看视频中节点掉线 → 该节点上所有视频连接立即中断；之后**新开的**视频连接仍会被调度到同一死节点，直到用户手动重启代理。这正是"故障自动恢复"声称所覆盖的场景，实际不存在。
- 【建议】在 `handle_socks5/handle_http_connect` 的取流失败分支调用 `scheduler.mark_node_offline(node)` 并对 `get_online_nodes()` 逐个重试一次；再配合 P0-3 修复的周期健康检查恢复节点。

### P0-3 Speedtest 测量逻辑失效，故障检测形同虚设（实测证实）
- 【位置】`hydra-client/src/speedtest.rs:74-111`；`transport.rs:66-79`（`connect` 无超时）；`hydra-node/src/handler.rs:61-93`
- 【描述】三重失效叠加：
  1. **测量内容错误**：向节点发送 JSON 序列化的 Packet 当作"目标地址"，节点按地址解析失败→回 `[0x02,0x00]` 后立即关闭流。quinn 0.10 中 `SendStream::drop` 会静默 `finish()`（quinn-0.10.2/src/send_stream.rs:263-284），因此客户端 `read_to_end` 得到的是**正常 FIN**——测量"成功"， latency=整个 DNS 失败往返，`bandwidth=1000/latency` 是伪造值，loss_rate 恒 0、load 恒 0.5。它既测不了带宽也区分不了节点健康度。
  2. **死节点检测不出**：`Transport::connect` 无超时，QUIC 握手按 idle timeout 60s 才失败；实测 `test_failover` 中节点进程被杀 15 秒后状态仍 Online，断言 `Offline` 失败。
  3. **根本没有运行**：`main.rs` 与 GUI 均未创建 Speedtest。GUI 的 30 秒健康检查（`hydra-client-gui/src/main.rs:578-587`）只更新自己的 UI 状态表，**不写入 ProxyServer 内部的 Scheduler**——检测与调度完全脱节。
- 【实测】`cargo test -p hydra-client --test test_failover` → FAILED（node1 停机后仍 Online）。
- 【视频影响】"故障检测与恢复"整体不成立；即使未来接线，当前 speedtest 也无法提供正确的评分输入。
- 【建议】重写 measure：带超时（3-5s）的握手测延迟 + 定长下载（如 1MB）测吞吐；失败立即（首次超时即 Degraded，连续 2 次 Offline）写回 Scheduler；把 GUI 健康检查结果也接进 Scheduler；并在 ProxyServer 启动时开启周期检测任务。

### P0-4 （Windows）GUI 系统代理在 Windows 上完全不生效，且日志谎报成功
- 【位置】`hydra-client-gui/src/main.rs:374-432`（set_system_proxy）、`434-464`（remove_system_proxy_static）、`363`（日志"已设置系统全局代理"）
- 【描述】系统代理只实现了 GNOME（gsettings）与 KDE（kwriteconfig/dbus-send）。Windows 上这些命令不存在，`Command::output()` 的错误被 `let _ =` 吞掉，随后日志输出"已设置系统全局代理"。没有任何 Windows 注册表（`HKCU\...\Internet Settings`）或 `InternetSetOption` 调用。环境变量只影响本进程。
- 【视频/稳定性影响】用户以为在走代理，实际流量直连（对翻墙场景是隐私事故）；同时造成"代理没生效"的稳定性错觉排查。
- 【建议】实现 Windows 分支：写注册表 `ProxyEnable/ProxyServer/ProxyOverride` + 调用 `wininet::InternetSetOption(INTERNET_OPTION_SETTINGS_CHANGED/REFRESH)`；按 `cfg!(target_os)` 分派；设置失败要报错而不是打成功日志。

### P0-5 节点是开放中继：认证机制未接线
- 【位置】`hydra-node/src/server.rs:14-48`（无客户端认证，`with_no_client_auth`）、`handler.rs:21-45`（accept 任意流）；`hydra-protocol/src/auth.rs` 全模块零引用（生产路径）
- 【描述】节点监听 `0.0.0.0:8080`，无 Token/PSK/用户名密码校验、无速率限制、无连接数上限（`NodeConfig.max_connections` 从未使用）。README 声称的 HMAC Token + PBKDF2 + 令牌桶均只在库里，未参与任何握手。另：`auth.rs:197-202 hex_decode` 对非法输入 `unwrap()` panic；README 声称的 "Nonce 追踪防重放" 在 `AuthToken::verify` 中不存在。
- 【视频影响】公网节点上线后会被扫描滥用（免费中继/刷流量），导致带宽被挤占、连接数暴增，视频卡顿与节点不稳定。
- 【建议】在 QUIC 连接建立后、首个流之前强制认证帧（可直接用现成 `AuthToken`），失败即 `connection.close()`；接上 `AuthRateLimiter`（同时修复其 HashMap 只增不减问题）；实现 max_connections。

### P1-6 客户端"DNS 失败重试"协议在节点侧从未实现，重试永远失败
- 【位置】`hydra-client/src/proxy.rs:467-522`（`handle_dns_retry`）；`hydra-node/src/handler.rs:76-91`（写完 `[0x02,0x00]` 立即 `return Err`，流已关闭）
- 【描述】协议设计是 0x02 → 客户端本地解析 → 回发 IP → 节点重试。但节点两条 DNS 失败分支都在写 0x02 后直接返回，SendStream 被丢弃（触发 FIN）。客户端随后写入的 IP 永远无人读取，`recv.read` 返回 None → `handle_dns_retry` 恒 false。
- 【视频影响】节点侧 DNS 故障（容器内无 DNS、上游 DNS 抖动）时，本可由客户端解析挽救的域名全部失败；视频站 CDN 域名解析失败直接表现为视频无法加载。
- 【建议】节点收到 0x02 后不关流，继续 `recv.read` 等待客户端回发的 IP 再连接；或干脆删掉客户端重试逻辑、改为客户端默认先本地解析（见 P1-7 一并理顺）。

### P1-7 目标地址无长度前缀 + 节点单次 read + SOCKS5 缓冲区偏小
- 【位置】`hydra-client/src/proxy.rs:685`（`write_all(地址字符串)`）；`hydra-node/src/handler.rs:52-57`（一次 `recv.read(&mut buf[256])`）；`proxy.rs:533`（SOCKS5 请求缓冲 256 字节）
- 【描述】① 无长度前缀/分隔符，靠"客户端等 2 字节应答再发数据"的锁步偶然成立；若地址跨 QUIC 包且尾包丢amendment，`read` 会先返回前缀，节点把截断地址拿去解析（可能解析出**错误端口**）或失败。② 最长 SOCKS5 域名请求为 4+1+255+2=262 字节 > 256 缓冲，超长域名必失败。③ SOCKS5 greeting/request 均只读一次，无循环补读，TCP 分段到达即解析失败。
- 【视频影响】低概率但真实的"连错端口/连接失败"；CDN 长域名（部分广告/统计域名>249 字节）必然失败并产生错误重试风暴。
- 【建议】改为 `[2 字节长度][地址]`；节点循环 read 直到收满长度声明；SOCKS5 缓冲升到 1024 并补读循环。

### P1-8 节点侧故障被静默转换为正常关闭（FIN），错误不传播
- 【位置】`hydra-node/src/handler.rs:140/159`（`write_all` 失败即 `break`，随后流被 drop）；quinn-0.10.2 `send_stream.rs:263-284`（Drop 未 finish 时自动 `finish()`）
- 【描述】节点↔目标 TCP 中途 RST/写失败时，节点既不向客户端发任何错误码，也不主动 reset 流——quinn 的 Drop 语义把它变成优雅 FIN。客户端中继收到 `Ok(None)` 后正常关闭本地 TCP。
- 【视频影响】目标服务器中断视频流时，浏览器看到的是"服务器正常结束连接"（HTTPS 下 TLS 记录被截断可能报错，但代理层完全无感知、无日志区分）。故障被吞掉：无法区分"播完了"和"节点/目标出问题了"，播放器重连策略与排查都被误导。
- 【建议】节点中继出错时调用 `send.reset(error_code)`（或 `connection.close` with application error code），客户端把 QUIC ApplicationClosed/StreamReset 映射为对本地 TCP 的 RST，同时打点统计。

### P1-9 无半关闭传播；select! 返回后另一方向任务脱管
- 【位置】`hydra-client/src/proxy.rs:765-768`（SOCKS5）、`proxy.rs:456-459`（CONNECT）、`proxy.rs:331-334`（HTTP）：`tokio::select!` 任一方向结束即返回；未对 QUIC 侧调用 `send.finish()`；另一方向任务 JoinHandle 被丢弃（detached 继续跑）。节点侧 `handler.rs:170` 用 `tokio::join!`，半关闭后节点任务持续悬挂等待另一方向。
- 【描述】本地客户端发 FIN（如 HTTP/1.1 请求发完即半关）不会转发为 QUIC FIN → 节点不会对目标 TCP 发 FIN → 目标服务器一直等请求。依赖半关闭语义的协议（部分上传 API、HTTP pipelining）行为错误；select 返回后下载方向成为无人监管的 detached 任务（通常会在对端关闭后退场，但不受生命周期管理，`Connection completed` 日志提前打印）。
- 【视频影响】视频主要用 HTTPS CONNECT，影响有限；但在长连接上传/双工场景会造成节点任务积压（长时间运行内存/任务数缓慢上涨）。
- 【建议】`client_to_node` 结束（读到 0）时对 QUIC `send` 调 `finish().await`；节点侧收到 recv FIN 后对 `target_write` 调 `shutdown()`；两方向用 `select` + 对 remaining 方向 `abort()` 收尾。

### P1-10 超时体系不一致，客户端握手读无超时
- 【位置】`proxy.rs:694`（等节点 2 字节应答无超时）；`handler.rs:66`（`lookup_host` 无超时）；`handler.rs:99`（TCP connect 60s）；`transport.rs:34`（QUIC idle 60s/keepalive 10s）；`pool.rs:63`（connect 10s）；`transport.rs:66-79`（connect 无超时）；GUI `test_connection` 3s
- 【描述】同一件事（"连上节点"）有 4 种超时取值；最关键的浏览器体验路径上——SOCKS5/CONNECT 握手等节点应答——完全没有超时。节点 DNS 卡住（Windows DNS 服务挂起很常见）或目标 connect 挂满 60s 时，浏览器侧请求无限悬挂。
- 【视频影响】起播阶段白屏转圈无错误提示；批量失败请求悬挂积累任务与连接。
- 【建议】握手应答统一 5s 超时（超时回 SOCKS5 TTL exceeded）；节点 `lookup_host` 包 `tokio::time::timeout(5s)`；TCP connect 降到 10s；`Transport::connect` 增加超时参数供 speedtest/健康检查复用。

### P1-11 连接池写锁跨 await，全局串行化取流
- 【位置】`pool.rs:94-116`：`get_stream` 在持有 `pools.write()` 的情况下 `pc.open_bi().await`
- 【描述】QUIC 流打开等待（对端流控满/连接繁忙/丢包恢复期）会**阻塞所有其他节点、所有其他请求**的取流操作（同一把写锁）。这是视频高并发场景下系统性的卡顿源：一个繁忙节点能拖死整体。
- 【建议】锁内只做"取出候选连接"并克隆 `Connection`（quinn::Connection 是廉价 Arc 句柄），锁外 `open_bi`，失败再回池清理；或直接按 addr 分桶加锁。

### P1-12 HTTP 明文代理用 from_utf8_lossy 重组报文，损坏二进制 body
- 【位置】`proxy.rs:147`、`proxy.rs:162`（`String::from_utf8_lossy` 拼接请求）；`proxy.rs:288`（把含 body 的重组串整体转发）
- 【描述】首读缓冲中若混入 POST body 字节（或任何非 UTF-8 序列），lossy 转换写入 U+FFFD 替换符后再原样转发 → 请求体被破坏、Content-Length 失配。
- 【视频影响】部分视频站 HLS 索引/上报走明文 HTTP，会偶发请求损坏。
- 【建议】全程用 `Vec<u8>` + 只对首行/头解析做 `str::from_utf8`（失败即 400）；头尾分界后 body 字节直接透传。

### P1-13 流量统计未接线，GUI 显示恒 0
- 【位置】`proxy.rs:17`（`traffic_monitor` 字段仅存储未使用）；`traffic.rs:136-158`（record_* 零调用，grep 证实）；GUI `main.rs:798-809`

### P1-14 GUI 首次点"启动代理"必然失败（读取过期的健康检查状态）

### P1-15 证书校验跳过（MITM 风险）

### P2-16 `"unknown".parse::<SocketAddr>().unwrap()` 必然 panic 的兜底

### P2-17 auth.rs 若接线后的隐患
- 【位置】`auth.rs:197-202`（hex_decode 非法输入 panic）；`auth.rs:117-147`（RateLimiter HashMap 的 IP 键永不删除，长期运行内存增长）；`AuthToken::verify` 无 nonce 重放表（README 声称有）

### P2-18 Assembler（若未来接线）无超时、无窗口
- 【位置】`assembler.rs:26-59`
- 【描述】`try_assemble` 要求 offset 严格连续：丢一个分片则 `expected_offset` 永久卡死，`chunks` HashMap 无限增长（长期内存泄漏 + 永久头阻塞）。`buffer` 字段从未使用。当前未接线所以只是潜在雷，但这是未来实现多路径时最容易踩的坑。

### P2-19 GUI 交互阻塞与退出竞态
- 【位置】`main.rs:719`（单节点"测试"按钮 `rx.recv_timeout(5s)` 阻塞 UI 线程 5 秒）；`main.rs:470-488`（stop_proxy 在 UI 线程 `join` 代理线程，Runtime drop 等待任务期间 UI 卡死）；`main.rs:308-315`（先 bind 成功再 drop 再由 proxy.start() 重新 bind，存在端口被抢竞态窗口）

### P2-20 资源上限缺失
- 【位置】`hydra-node/src/server.rs:50-63`（accept 无上限）、`handler.rs:132-167`（每流两个 64KB 缓冲 + 两任务，无总闸）；`NodeConfig.max_connections/buffer_size` 从未使用

### P2-21 NAT 模块未接线且实现有误

### P2-22 配置系统不存在

## 6. 稳定性改进目标

### 短期（1 周内，不加新特性，先把现有路径做稳）
1. **故障切换**：取流/握手失败 → 标记节点 Degraded/Offline → 立即换节点重试一次（P0-2）。
2. **超时闭环**：握手应答 5s、节点 DNS 5s、TCP connect 10s、Transport::connect 增加超时（P1-10）。
3. **协议加固**：地址加 2 字节长度前缀；节点循环补读；SOCKS5 缓冲 1024 + 补读循环（P1-7）。
4. **Windows 系统代理**：注册表实现 + 失败显式报错（P0-4/W1）。
5. **修坏测试**：让 test_client/test_failover 匹配当前协议并通过；CI 加 windows-latest。
6. 错误不再吞掉：节点侧中继错误改 `reset(error_code)` 并在客户端映射为 RST + 日志（P1-8）。
7. 半关闭传播：client_to_node 读到 EOF → `send.finish()`；节点 recv FIN → `target_write.shutdown()`（P1-9）。

### 中期（2-4 周）
1. 真实测速与健康检查：定长下载测吞吐、超时快速摘除、结果写回 Scheduler、随 ProxyServer 常驻（P0-3）。
2. 认证接线：QUIC 连接级 Token 认证 + 速率限制 + max_connections（P0-5、P2-17、P2-20）。
3. 流量统计接线 + GUI 数值真实化；池锁拆分消除跨节点串行化（P1-13、P1-11）。
4. DNS 策略统一：客户端默认本地解析（可带远端解析回退），删除永远失败的 0x02 重试或将其实现完整（P1-6）。
5. 观测性：连接级日志结构化（node/target/bytes/duration/error_code），区分"正常关"与"故障关"。

### 长期（1-2 月，若要做真"多路径"）
1. **会话层多路径设计**（对应 RFC）：一条逻辑会话 = 每节点一条 QUIC 连接 + 流内序号；发送端按调度权重分配字节块；接收端 Assembler 带**乱序窗口 + 分片超时重传 + 缓冲上限**；任一路径死亡时会话内将其字节块在其余路径补传（这才是"视频不中断"的正确姿势）。在此之前**不建议**在视频场景启用分片——单路径 QUIC 的稳定性优于有洞的多路径。
2. 拥塞控制可选项 BBR（quinn 支持自定义 congestion control）。
3. 配置持久化 + 系统托盘 + Windows 自启动（GUI 工程化）。
4. 修正 README：把未接线模块从"已实现"清单移到"规划中"，当前文档可信度为负资产。

## 附：QUIC 参数评估（视频吞吐视角）

- 当前设置：客户端/节点 idle timeout 60s、keep-alive 10s（transport.rs:33-36、server.rs:42-45）；未调流控窗口。
- quinn-proto 0.10.6 默认：`stream_receive_window = 12.5MB/s × 100ms ≈ 1.19 MiB`，`send_window ≈ 9.5 MiB`（quinn-proto-0.10.6/src/config.rs:315-327）。
- 含义：单流吞吐上限 ≈ 1.19MiB/RTT。50ms RTT ≈ 200Mbps、150ms RTT ≈ 66Mbps、200ms RTT ≈ 50Mbps。1080p（5-10Mbps）无忧；4K 高码率（25-50Mbps+）在 150ms+ 的跨境链路上会触顶。
- 建议（中期）：`stream_receive_window` 提至 4-8 MiB、`receive_window` 显式设 16-32 MiB，配合中继缓冲 64KB→128KB；keep-alive 10s + idle 60s 对"暂停视频再继续"是安全的，不会掐断长视频。
