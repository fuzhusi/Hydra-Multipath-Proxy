## 三优先级对应

- **性能**：批次 B 全部 + B0 基准（优化以数据说话）
- **安全**：缓冲复用引入的所有权/生命周期风险 → 所有权单测覆盖（B1/B3 强制）；tracing 字段化顺带解决日志脱敏一致性（字段级脱敏函数单点化）
- **美观**：日志页级别筛选已有；新增级别下拉/持久化开关沿用既有设置行样式（不新造组件）

### B5 评估：UDP 下行写聚合（只评估，未实现）

**Windows（wintun）：无可行收益，否决。** 实测依据（本机 registry 源码核查，
tun2 4.0.0 → wintun-bindings 0.7.40）：`Session::send(&[u8])` = `WintunAllocateSendPacket`
（ring 环上按包长分配槽位）+ `WintunSendPacket`（环写指针前移）——wintun 驱动
API **本身就是每包一槽、无多包 batch 入口**（ring 设计即逐包复制，发送无 syscall，
纯用户态 memcpy）；聚合多包不会减少任何内核调用，只增加一层数组管理开销。
预估收益 ≈ 0，维护成本 > 0 → 不做。

**Linux（/dev/net/tun）：单次 write 只写一个包，多包聚合需 GSO（IFF_VNET_HDR +
virtio_net_hdr 大包卸载），改变 MTU/卸载语义且需节点侧配合实测**——与评审
「Linux 需 GSO 先测」一致，当前数据面瓶颈不在 write 次数（B0/B 基准均为每包
构造侧，ns/op 级），列为远期实测项，本轮不做。

### B6 评估：泵缓冲池化（只评估，未实现）

内存模型（代码现状实测）：`UdpDirectNat::MAX_SESSIONS = 512`，每会话回包泵持
1 × 65535B recv buf（B1 后泵再持 1 块复用 scratch，稳态自动收敛到峰值包长，
典型 ≤2KB）→ 全局稳态上限 512 × 64KB ≈ **32MB**（recv buf 主导）+ scratch 实际
占用（B1 后不再固定 64KB，按需增长，典型 DNS/QUIC 流量 < 2KB/会话 ≈ 1MB）。

结论：池化只省「每会话一次」的 recv buf 分配（**非每包**，B0/B1 优化后热路径
已零分配），对性能无收益，纯内存项；32MB 上限在桌面可接受，Android 上限由
VpnService 路径决定不经过此代码。若未来实测 UDP 会话常驻数显著超 512 或
内存预算收紧，优先把 recv buf 尺寸改为 `max(mtu, jumbo 需求)` 按需分配
（一行改动省 ~97%），池化结构本身仍不值得引入（跨 await 生命周期风险）。
⏸ 保留为观测项：建议 GUI 日志/流量页暴露 UDP 会话数峰值后再复核。
