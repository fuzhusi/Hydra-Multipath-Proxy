## 一、直连技术路线（方案 A：源地址绑定）

### 1.1 Windows 强主机模型下 bind+connect 的行为（基本成立，但表述需修正）

**设计主张**（方案 v1:21）：「绑定了源地址的 socket 按该接口路由出网，不进 TUN」。

外部事实核对：Windows Vista+ 默认强主机发送模型——源地址与路由查找**都约束在发送接口上**（Microsoft 文档 *Strong and Weak Host Models*；`GetBestRoute2` 可显式按接口查询）。对已 `bind` 物理网卡 IP 的 socket：

- 路由查找仍是全局最长前缀匹配，但**候选路由被限定到源地址所属接口**（强主机 send 语义）；
- TUN 的接管路由是 `0.0.0.0/1` + `128.0.0.0/1` 指向 TUN 地址（tun.rs:218-227，metric 1），物理默认路由 `/0` 仍在表中且属于物理接口；
- 因此 bound socket 的查找被约束到物理接口后，`/0` 物理默认路由胜出，包从物理口出——**不进 TUN 的结论正确**。这正是 sing-box `bind_interface` / Clash `interface-name` 在 Windows 上的同款原理。

两点必须写进设计的边界：

1. **「源地址选择 vs 路由查找顺序」的设计文档表述不准确**。不是「绑定源地址后按该接口路由」一句话了事，而是：源地址 bind → 强主机模型把路由查找约束到该接口 → 该接口上的最优路由（物理 `/0`）生效。弱主机模型（极少数场景被改为 weak）下此保证不成立。
2. **bind(IP) 不锁定接口 index，bind(interface) 才锁定**。DHCP 续租换 IP、多网卡多 IP 时，按 IP 绑定存在失效窗口。Windows 上更稳的做法是 `IP_UNICAST_IF` 指定接口 index（sing-box 采用），`direct_bind_ip: Option<IpAddr>`（v1:25）可保留，但建议预留接口 index 字段或注明 v1 接受 IP 语义的局限。

**待验证 ①**：真机验证 bind(物理IP)+connect 在 `/1` 接管路由存在时确实从物理口出网（含 metric 1 的 `/1` 与物理 `/0` 并存场景）。

### 1.2 IPv6 直连的源绑定（设计缺口）

- 现状 TUN 已默认接管 IPv6 TCP（`ipv6_enabled` 默认 true，tun.rs:70/96；`::/1`+`8000::/1` 接管，tun.rs:348-358）。规则模式下 v6 流量同样要分流，`direct_bind_ip: Option<IpAddr>` **单值不够**——v4 与 v6 各需一个物理源地址（`direct_bind_ip` + `direct_bind_ip6`）。
- v6 侧 bind 源地址同理受强主机约束，但首选 `IPV6_UNICAST_IF`；且需处理「物理口无全局 v6 地址」场景（v6-only 抑制/临时地址随机化——Windows 临时隐私地址会周期轮换，bind 到已废弃的临时地址会失败，回退语义必须覆盖）。
- 设计 §3.1 声称 IP-CIDR 规则「含 v6 段」，但 §3.3 GeoIP-CN 表只字未提 v6（APNIC delegated 派生的 CN 表以 v4 为主）。**v6 目标的 GeoIP 判定策略缺失**，见 §四 R6。

### 1.3 回退语义的完整性（必须扩展）

设计 v1:27 只写了「绑定失败（取不到物理 IP/接口变化）→ 回退走节点」。语义不完整：

| 失败点 | 设计覆盖 | 应有语义 |
|---|---|---|
| 取不到物理 IP / bind 失败 | ✅ | 回退节点 |
| **connect 失败/超时**（物理口无网、防火墙 REJECT、IP 刚变化） | ❌ 未写 | **同样回退节点** |
| connect 成功后中断 | — | 正常断流，不回退（与代理通道一致） |

现状已有正确先例可循：SOCKS/HTTP 路径的 `try_direct`（proxy.rs:1324-1366）对直连失败与超时均回退节点路径。复用该语义即可，但注意：

- 直连 connect 必须有**独立的短超时**（`try_direct` 用 `DIRECT_CONNECT_TIMEOUT`，proxy.rs:1332），不能复用 `OPEN_TIMEOUT` 15s（tun.rs:1042）——否则 CN 站点在直连环境异常时要先白等 15s 才回退节点，体验劣化远大于不分流。
- `spawn_up_task`（tun.rs:1083-1105）对 opener 失败统一回 RST；直连失败若在 opener 包装层内部消化（direct 失败→再试 proxy opener），则 spawn_up_task 零改动，这是推荐的接线方式（见 §三.3）。

**待验证 ②**：直连 connect 被无提示丢包（防火墙 DROP）场景的回退时延实测，确认短超时取值。

## 二、规则模型

### 2.1 v1 裁剪为 IP-CIDR + GeoIP + 端口：正确，但需处理与既有 Exec2 分流的关系

TUN 用户态栈天然只拿得到目的 IP（v1:48 自认；tun.rs:2254-2257 从 smoltcp local_endpoint 提取 `ip:port` 字符串），域名/SNI 规则需嗅探，v1 裁剪正确。

但现状代码已有**另一套分流**：SOCKS/HTTP 路径的 Exec2 CN 域名分流（proxy.rs:892-894、964-965、1285-1289，`routing::is_direct_target` 域名表 + `try_direct`）。TUN 规则引擎（routing_rules.rs，GeoIP）与 SOCKS 分流（域名表）将长期并存、口径不一（同一目标在两条入口可能走向不同）。设计 §五 模块落点未提 `routing` 模块，建议至少注明关系（v1 允许两套并存，v1.1 统一），避免后续维护者困惑。

### 2.2 「DNS 经节点解析导致 GeoIP 判定偏移」的真实影响面（核心疑问，影响 v1 可用性）

这是本次评审最重要的实质性风险，设计 v1:49/99 以「如实写入文档」带过，**低估了影响面**：

- 机制：`dns_via_proxy` 默认 **true**（tun.rs:84/102），系统 DNS 经节点（境外）解析。国内头部站点（电商/视频/门户）几乎全部走 CDN，权威 DNS 按解析发起地（= 境外节点）返回**海外 CDN 边缘节点 IP**。
- 关键事实：这些海外边缘 IP 归属于 CDN 厂商的**海外段**（阿里云/腾讯云 CDN 海外 PoP 等），**不在 APNIC delegated 的 CN 分配内**——即不在 GeoIP-CN 表中。也就是说偏移不是「少数边缘 case」，而是**国内 CDN 化流量的主体会被判为非 CN → 走节点**。
- 影响分层：
  - 非 CDN 的国内站（固定 CN 服务器 IP）：判定正确，直连生效 ✅
  - 国内 CDN 站（头部大站主体）：判非 CN → 走节点，功能可用但「绕道境外再回国」，延迟/带宽双输，**分流的带宽节省目标大打折扣** ⚠️
  - 反向风险：个别场景节点侧解析返回的 CDN IP 恰在 CN 表内（厂商国内段），直连一个「为海外用户优化的国内入口」，可能比走节点更慢 ❌（低概率，但要写进已知缺陷）
- **设计遗漏的联动项（比文档声明更重要）**：tun.rs 已有现成开关 `HYDRA_TUN_DNS_DIRECT=1` 恢复 DNS 直连（tun.rs:80-84），DNS 直连解析后国内域名拿到真 CN CDN IP，GeoIP 判定即恢复准确。规则模式下默认策略应**联动修改**（规则模式 → 建议 DNS 直连，或在 GUI 规则分流开启时提示该权衡），而不是维持 `dns_via_proxy=true` 现状让分流静默失效。设计全文未出现 `dns_via_proxy`/`HYDRA_TUN_DNS_DIRECT` 字样，这是 v1 文档最需要补的一段。
- 现状代码另有矛盾点需澄清：`detect_dns_servers` 探测的系统 DNS 在 `dns_via_proxy=false` 时才进豁免清单直出物理网卡（tun.rs:80-84）；规则模式下无论哪种取值，DNS 的 UDP 包都会流经 `try_forward_udp`（tun.rs:2041/2064）——**DNS 分流接入点见 §四 R1**。

**待验证 ③**：真机采样 top 100 国内域名：分别在 DNS 直连 / DNS 经节点两种配置下解析，统计结果 IP 落在 CN 表外的比例，量化偏移面，据此决定 v1 默认值。

### 2.3 端口规则示例有误导

v1:37 示例 `DST-PORT,443,PROXY`——默认策略已是 PROXY（v1:45），此规则是冗余的；端口规则的实际价值是 **DIRECT 例外**（如对某非标端口放行直连）。建议示例改为 `DST-PORT,x,DIRECT` 形态，并在文档注明端口规则仅作次要例外手段（设计自己也是这么定位的，示例却反着写）。

## 三、性能

### 3.1 GeoIP 二分成本：可忽略，结论成立

排序 u32 段数组二分 O(log n)：CN 聚合段数千量级 → 每次查询 ~12 次比较，每连接建连时一次，相对一条 TCP 连接的 TLS+代理握手成本完全可忽略（v1:59 的判断正确）。「缓存到流上下文」其实多余——每连接只判一次，缓存的唯一价值是 opener 闭包内把判定结果随流携带，注意别做成跨连接全局 LRU（无必要且引入锁）。

自定义规则文件的线性扫描才是潜在热点：规则多时（数百条 CIDR）应同样构建排序段数组二分，仅精确参数/端口规则线性——建议在 routing_rules.rs 设计里写明。

### 3.2 嵌入 50-100KB：取舍正确

`include_bytes!` 零运行时加载成本，100KB 对二进制体积增量 <1%，离线可用免下载依赖。v4 u32 段数组无压缩也远小于此估计（APNIC CN 聚合后通常 1-2 万段 ≈ 数十 KB 上限），50-100KB 偏保守但无害。R8/CI 生成路径稳定性（v1:100）已识别。唯一注意：`include_bytes!` 相对路径在 workspace 外的 crate 构建时的路径解析要在 CI 固定（设计已提）。

### 3.3 spawn_up_task 前插入点：位置正确，实现建议「包装 opener」+ 用 SocketAddr 而非字符串

- 插入时机正确：`spawn_up_task` 在流进入 Established 后才派生（tun.rs:2311-2329，06-P2-8 优化），规则判定放在此处**不会**为端口扫描 SYN 付出任何成本。
- **零拷贝可达成，但设计未写明关键点**：判定需要的 `{dst_ip, dst_port}` 在 `step` 的接受分支里已有原始 `SocketAddr` 形态（tun.rs:2237-2257），**不应**对 `flow.target` 字符串（v6 为 `[..]:port` 格式，tun.rs:2256）做二次 parse——直接把 `IpAddr`+port 传给规则引擎，零新增分配。建议设计 §五 明确「判定输入为 SocketAddr，target 字符串仅供日志」。
- 接线方式：`ChannelOpener` 是 `Arc<dyn Fn(String) -> OpenFuture>`（channel.rs:24，proxy.rs:388-430 构造）。最小侵入做法是在 `run_stack` 入口（tun.rs:1846 处）把代理 opener 包一层规则 opener：闭包内判定 → DIRECT 时走 `direct_opener`、失败回退代理 opener；`step`/`spawn_up_task`/`Flow` 结构零改动。设计 §五 说「hydra-client/src/tun.rs：spawn_up_task 前判定分流」，建议修订为「run_stack 入口包装 opener」表述，与现有结构吻合。
- 中继泵（FlowMsg::Link 之后的 reader/writer 任务，tun.rs:2332-2434）对 `ProxyDuplex` 来源无感知，直连通道包成 `ProxyDuplex` 后确实零改动（v1:24 判断正确）。

## 四、遗漏项与逐条建议

### R1（P0）UDP 分流完全缺失——必须补

TUN 的 UDP 不走 `ChannelOpener`，走独立管道：`try_forward_udp`（tun.rs:1741-1788）→ `UdpCmd` 通道 → `udp_relay_task`（tun.rs:1473-1594）经节点中继。v1 设计只字未提 UDP，后果：

- QUIC/HTTP3（UDP 443）到 CN 目标全部走节点中继——浏览器优先 QUIC，**TCP 分流形同虚设**（流量大头在 QUIC 上绕道）；
- DNS 也是 UDP：`dns_via_proxy=true` 时 DNS 同样经 `try_forward_udp` 进中继（tun.rs:2064）。**回答评审问题：两处都要接规则，且实为同一处**——`try_forward_udp` 是 DNS 与数据 UDP 的公共分发点，规则判定应加在此处（目标 IP:port → 规则 → DIRECT 走「bind 物理 IP 的本机 UDP socket 直发」或 PROXY 走既有中继）。UDP 直连需要一个本机 UDP socket 池（bind 物理源 IP + 回包注入 TUN），这是 v1 新增工作量，设计必须列出。

### R2（P0）规则模式与 DNS 策略联动缺失

见 §2.2。规则模式启用时必须显式定义 DNS 行为（直连解析 / 经节点解析，默认值 + GUI 提示），否则 GeoIP 分流对 CDN 流量静默失效。至少在 §3.2 写明「规则模式建议配合 HYDRA_TUN_DNS_DIRECT=1」。

### R3（P1）direct opener 必须过 socket_protect 钩子（Android 对齐）

现状所有出站连接统一走 `connect_tcp_protected`（proxy.rs:1384、tcp_transport.rs:482/558；socket_protect.rs:61-80：Android 下 protect(fd)，桌面零开销直通）。新 `tun_direct_opener` 若裸用 `TcpSocket::bind + connect` 会绕过钩子——未来 Android（v2.1 的 tun_core 复用同一 channel 接口，tun.rs:826-828 注释）上直连会被自身 VpnService TUN 捕获回环。**回答评审问题：直连与 protect 钩子正交互补**——桌面防回环靠「bind 物理源 IP」（路由层），Android 防回环靠 `protect()`（VpnService 层），direct opener 必须统一走 `connect_tcp_protected` 再叠加 bind，且 bind 参数化要抽象（桌面=bind IP，Android=protect 无 bind），`direct_bind_ip` 单参数不够。设计 §五 把 `tun_direct_opener` 放在 hydra-core 是对的，但需写明钩子契约。

### R4（P1）`direct_bind_ip` 的探测来源未落点

v1:25 说「由上层（RouteGuard/网关探测基建）填入」，但现状 `detect_physical_gateway`（tun.rs:634-679）探测的是**网关 IP**，不是**本机物理网卡源 IP**——两者不是一回事（网关可能是旁路路由）。需新增「本机物理网卡源 IP 探测」（Windows：`GetBestRoute(目标)` 返回的源地址，或 best-route 探测法；Linux：connect UDP socket + getsockname 技巧），设计应列明函数落点与失败语义（None → 全部走节点 = 规则模式静默退化为全局代理，UI 应可见）。

### R5（P1）私网目标的规则兜底

私网段正常时被豁免路由引回物理网关不进 TUN（tun.rs:250-256）；但豁免缺失场景（网关探测失败）私网 TCP 包会到达栈且被 `handle_v4_else` 丢弃（tun.rs:2178-2189）。规则引擎应内置「私网/回环/链路本地 → DIRECT」最高优先级匹配：direct opener bind 物理 IP 后连私网目标通常可行（可访问 NAS/路由器），比丢弃/走节点（节点 SSRF 拒绝）语义都好。

### R6（P1）IPv6 GeoIP 表缺失的策略必须显式

`ipv6_enabled` 默认 true，v6 TCP 已被代理。若 GeoIP-CN 表无 v6 段，v6 目标全部默认走节点——可用但国内 v6 流量（国内运营商 v6 普及率高）全绕道。三选一写进文档：(a) 构建脚本同步产出 v6 CN 段（u128 数组）；(b) v1 对 v6 目标固定 DIRECT（配合 R3 直连）；(c) v6 固定 PROXY 并声明。推荐 (a)，工作量小。

### R7（P2）ICMP 现状即静默丢弃，与规则分流无关但要声明

现状 IPv4 ICMP 一律丢弃防 any-ip 伪造回显（tun.rs:2154-2158，09-P2-2）、ICMPv6 同（tun.rs:2027-2031）。规则模式不会改变此行为——「CN 直连后 ping 通」用户预期会提升，文档应声明 ping 不通仍属设计内（测试章节 v1:91 的真机验证项建议改为「TCP 可用性 + IP 属地」而非 ping）。

### R8（P2）规则文件编码/换行容错

`%APPDATA%\rules.txt` 用户手工编辑：需容忍 UTF-8 BOM、CRLF、行尾空白、`#` 内联注释。旧版记事本可能存为 ANSI（GBK）——解析到非法 UTF-8 时应告警并跳过该行（而非静默整表失效）。热重载 v1 不做可接受（v1:60/67 已声明重启生效），GUI 已有「重启提示」配套（v1:72）。

### R9（P2）GUI「规则分流」文案的数据源错位

v1:73 说「boundAddr 显示规则分流……」。核实：桌面 GUI 的 `proxy_bound_addr` 是本地 SOCKS 监听地址（hydra-client-gui/src/main.rs:80、proxy_control.rs:431），与 TUN 运行状态是两个数据源；UI v4 的首页 Hero 条第三格是「监听摘要」（桌面端UI重设计方案-v4.md:104）。规则模式文案应挂在 **TUN 运行状态位**（而非覆盖 boundAddr 字段语义），否则 TUN+SOCKS 并存时监听地址信息丢失。文案建议「规则分流 · CN 直连 · 其余经节点」并同时保留监听地址小字。另注意 Android 端 `boundAddr` 文案已固定为「全局 VPN（所有应用流量经节点）」（HydraVpnService.kt:290），v2.1 对齐时同改。

### R10（P2）端口规则与动态监听的关系确认

R1 任意端口动态挂监听已交付（tun.rs:1817-1837），规则分流对所有端口可达，无额外限制——设计无需改动，仅在此确认无冲突。

## 五、结论

**需修订后实施**。技术路线（方案 A 源地址绑定）在 Windows 强主机模型下成立，性能设计（二分 + 嵌入 + spawn_up_task 前判定）全部合理，与现有 `ChannelOpener`/`ProxyDuplex`/`try_forward_udp` 结构的接合点清晰。但 v1 文档存在三个硬伤：UDP 分流缺失（R1，缺失即 QUIC 流量全走节点、分流目的落空）、DNS 策略联动缺失（R2，缺失即 GeoIP 对 CDN 流量静默失效）、direct opener 与 protect 钩子契约缺失（R3，Android 对齐即返工）。补齐 R1-R3 及 R4-R6 后可进入实施。
