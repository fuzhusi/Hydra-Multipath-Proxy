## 1. P1（高，7 项）

### P1-1 节点 UDP 中继连接无连接级空闲看门狗 → 认证连接可永久钉满连接额度
- 位置：`hydra-node/src/udp_relay.rs:362-385`（`serve_with_idle` 上行读循环裸 `read_udp_frame`，无 timeout）、`hydra-node/src/tcp_server.rs:296-302`（分流调用点无超时）。
- 触发：已认证客户端开 `@udp-relay/` 连接后不发一字节不关流（恶意或半开连接——`TcpStream` 未设 keepalive）。每条永久占用 1 个 Semaphore permit + fd + reaper 任务；默认 `max_connections=1000`，1000 条即全节点拒绝服务。对照：TCP 转发路径有 pump idle 看门狗（300s）、信令路径有 90s 读超时，唯独 UDP 中继三无。**两个审查代理独立发现，结论一致。**
- 修复：`read_udp_frame` 外包连接级空闲超时（复用 idle 语义 90-300s），超时 break 走既有清理（`reaper.abort()`）；可加 TCP keepalive 兜底。补"连接静默 N 秒关闭"测试。

### P1-2 客户端双向转发无空闲超时、全仓库无 TCP keepalive → 静默死亡连接永久泄漏
- 位置：`hydra-core/src/proxy.rs:1071-1140`（上下行循环裸 read/write）；`grep keepalive` 全仓库零命中（`tcp_transport.rs:423` 只设 nodelay）。
- 触发：节点掉电/网线拔出/NAT 空闲回收映射且不回 RST → `down` 任务阻塞在 read 永不返回，`up` 随后被发送缓冲背压阻塞；四个收敛分支只覆盖"任一方向先结束"，双向静默时 select 永久悬置。每泄漏连接占 2 任务 + 2×16KB 缓冲 + 连接注册表永久条目；TUN 每流一条，长时间运行持续累积。
- 修复：上下行 read 包 `tokio::time::timeout(IDLE_TIMEOUT)`，或对节点 TCP 流启用 socket2 keepalive（idle≈空闲超时、interval 5s、retries 3）。

### P1-3 `target_unreach_counts` 进程级 HashMap 无上限无 TTL → 内存打满
- 位置：`hydra-core/src/proxy.rs:58-99`。key 为客户端提交的原始目标串（SOCKS5 域名约 262B 上限），仅"连接成功"与"达阈值重置"两条清除路径。`--listen 0.0.0.0`（代码注释明示支持）时任意 LAN 主机每次连接提交一个唯一且必然被拒的目标（随机子域/私网 IP）→ 每条约 350B 永久驻留，分钟级可注入数百 MB。已核实代码证据属实。
- 修复：改 `(u32, Instant)` 惰性过期，或设容量上限（如 10 万条超限驱逐）。

### P1-4 分享链接数值参数无范围校验 → 恶意订阅操纵调度（NaN 胜出 / -1e300 恒第一）
- 位置：`hydra-core/src/share_link.rs:391-410`（`bandwidth/latency/loss_rate/load` 仅 `parse::<f64>()`，`NaN/inf/±1e300` 全部解析成功）。已核实代码证据属实。
- 后果链：恶意订阅行 `hydra://1.2.3.4:443?bandwidth=NaN` 导入即注册为 Online；`scheduler.rs:38-43` `max_by` 语义下 NaN 与任何节点比较恒 Equal，HashMap 随机序约 50% 胜出健康节点；`loss_rate=-1e300` 评分为 +2e299 确定性恒排第一；且该节点无法完成 Noise 握手 → 无中继字节 → `merge_stats` 永不覆盖，污染持久。效果为稳定全量降速 DoS；若攻击者持有 PSK 则直接流量劫持。
- 修复：解析期校验 `is_finite()` 且范围合法（bandwidth/latency≥0、0≤loss_rate≤1、0≤load≤1），`update_node_stats` 入口再做一次 clamp。

### P1-5 客户端 UDP 会话号只增不回收 → u16 耗尽后整条通道永久报废
- 位置：`hydra-core/src/udp_relay.rs:76-96`。sid 单调分配，注释自认"号本身不回收"；TUN 全流量场景每个目标 addr:port 占一个 sid，一次性 DNS 目标/P2P 每分钟上千个即可约 1 小时耗尽 65535；耗尽后 `checked_add` 永久 Err，无自愈/重建。该模块尚未接入生产调用链（TUN UDP 接线前必修）。已核实代码证据属实（含"会话号耗尽（请重建通道）"注释）。
- 修复：sid 池化复用（节点以 sid 为键无历史唯一性要求），或耗尽时重建通道；至少给 `sessions` 加容量上限。

### P1-6 GUI TUN 失败与就绪信号竞态 → 显示"TUN 已全局接管"实际流量明文直连
- 位置：`hydra-client-gui/src/main.rs:915-927`（就绪即发 Ok）、`1750-1760`（TUN 任务失败另发 Err 走同一 mpsc）、`1819-1860`（`poll_start_receiver` 只处理首条消息，其余降级为日志"附加启动消息（勿忽略）"；`tun_enabled` 分支跳过系统代理设置）。已核实代码证据属实。
- 触发：SOCKS 先 bind 成功（先发 Ok）→ UI 置 `proxy_running=true` 并跳过系统代理；随后 TUN 失败 Err 只进日志。终态：托盘/首页显示运行中，TUN 已死、系统代理未设，用户以为全局被代理，实际明文直连（隐私态势显示错误）。
- 修复：已置 `proxy_running` 后收到 Err 不得仅记日志——应视为降级事件：`tun_enabled` 置回 false、回退设置系统代理、首页显著告警；或 TUN 失败一律走启动失败分支。

### P1-7 Android R4 防环回：SocketProtect 回调被丢弃，未接线到任何出站 socket
- 位置：`hydra-android/src/lib.rs:145-147`：`// R4：回调交引擎持有（M2 接线）` / `let _protect = protect;` —— 构造即析构。已核实代码证据属实。
- 现状无 VpnService 故不环回；但按方案叠加 TUN/VPN（M2）时，所有到节点的出站连接（TCP 与 UDP）未经 `protect()`，流量被自己的 TUN 捕获 → 无限回环/断网。这是 Android 方案 v2.1 R4 必须项，属 VPN 交付硬前置缺口（当前代码状态"接口已定义、零接线"，与 CHANGELOG 声明一致，但需在 M2 开工前列为第一依赖）。
- 修复：在引擎出站建连唯一收口（建议 hydra-core transport 层 hook trait）回调 `protect(fd)`（TCP connect 前、UDP sendto 前），失败时中止该连接而非静默放行。
