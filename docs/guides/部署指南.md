# Hydra 节点部署指南

面向运维的最小部署手册：3 条命令部署、防火墙、排障表、升级流程。
本指南对应仓库内 `deploy/` 套件（systemd unit / env 模板 / install.sh / docker）。
部署演练中的坑位与修复对照见 [docs/assessment/部署运维评估.md](../assessment/部署运维评估.md)。

---

## 1. 三条命令部署（systemd，推荐）

前置：一台 Ubuntu/Debian VPS，已装 Rust 工具链（cargo 1.81+）、openssl、git。
仓库内**没有远程发布产物**（无预编译包），必须在 VPS 本地构建（首次约 2-5 分钟）。

```bash
git clone <你的仓库地址> hydra && cd hydra     # 前置步骤，不计入三条
cargo build --release -p hydra-node            # ① 构建
sudo ./deploy/install.sh                       # ② 安装（用户/配置/密钥/systemd/自启）
sudo systemctl status hydra-node               # ③ 确认运行（active (running)）
```

`install.sh` 自动完成：

| 动作 | 落点 | 说明 |
|---|---|---|
| 安装二进制 | `/usr/local/bin/hydra-node` | 来自本地构建产物 |
| 创建系统用户/目录 | `hydra` 用户、`/etc/hydra`（750） | 节点不以 root 运行 |
| 生成环境配置 | `/etc/hydra/env`（600） | 密钥未提供时自动 `openssl rand -hex 32` 生成 |
| 安装 unit 并自启 | `/etc/systemd/system/hydra-node.service` | `enable --now`，崩溃自动重启 |

脚本结束会打印**认证密钥**（客户端配置用）与证书分发指引。密钥管理规则：

- **不要** `export HYDRA_AUTH_KEY=...`（进 shell history）、**不要** `--auth-key` 参数（进 `/proc/<pid>/cmdline` 全机可读）
- 改密钥/端口一律 `sudo vi /etc/hydra/env` 后 `sudo systemctl restart hydra-node`

unit 已内置的修复与加固（对应评估报告坑位）：

- `WorkingDirectory=/etc/hydra` —— 证书固定生成在 `/etc/hydra/hydra-node-cert.der`，修掉"systemd 从 `/` 启动导致证书重生成、客户端全员失配"的 CWD 陷阱
- `AmbientCapabilities=CAP_NET_BIND_SERVICE` + `User=hydra` —— 非 root 绑 443，无需 setcap/root
- `EnvironmentFile=/etc/hydra/env` —— 密钥不进 unit 文件（world-readable）、不进 history/cmdline
- `Restart=always` + `ProtectSystem=strict`、`ReadWritePaths=/etc/hydra` —— 崩溃自拉起，全盘只读仅证书目录可写

首次启动后把证书分发给客户端（客户端 pinning 用）：

```bash
sudo scp /etc/hydra/hydra-node-cert.der <客户端机器>:<目录>/
```

## 2. Docker 部署（替代方案）

```bash
cd deploy/docker
cp ../env.example node.env && vi node.env    # 填 HYDRA_AUTH_KEY（勿 export）
docker compose up -d --build                 # 构建+启动，443/tcp 已映射
docker compose cp hydra-node:/etc/hydra/hydra-node-cert.der ./hydra-node-cert.der
```

- 证书持久化在命名卷 `hydra-data`（对应容器 `/etc/hydra`），容器重建**不**重新生成证书
- 容器内非 root 运行，compose 已 `cap_add: NET_BIND_SERVICE` + `cap_drop: ALL`
- 健康检查如需从宿主 curl：把 `node.env` 里 `HYDRA_HEALTH_ADDR` 改为 `0.0.0.0:8081` 并放开 compose 中 `8081/tcp` 映射（公网机器注意防火墙拦 8081）

## 3. 防火墙

```bash
sudo ufw allow 443/tcp        # 节点数据面（TCP/TLS），必须放行
sudo ufw status verbose       # 确认 443/tcp ALLOW Anywhere
```

- **健康检查端点只绑 `127.0.0.1:8081`**（`/etc/hydra/env` 默认值），是宿主本机拨测/负载均衡探活用的，**不要**放行到公网，也不要绑 `0.0.0.0`
- 客户端从 `127.0.0.1:1080`（SOCKS5/HTTP 本地代理）接入，与节点端口无关

## 4. 排障表（"连不上"三类静默故障 + 指纹）

> 背景：节点把未认证的流**静默关闭**（反主动探测的设计意图），副作用是
> 防火墙未放行 / 密钥不一致 / 端口错 三种故障在两端日志里**看起来一样：什么都没有**。
> 按下表逐项区分。另可用 `curl http://127.0.0.1:8081/health`（VPS 本机）先确认节点进程活着。

| 故障 | 症状 | 确认方法 | 修复 |
|---|---|---|---|
| **防火墙未放行** | 客户端节点 Offline/超时；VPS 本机 `curl /health` 正常；节点日志**无** "TCP/TLS transport ... listening" 之外的新连接痕迹 | VPS 上抓包：`sudo tcpdump -ni any tcp port 443`——客户端重试时**无任何 TCP SYN 到达** | `sudo ufw allow 443/tcp`（或云厂商安全组放行 443/tcp，两处都可能拦） |
| **密钥不一致** | 客户端超时/OFFLINE；VPS 本机 `curl /health` 正常；抓包**能看到 TLS 握手完成**但随后连接被静默关闭；节点日志只有 TLS accept、无转发成功记录 | 比对两端密钥：节点 `sudo grep ^HYDRA_AUTH_KEY /etc/hydra/env`；客户端看其环境变量/配置。两端 hex 完全一致才合法 | 客户端改为与节点一致的密钥（或节点 `vi /etc/hydra/env` 改后重启，**两端同时换**） |
| **端口错** | 客户端超时；抓包有 TCP 包但到达的不是节点监听端口；`ss -lntp` 看不到监听 | VPS 上 `sudo ss -lntp \| grep hydra`——确认实际监听地址端口与客户端配置的 `节点IP:端口` 一致 | 客户端节点地址改成 `/etc/hydra/env` 里 `HYDRA_LISTEN` 实际端口；或改 `HYDRA_LISTEN` 后 `restart`（注意同步改防火墙规则） |
| **证书指纹不匹配** | 客户端报 TLS/证书校验类错误（pinning 失败），连接在握手阶段被拒；节点日志可能只有 "Connection error" | 对比指纹——节点：`openssl x509 -inform der -in /etc/hydra/hydra-node-cert.der -noout -fingerprint -sha256`；客户端：检查其 `HYDRA_NODE_CERT` 指向的文件是否同一份（`ls -l` 日期/大小，或本地同命令跑一遍） | 重新分发：`sudo scp /etc/hydra/hydra-node-cert.der 客户端:路径/` 并更新客户端 `HYDRA_NODE_CERT`。若节点证书意外被删导致重新生成（生成时间与 `/etc/hydra` 内文件 `stat` 对不上），必须全量重发证书 |

辅助判据：`journalctl -u hydra-node -f`（节点日志，info 级目标地址已脱敏为短哈希，
`RUST_LOG=debug` 可看明文，见 §6）；客户端 `RUST_LOG=debug` 可看离线/切换原因。

## 5. 升级流程（证书/密钥不动）

```bash
cd /path/to/hydra && git pull
cargo build --release -p hydra-node
sudo ./deploy/install.sh          # 幂等：覆盖二进制与 unit；/etc/hydra/env 已存在则保留（密钥不动）
sudo systemctl restart hydra-node # 若 install.sh 未自动重启
```

要点：

- **`/etc/hydra` 是状态目录**：证书、私钥、env 全在里面，升级流程不触碰 → 客户端 pinning 与密钥继续有效，无需重新分发
- 版本回滚 = 检出旧 commit 重新构建再执行同一流程
- 若升级后客户端大规模失配，按 §4 "证书指纹不匹配" 行排查（先确认 `/etc/hydra/hydra-node-cert.der` 修改时间是否早于本次升级——早于即证书未被触碰，问题在别处）

## 6. 反代静态页（抗主动探测，可选）

默认关闭。`/etc/hydra/env` 中：

```bash
HYDRA_FALLBACK_PAGE=1   # 开启；默认 0 = 静默关流（行为零变化）
```

开启后，非代理流量访问 443（TLS 建立后版本字节/握手/认证失败）会收到一份
内置静态网页（伪装普通个人博客，无本项目字样）而非静默断开，即 Trojan 式
标准反代伪装。**取舍**：静默关流「有 TLS 却永不出字节」是指纹；回退页像真
网站但「每次都同一页面」也可被批量探测统计。**建议真证书部署开启**，自签
无域名隐蔽部署保持关闭。回退路径仍受认证超时与连接额度保护。

## 7. 日志与健康检查说明

- systemd 日志走 journald：`journalctl -u hydra-node -f`（无需另行配置文件日志）
- **info 级日志中目标地址一律脱敏**为 SHA-256 短哈希（如 `a1b2c3d4:443`）——节点日志落在公网 VPS 上，不泄露用户浏览历史；需要明文排障时 `RUST_LOG=hydra_node=debug`（仅临时、仅回环排查场景）
- 健康检查（默认 `127.0.0.1:8081`）：

  ```bash
  curl http://127.0.0.1:8081/health
  # {"status":"ok","mode":"tcp","uptime_secs":1234,"version":"0.1.0"}
  ```

  未设置 `HYDRA_HEALTH_ADDR` 时端点关闭；其他路径 404，非 GET 405。
- 密钥轮换：两端同时改 `HYDRA_AUTH_KEY` 并重启（客户端重启代理，节点 `systemctl restart`）；换证书 = 删除 `/etc/hydra/hydra-node-{cert,key}.der` 重启 + 重新分发，两者都会导致客户端重配
